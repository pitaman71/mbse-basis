From the workspace's `VISUALIZATION.md`. Index entries: [FEATURES.md](../FEATURES.md#FEA-007), [CAPABILITIES.md](../CAPABILITIES.md). A capability without an ID is not in plan yet.

## <a id="CAP-014"></a>CAP-014 · object properties as markdown

- anything currently represented as Schemas.OfStr is to be interpreted as
  markdown
- in object detail panel click/tap on 'edit' button toggles from view mode to edit mode
- in object detail panel view-mode, clicking on property value also toggles from view mode to edit mode
- properties participating in an ownership key are not editable here
- in edit mode 'cancel' button discards changes, 'save' button commits
- during commit, inspector toggles from edit mode to save mode
- in save mode values cannot be modified, close is disabled, save shows busy
- when services confirm edits are accepted and committed, inspector panel toggles back to view mode
- no UI or services validation at this time. all data is good data for now

## <a id="CAP-022"></a>CAP-022 · boolean properties as checkboxes

Every `Schemas.OfBool` property is shown and edited as a checkbox, in the
object inspector (CAP-017) and the adjacency inspector (CAP-018).

## <a id="CAP-015"></a>CAP-015 · transaction provenance

Services retain a record of each transaction that writes, as mbse-schemas'
`Provenance` module defines it (proposals/transaction-records, for
mbse-schemas): a `Provenance.OfTransaction` keyed by the transaction's
uid, with its `when` and `where`; its `Provenance.OfSession`, with the
session's locale, device and identity (`Provenance.Who`,
`Provenance.OfIdentity`); and `Provenance.CreatedBy` and
`Provenance.ModifiedBy` (the latest write only) linking the objects of
the schemas an app chooses.

- the service validates the user's token and writes the session's id and
  identity, and the transaction's `when`, into the mutation before
  executing and journaling it; the token itself is never recorded
- the UI provides the session's locale and device, and the transaction's
  geolocation where given, in the mutation
- the detail view (CAP-007) of an object whose schema has provenance also
  carries it: its `CreatedBy` and `ModifiedBy` entries, each transaction
  record, its session and the session's identity, in the frame's
  `assigns` and `entries`, so the UI fetches provenance with the object's
  detail and needs no request of its own

## <a id="CAP-016"></a>CAP-016 · comments

Comments are data in the demo app's schema, shown and posted through
general, schema-driven capabilities; nothing in the UI is specific to
comments.

- the demo app models them: `work.Comment` (`text`, and `resolves_thread`
  of `Schemas.OfBool`), about topic elements through `work.About` (a
  thread), replying to a thread through `work.RepliesTo` (a reply); the
  two relations give the two levels
- `work.Comment` has provenance (CAP-015): the demo app's install calls
  `Provenance.extend` for it, so each comment has its author, session and
  time
- posting: "+" on an element's comments opens the adjacency inspector
  (CAP-018) with a proposed comment, and "+" on a thread's replies, with a
  proposed reply; checking `resolves_thread` (CAP-022) marks a reply as
  resolving its thread
- showing: a topic's detail ends with its threads, and a thread's detail
  with its replies (CAP-019), in the order created (CAP-021), each with
  its author and time (CAP-020)
- for the demo, the user's identity is fudged (CAP-015)

### shared property handling by UI

There is an important modeling case where an object logically 
shares a property with one of its adjacencies. This case is common, but 
not assumed by default. A directory for example might put "name" on the 
link and on located/defined object.

Eventually this modeling case will be directly handled via 
adjacency constraints. Until then, it is handled with a feature of
`Visitors.OfAdjacency` which supports visiting a shared property
of the entry and of the "other" linked object for applicable relation 
schemas. In this mode, if the same property (by name) exists on both the
relation entry and on the "other" linked object:

- reading the shared property value reads the value from the entry
- setting the property value via the adjacency visitor should 
  result in both the link property and the object property being set to 
  the same value. 
- modifying the property value by any other mutation verb (append, 
  insert, remove, etc.) has undefined effect on the object property 
  value.

### object properties as text/date

- domain representations carry three things simultaneously (PRI-023)
- add new repo `mbse-domains`. this may eventually get folded into 
  `mbse-expressions` but for now it allows us to extend the visualization
  work without carrying an in-progress overhaul from `mbse-schemas` 
  into `mbse-expressions`
- in new repo `mbse-domains` define `Dialects.Text.Word`, `Dialects.Text.Phrase`, `Dialects.Text.Paragraph` and `Dialects.Text.Document`
- in `mbse-domains`, define `Dialects.ISO8601.CalendarDate`, 
`Dialects.ISO8601.OrdinalDate`, `Dialects.ISO8601.Duration`, `Dialects.ISO8601.Interval`, etc. Each carries the three things a domain representation carries: a property for the string representation, which may contain invalid data; a validation indicator for each possible validation error; and properties that encode the date in ISO8601 format
- modify `mbse-demo-apps` to use `mbse-domains` and prefer the refined `Dialects.Text.*` and `Dialects.ISO8601.*` forms over `Schemas.OfStr`
- in object detail panel, property value display automatically configures based on `Dialects.Text` subtype
