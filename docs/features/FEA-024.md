# FEA-024: expressions as data

*Confers* [QUA-002: open-world models](../QUALITIES.md#QUA-002), [QUA-004: models as an alternative representation of source code](../QUALITIES.md#QUA-004). Index entry: [features/README.md](README.md#FEA-024).

Serializable expressions for [mbse-schemas](https://github.com/pitaman71/mbse-schemas): constraints about its data,
which [mbse-patterns](https://github.com/pitaman71/mbse-patterns) keeps as constraints, such as "at least one phone",
and uses as queries. This package depends on mbse-schemas (a sibling checkout, pinned in `siblings.json`), whose
[schema-driven data](README.md#schema-driven-data) describes the framework; this
feature covers expressions only.

Expressions come in dialects: expression languages that implement one framework, so that each is serializable,
structurally traversable, validatable, evaluatable, and translatable into the others. The Basic dialect is the core
vocabulary below, in which constraints about mbse-schemas' data are written; `from mbse.Expressions import Expressions,
Evaluators` imports it. The Python, Matlab, Excel, Latex, Ccpp (C and C++) and SystemVerilog dialects model those languages' expressions (see
[CAP-100: six languages' expression dialects](../capabilities/CAP-100.md)); the framework is described in
[CAP-098: dialects over one framework](../capabilities/CAP-098.md), and translation in
[CAP-101: translation between dialects](../capabilities/CAP-101.md). Both implementations have all of them (see [Equivalence](../../../mbse-expressions/docs/EQUIVALENCE.md)).

Its port to the stabilized mbse-schemas is [a proposal of mbse-expressions](../../../mbse-expressions/docs/proposals/port/README.md), in progress.

## Open questions

- **Removing Basic** stays deferred ([the port](../../../mbse-expressions/docs/proposals/port/README.md), question 9, and Resolved, "Dialects hold the
  semantics of datatypes and operations"): Basic is kept through the port, the oracle the tests are written in. Open:
  which standards' and languages' dialects take its value domains (IEEE 754, IEEE 1164, C's fixed-width integers), and
  how translators through Basic become transform steps.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **Porting to the stabilized mbse-schemas** (2026-10-28 and 29), as the user decided on
  [the port's proposal](../../../mbse-expressions/docs/proposals/port/README.md) (its Decided, recorded there in full; quoted here where the wording
  matters). mbse-expressions moves from mbse-schemas 0.10 to 0.26, whose store overhaul is done:
  1. **Model first** ("yes"): the framework and each dialect are defined by installs (a module-scope `install(txn)`),
     terms are stored in the store, and the cases are rewritten to it; no runtime view over the old classes.
  2. **Terms are one nested value**, held by an expression, a reference object, its root ("yes").
  3. **`Schemas.OfExpression` gains its terms by an extension adjacency** ("yes"): a relation of two links from it to
     the expression holding the term (`Expressions.Framework.HasRoot`).
  4. **A dialect defines its domains by name**, through `Expressions.Framework.Defines(dialect, name, domain)`: "you
     don't need to repeat the parent scope in the name. mbse-expressions.Framework.Defines is not the same as
     mbse-schemas.Schemas.Defines". The plan's `DefinesDomains` goes. A basic scalar has one domain or more through
     `HasDomain(schema, domain)`; a domain is an object.
  5. **The executor's evaluator is a protocol in mbse-schemas, given to a store once**, "a fine intermediate solution
     for now"; the executor refuses as today where none is given.
  7. **A variable over a finite domain is in the plan** ("(b) is in the plan"): each frame fans out into one frame per
     value the domain holds and its pattern's `requires` allows (bool, an enum). A variable computed from the frame:
     "(a) is not in the plan". Solving for a variable's values: "(c) can be deferred".
  9. **Basic is kept through the port**; removing it stays deferred ("yes").
  10. **The writers are kept**, until mbse-codegen-python moves off them ("yes").
  11. **All six dialects and the twelve translators are ported with the model**; vocabularies as data and value
      parameters after ("yes").

  And on what stage 2b raised (2026-10-30), "yes" to each: **a dialect reuses the framework's kinds wherever the shape
  matches** ([CAP-100: six languages' expression dialects](../capabilities/CAP-100.md#decided), Decided), and **a
  term's domain is a registered name until stage 3** ([CAP-097: value domains of published standards](../capabilities/CAP-097.md#decided), Decided).
- **Dialects hold the semantics of datatypes and operations** (from the `scalars` branch, reapplied as the port's
  proposal states it, not cherry-picked: that branch cites mbse-schemas items that never landed, a palette, `OfName`,
  scalars as placeholders, and mbse-schemas has since made the five basic scalars real and finer scalars domains here,
  its Store overhaul, Decided, 8 and 9). As the user put it: "I generally dislike semantics of datatypes and
  operations leaking into the modeling language as currently built"; dialects hold the semantics of datatypes and
  operations, one for each language's built-ins and for interoperation types such as IEEE 754; "the attempt to invent
  a neutral type system was a mistake. we should model standards not invent them", so a neutral Basic "should be
  removed", its expression kinds and three-valued evaluation kept, and translation across languages belongs to
  transforms. Removing Basic itself stays deferred (Open questions). The user's decisions on domains are in
  mbse-schemas: Store overhaul, Decided, 8, 9 ("all scalars are domains and users may define domains and dialects
  containing domains"; "a scalar schema can have > 1 domain"; "width is a property of the domain, not the schema") and
  22 (formats become domains); Schema extension, Decided, 9 to 14 and 21.
- **(schema extension 4)** Defaults: codegen "would work with or without the additional schema info from mbse-expressions, and if absent
  should assume the most universal default. in the case of size, that makes a scalar without a domain basically
  plain data".
- **(schema extension 5)** `requires` "moves out of mbse-schemas all the way out to `mbse-patterns` using the new extension mechanism".
- **(schema extension 6)** "all bindings will need to move into mbse-expressions": `OfApply` and its arguments, literal values and terms
  (`ArgumentTerm`), with mbse-schemas declaring `parameters` only ("it matches well enough").
- **(schema extension 7)** `Form` "should go" from mbse-schemas.
  As built, for 5 to 7: since 0.17.0 mbse-schemas has no `requires`, `OfApply`, arguments, terms or `Form`, nor
  widths (Store overhaul, Step 2, as built); their homes in mbse-expressions and mbse-patterns are still to be built.
- **(schema extension 8)** Scalar values, formal parameters and intrinsics: see section 2.
- **(schema extension 9)** "printers and parsers go through Visitor just like everything else" ([PRI-018: no model needs code to read or write](../PRINCIPLES.md#PRI-018)); only intrinsics'
  implementations are code, each found through its named reference object (`AsIntrinsic`).
- **(schema extension 10)** "free variables are just free variables": each dialect (Python, Excel, MATLAB, ...) "selectively permit[s] access
  to global context by free vars".
- **(schema extension 11)** Signatures: `Same` and `Overloaded` are "specific names that resolve function binding". A signature is a
  `Function`, named, with formals and a result, each typed by a schema; several functions may share a name, and a call
  binds to one by its name and its arguments' types. Intrinsics, native functions registered against named reference
  objects, implement them (sections 4 and 5).
- **(schema extension 12)** "any expression dialect can define scalar domains that make sense. the scalar types defined in mbse-schemas aren't
  special and could potentially go away".
- **(schema extension 13)** "expressions only deal in scalars. All object/relation functionality is moving up to mbse-patterns". Containers of
  scalars stay: "quantifiers over containers - starting with map/reduce - should be included". Terms were first made
  reference objects ("terms are reference objects"), so that other packages' relations could link them; reviewing the
  framework model's draft, the user undid that ("undoing decision 13 might be the right track"): terms are values,
  an expression one nested value held by a reference object, its root, which is all that is linked. "call terms may
  name their function", bound by its name and its arguments' types; "`HasSchema` annotates the root, never a
  subterm" (superseded by 21: a root has no schema); "`requires` is moving out to mbse-patterns anyway"; and the losses, sharing a subterm and linking one from
  outside, are not a problem ("I don't think the losses are a problem"). Kinds are a union again (decision 3).
- **(schema extension 20)** A dialect's vocabulary (its domains, functions and intrinsics, data installed in a store): "yes to the handshake,
  fallback to adding if fails". A store connection's handshake names the dialects both sides install, and a snapshot
  does not write their vocabulary; where the handshake fails, the vocabulary is written.
- **(schema extension 21)** Domains: a scalar schema has a domain, `HasDomain(schema=Schemas.OfScalar, domain=Expressions.Framework.Domain)`
  ("Moving `.bits` and `.bytes` means associating a domain to a scalar schema", section 2); domains stay objects. A
  term has a domain ("variables are implicitly bound to terms and terms have a domain"). Revised 2026-10-16: an
  expression's root no longer has a schema, so `HasSchema(root=Expressions.Framework.Root, schema=Schemas.OfY)`, and
  the domain reached through it in two steps ("a two-step association using your new expression-root ref obj"), are
  gone.
- **(schema extension 22)** Formals are objects (`Function` → `HasFormal`, with an index → `Formal` → `FormalType` → schema), since a
  meta-schema's adjacency is to a relation of two links and no properties: "yes that's a compromise".
