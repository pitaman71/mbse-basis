# FEA-003: no-code logical views

Index entries: [features/README.md](README.md#FEA-003), [capabilities/README.md](../capabilities/README.md). A capability without an ID is not in plan yet.

Logical views define specific query formats
that must be accessible from the backend via a mutation
expression.

Backend interaction is batched by allowing logical views
to be either requested in isolation or sensibly nested
in a single response. Sensibly nested usually involves

- treating a query as graph traversal
- query-specific limited adjacency traversal rules
- query-specific level of detail per visited object/adjacency

Each logical view kind defines which properties, adjacencies and closures
its response includes.

Objects and relation entries are designated by mbse-schemas References:
`References.OfObject` for an object and `References.OfEntry` for a relation
entry. A response is a stream of `References.OfFrame`, whose `assigns`
(`References.OfProperties`) and `entries` (`References.OfEntry`) carry the
view's data.

Only singletons and owned objects have references. Counted objects are
not recorded or transmitted (tech debt, to revisit).

## Not yet planned

### logical view of object as detail with closures

Extends [CAP-007: detail view](../capabilities/CAP-007.md): the response also comprises the closures of the object.

### logical view of closure as list of chips

Given a `References.OfObject` or `References.OfEntry`, 
UI can obtain a logical view template, the response for which
comprises a list of transitively adjacent objects each of
which includes the linked object and a chip view of that object.

## As built

### View kinds

The server executes the transaction and, for each frame the executor gives back, writes a `References.OfFrame`:
`binds`, each symbol's `References.OfObject`; `assigns`, a `References.OfProperties` for each object it witnesses,
once, in the order met; `entries`, a `References.OfEntry` for each entry it witnesses, once. `variables` is empty.

| Kind | `assigns` | `entries` |
|---|---|---|
| `label` ([CAP-005: label and summary view](../capabilities/CAP-005.md)) | `x`: its label's and its summary's properties | none |
| `chip` ([CAP-006: chip view](../capabilities/CAP-006.md)) | `x`: `label`'s, then the first three other scalar properties its schema declares that it holds | none |
| `detail` ([CAP-007: detail view](../capabilities/CAP-007.md)) | `x`: every property it holds; then each object its entries link: `label`'s | every entry of each of `x`'s named adjacencies, in the schema's order |
| `adjacency` ([CAP-008: adjacency as a list of chips](../capabilities/CAP-008.md)) | `y`: `chip`'s | every entry of `x`'s named adjacencies that links `y` |

- **Label and summary** ([CAP-005: label and summary view](../capabilities/CAP-005.md)'s convention). The label's property is the first of `label`, `name` and `title` that
  the object holds; the summary's, the first of `summary` and `description` that it holds. The values are the properties' own, so `assigns` names them as
  the schema does (`title`, not `label`). The client reads them back: `Views.label`, `Views.summary`, `Views.chip`.
- **Fallbacks** (client side, from what the frame carries). An object's label, where it holds none: its schema's
  name, where the caller knows it (it gave the symbol that schema), and its path's last key, the owning entry's key
  values, or, a singleton, the singleton's name: `work.Comment CMT-001`, `work.ProjectDirectory work.Projects`. An
  entry's label: its relation's name and its linked objects' labels in its links' order,
  `work.Plans: Demoable index site, No-code index view` (`Views.entryLabel`). A summary, where none is held, is empty.
- **Entry views** ([CAP-005: label and summary view](../capabilities/CAP-005.md) and [CAP-006: chip view](../capabilities/CAP-006.md) of a `References.OfEntry`) are requested as mutation expressions, as any view
  is, and come back in frames' `entries`, with the entry's properties; the client labels them (`Views.entryLabel`).
- **Counted objects** have no reference: a frame that binds one is left out of the stream, and an entry that links one
  out of `entries`.
- A view's transaction may write ([CAP-013: an in-memory store journaled to DynamoDB](../capabilities/CAP-013.md)'s flow): whatever it writes is committed, and journaled, before its frames
  are filled.

### The golden corpus

`conformance/cases.json` lists each case: `name`, `method`, `path`, `request` (a file, or null), `status`,
`content_type` and `response` (a file). Each case is sent to a fresh stub server over the WorkTracker seed
(mbse-demo-apps). `uv run python -m mbse.Services.Rest.Conformance` writes it; `--check` reports what differs.

Beside the hand-written cases, the corpus holds a case for every view mbse-react asks of the seed (`ui-*`), generated
from the store so that the UI can develop against the corpus alone: each app reference object schema's chips
(`ui-chip-<schema>`, [CAP-006: chip view](../capabilities/CAP-006.md)) and entries (`ui-entries-<schema>`, [CAP-007: detail view](../capabilities/CAP-007.md) with `x` given the schema, the relation
browser's), each object's detail (`ui-detail-<key>`, [CAP-007: detail view](../capabilities/CAP-007.md)), and each object's named adjacencies, one case for each
schema whose objects their entries may link (`ui-adjacency-<key>-<adjacency>-<schema>`, [CAP-008: adjacency as a list of chips](../capabilities/CAP-008.md)). They only read, so
they share one server. Each carries `view`, what its request is made of: its `kind`, what each symbol is `given` (a
`schema` by name, or a `reference`, a `References.OfObject` in mbse-schemas' JSON), and, an adjacency view's, its
`adjacency`; the client's tests build each such request again from it, byte for byte.

- The server's tests require the corpus to be current: a change to a response is a change to the corpus, committed
  with it, and reviewed as a change to the contract.
- The client's tests serve the corpus through a fetch of their own: the client must build every request byte for byte
  (in mbse-schemas' JSON) and read every frame back byte for byte. mbse-react can develop against the corpus with
  the same fetch, before a server runs.

### The client

`typescript5/mbse/Services/Rest/Client.ts` (`@mbse/rest/Services/Rest/Client`), over mbse-schemas' TypeScript
implementation. A store (`newStore()`) reads the schemas once, then gives symbols schemas and reads frames back
(`Views`).

```typescript
import { Client, newStore, Views, TransactionRefused } from "@mbse/rest/Services/Rest/Client";

const client = new Client("http://localhost:8000");          // or "", the page's own origin; or { fetch, headers }
const store = newStore();
const names = await client.loadSchemas(store);                // CAP-002: every named schema, now in `store`
const tasks = await client.chip(store, store.registered("work.Task"));
for (const frame of tasks) console.log(Views.label(store, frame), [...Views.chip(store, frame)]);
const abort = new AbortController();
for await (const frame of client.stream(store, "detail", Views.request(store, "detail", { x: ref }),
  { signal: abort.signal })) { /* each frame as it arrives */ }
```

| Member | For |
|---|---|
| `new Client(base = "", options?)` | `base` without its trailing slash; `options` is `{fetch?, headers?}`, or a fetch (as in M0) |
| `loadSchemas(store, {signal}?)` | [CAP-002: named schema list](../capabilities/CAP-002.md): reads the schema snapshot into `store`; gives `schemaNames(store)` |
| `schema(name, {signal}?)` | [CAP-003: schema inspector](../capabilities/CAP-003.md): rejects with `Unimplemented` (501) for now, `NotFound` for an unknown name |
| `templates({signal}?)` | [CAP-004: logical view templates](../capabilities/CAP-004.md): a `Map` of each kind's template |
| `stream(store, kind, transaction, {signal}?)` | [CAP-012: logical view endpoints](../capabilities/CAP-012.md): an async generator of `Views.Frame`, read as the response arrives |
| `view(store, kind, transaction, {signal}?)` | [CAP-012: logical view endpoints](../capabilities/CAP-012.md): every frame, as an array |
| `viewOf(store, kind, given, {adjacency?, signal?})` | `view` of `Views.request(store, kind, given, adjacency)` |
| `label(store, x)`, `chip(store, x)`, `detail(store, x)`, `adjacency(store, x, adjacency, y)` | [CAP-005: label and summary view](../capabilities/CAP-005.md) to [CAP-008: adjacency as a list of chips](../capabilities/CAP-008.md), `x` a schema or a `References.OfObject`, each with `{signal}?` last |
| `url(path)` | the URL a call is sent to |

Errors, each a `RestError` (an `Error`):

| Class | When |
|---|---|
| `ServiceError` | any refusal: `status`, `body`, and `error`, the body's message |
| `TransactionRefused`, `NotFound`, `Unimplemented`, `Unavailable` | `ServiceError`s of 400, 404, 501 and 503 (`ServiceError.of`) |
| `TransportError` | the service out of reach, or the response cut off: `cause` is the platform's error |
| `ResponseError` | a response accepted that is not what the contract gives (not JSON, not NDJSON, a line not a frame) |

An abort is not a `RestError`: the call rejects with the signal's reason, the platform's `AbortError`, so that a UI
tells it apart as it does any fetch's. Aborting, or leaving a `for await` over `stream` early, cancels the response.

## Decided by an agent, for review

Where this capability was silent, the simplest default consistent with it and with mbse-schemas, each *proposed*
until reviewed, labeled with the repository and number it was decided under.

- **(mbse-rest 14)** **The corpus** as in [the golden corpus](#the-golden-corpus),
  one case per file pair, `.json` compared as JSON and `.ndjson` byte for byte.
- **(mbse-rest 23)** **The client's errors** are classes, `RestError` and below, by status where the contract names one;
  an abort rejects with the signal's own reason, unwrapped.
- **(mbse-rest 24)** **The client's conveniences** (`viewOf`, `label`, `chip`, `detail`, `adjacency`) build requests
  with `Views.request`, as before, so they send what the corpus holds byte for byte.
