# FEA-003 · no-code logical views

From the workspace's `VISUALIZATION.md`. Index entries: [features/README.md](README.md#FEA-003), [CAPABILITIES.md](../CAPABILITIES.md). A capability without an ID is not in plan yet.

Logical views define specific query formats
that must be accessible from the backend via a mutation
expression.

Backend interaction is batched by allowing logical views
to be either requested in isolation or sensibly nested
in a single response. Sensibly nested usually involves

- treating a query as graph traversal
- query-specific limited adjacency traversal rules
- query-specific level of detail per visited object/adjacency

Each logical view kind defines which properties, adjacencies and closures
its response includes.

Objects and relation entries are designated by mbse-schemas References:
`References.OfObject` for an object and `References.OfEntry` for a relation
entry. A response is a stream of `References.OfFrame`, whose `assigns`
(`References.OfProperties`) and `entries` (`References.OfEntry`) carry the
view's data.

Only singletons and owned objects have references. Counted objects are
not recorded or transmitted (tech debt, to revisit).

## <a id="CAP-002"></a>CAP-002 · named schema list

Backend has a designated endpoint which returns a list
of every named schema.

While CAP-003 is blocked (mbse-schemas cannot yet write one schema object
as a document), it returns the store's whole schema snapshot instead, from
which the client's store takes every schema.

## <a id="CAP-003"></a>CAP-003 · schema inspector

Given a schema's name, UI can obtain the full
detail for that schema. Definitions for unnamed schemas
must be included in the response. Named schemas
may be included only in referenced form.

## <a id="CAP-004"></a>CAP-004 · logical view templates

Backend has a designated endpoint (no arguments) that for every 
supported logical view, returns a template for that logical view 
as a mutation query beginning with a Mutations.OfMap with
at least one symbol. When the UI uses the template it gives each symbol
(`Schemas.OfSymbol`) in the outermost `Mutations.OfMap` expression exactly
one of a schema or a `References.OfObject`. A symbol given a schema always
has universal interpretation: it ranges over every extant object of that
schema. A symbol given a reference binds the one object it designates.
The UI may also add to the pattern's spec, for example naming the
adjacency a CAP-008 view follows.

Variables in templates are deferred.

## <a id="CAP-012"></a>CAP-012 · logical view endpoints

Backend has one endpoint per logical view kind, each taking a
transaction expression (a template from CAP-004, its symbols given).
Endpoints take no arguments: the mutation expression in the request's
body carries the query's bindings.
Its response is a stream of `References.OfFrame` whose `assigns` and
`entries` the service fills as the view kind defines.

## <a id="CAP-005"></a>CAP-005 · logical view as label, summary

This is a minimum-sized logical view of an object or a relation entry.

Given a `References.OfObject` or `References.OfEntry`, 
UI can obtain a logical view template, the response for which
comprises two strings : 

- `label`: a one-line phrase
- `summary` : a sentence or short paragraph describing the object or relation entry

Each maps to a specific property. For now the sensible default is a naming
convention: `label` is the first of the properties `label`, `name` and
`title` that the object holds, and `summary` the first of `summary` and
`description`.

Where no property matches, `label` falls back to the schema's name and the
object's last path key; for a relation entry, to its relation's name and
the labels of its linked objects. Where no property matches, `summary` is
empty.

## <a id="CAP-006"></a>CAP-006 · logical view as chip

This is a medium-sized logical view of an object or a relation entry.

Given a `References.OfObject` or `References.OfEntry`, 
UI can obtain a logical view template, the response for which
comprises properties and adjacencies
for display in chip previews. The set of properties and 
adjacencies included in the response are intentionally
abbreviated.

For now the sensible default is the `label` and `summary` properties
(CAP-005) and the first three other scalar properties the schema declares,
with no adjacencies.

## <a id="CAP-007"></a>CAP-007 · logical view of object as detail

This is a full-sized logical view of an object.

Given a `References.OfObject`, 
UI can obtain a logical view template, the response for which
comprises properties and adjacencies of an object for display in a detail inspector over the full set of schema-defined properties and 
adjacencies.

## <a id="CAP-008"></a>CAP-008 · logical view of adjacency as list of chips

Given a `References.OfObject` and the name of one of its adjacencies, 
UI can obtain a logical view template, the response for which
comprises a list of immediate adjacencies 
including entry properties, the linked object's `References.OfObject`,
and chip view of the linked object.

The adjacency is named in the template's spec. For example, the people
`ada` knows, `ada` given by reference:

```python
store.transaction(lambda t: t.mutations([lambda mu: mu.map(lambda m: m.symbols([lambda p: p
    .symbols({"x": ada_reference, "y": t.crm.Person})
    .spec([lambda _: _.x.knows([_.y])])]))]))
```

## Not yet planned

### logical view of object as detail with closures

Extends CAP-007: the response also comprises the closures of the object.

### logical view of closure as list of chips

Given a `References.OfObject` or `References.OfEntry`, 
UI can obtain a logical view template, the response for which
comprises a list of transitively adjacent objects each of
which includes the linked object and a chip view of that object.
