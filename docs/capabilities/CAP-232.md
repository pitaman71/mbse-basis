# CAP-232: domains inferred for terms

*Implements* [FEA-024: expressions as data](../features/FEA-024.md). *Relates to* [CAP-097: value domains of published standards](CAP-097.md), [CAP-104: typed values translated beyond C and SystemVerilog](CAP-104.md), [CAP-101: translation between dialects](CAP-101.md).

## Design

Not built. A term carries no domain ([CAP-097: value domains of published standards](CAP-097.md#decided), Decided):
the reference object that owns an expression's root specifies its schema, and since mbse-expressions 0.7.0 Patterns'
evaluation takes values by the schemas they are written with (ints unbounded, floats binary64). This capability is the
type inference that gives each term its domain from that schema and the domains its dialect defines, which since
mbse-expressions 0.9.0 are stored data, every dialect's but LaTeX's ([CAP-097: value domains of published standards](CAP-097.md#value-domains)),
and it builds on them (Decided, "Before domain inference"). With it, it restores what evaluation in domains needs and
0.7.0 retired:

- integer widths and overflow (`wrap`, `saturate`, `raise`);
- IEEE 754 formats other than binary64, with their rounding;
- enums, and packed enums;
- the conversions `convert`, `reinterpret`, `pack` and `unpack`, as operations and writers;
- typed literals in the C and SystemVerilog translators (Basic and Ccpp, Basic and SystemVerilog: `(uint8_t)200`,
  `8'd200`), and so typed values beyond them ([CAP-104: typed values translated beyond C and SystemVerilog](CAP-104.md));
- tutorial 4, the corpus's domain cases and DOM's width cases (DOM-04, DOM-13 to DOM-16).

Overloads (several operations of one name, bound by their arguments' domains) were to be proposed with it ([the port's
proposal](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/README.md#proposed-for-the-users-review), B).

What stays code until this capability, each marked in a source comment as its to replace: `Dialect.infer`'s
signatures (Patterns' `SIGNATURES`, over its natives' domains, `OfTypes`, since its families went in 0.9.0's stage 2),
every dialect's code domains for inference (`OfTypes`: Python3's `Int`, MATLAB's `Double`, LaTeX's `number`, ...), and
the rules over the working values C's and SystemVerilog's evaluators compute on (C's promotions and usual arithmetic
conversions, SystemVerilog's `common`), which read the stored domains for every named type
([CAP-097: value domains of published standards](CAP-097.md#value-domains)). The relation from an operation's argument
domains to its result domain, and how it is populated, are this capability's (Decided, below). The properties each
stored domain holds that follow from its parameters are populated by hand until constraint resolution computes them
([CAP-043: constraints resolved in any direction](CAP-043.md)). Found while building 0.9.0, left for this capability:
C++'s `std::bfloat16_t` and `std::float16_t` are both 16 bits, and the usual arithmetic conversions pick a floating type
by width, so mixing them takes the first operand's type, where C++ refuses it, their conversion ranks unordered. What
evaluation in domains did before
0.7.0, when a literal and an operation named their domain (mbse-expressions 0.5.4 to 0.6), is where this starts, a
term's domain then given by inference in place of a name:

- **Basic has no implied promotions.** An operation takes its arguments' domains as they are: `add` of an
  `Integer(8)` and an `Integer(16)` does not apply until one is converted explicitly. A dialect's translator writes out
  its language's promotions as conversions.
- **A value of another domain than its native's default is a typed value**, its value a native its domain holds; a
  value of a default domain is the bare native, so constraints over natives are unchanged.
- **A literal's value is a native of its domain**: an `int` for an `Integer`, a `float` for a binary `Ieee754` and the
  decimal text for a decimal one, `bytes` for `Bits` (big-endian, in the fewest bytes, the unused leading bits zero)
  and `Bytes`, a `str` for `Unicode`, `Ieee1164` (one of `U X 0 1 Z W L H -`, or as many as its width, the most
  significant first), an `Enum` and a `Packed` enum (a member's name), and a `bool` for `Bool`.
- **Comparisons take two values of one domain**; values of different domains are incomparable (unknown). Every domain
  has `eq` and `ne`; `Integer`, `Ieee754`, `Bytes`, `Unicode` and `Packed` are ordered, `Bool`, `Bits`, `Ieee1164` and
  `Enum` not. `Ieee754` values compare by IEEE 754's `totalOrder`, except that NaNs equal each other and are
  incomparable with numbers; a `Packed` value orders by its code.
- **Arithmetic takes two values of one domain, `Integer` or `Ieee754`, and gives that domain.** An `Integer` result
  outside the domain wraps (into the width, two's complement), saturates or raises `OverflowError`; an `Ieee754`
  result is the exact one rounded to the format with the domain's rounding direction, with IEEE 754's default
  exception handling, and a decimal result keeps IEEE 754's preferred exponent when it is exact.
- **The bitwise operations take `Integer` and `Bits` values of one domain**, on two's complement patterns of the
  width, applying the domain's overflow to a result outside it; `shl` and `shr` take a non-negative count, `shr` on an
  `Integer` arithmetic, on `Bits` logical.
- **An operation's `domain` is the domain of its result**, which `convert`, `reinterpret` and `unpack` need.
- **What converts.** `convert` keeps the value: between `Integer`s (the target's overflow), from an `Integer` to an
  `Ieee754` (the target's rounding), between `Ieee754` formats, from an `Ieee754` to an `Integer` (rounded in the
  source's direction, then the target's overflow; NaN raises), between `Bytes` domains when the value fits, between an
  `Enum` and a `Packed` domain of it, and from any domain to itself. `reinterpret` keeps the bit pattern, big-endian,
  between fixed-width `Integer`s, the binary `Ieee754` formats and `Bits` and `Bytes` of the same number of bits; the
  decimal formats do not reinterpret. `pack` gives a packed value's code in its representation, and `unpack` the
  packed value of a code, raising `ValueError` when no member has it.

## Decided

As the user decided, adopted, quoted as written.

- **No domain inference yet; it is a follow-up capability** (2026-10-30, on [the port's proposal](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/README.md#decided-for-stage-3),
  Stage 3's model, Decided, 2). "For the time being, evaluation will need to do without an
  external source specifying the domain for every term, as that involves building a type inference system which should
  be a follow-up capability."
- **What needs a term's domain is deferred with it**: "(iii) agreed, defer for type inference": widths, overflow,
  IEEE 754 formats other than binary64, enums, `convert`, `reinterpret`, `pack`, `unpack`, and the translators'
  conversions of typed literals; tutorial 4, the corpus's `domains` case and DOM's width cases go until then.
- **Before domain inference** (2026-11-04, on mbse-expressions' proposal, domains as data, its questions 1 and 5): "1,5.
  yes before per your recommendation": domains as data first, as its own release (0.9.0); this capability builds on
  stored domains.
- **Operations' result domains are this capability's** (2026-11-04, the proposal's question 2). Asked what "code
  intrinsics" meant (the first draft's word, for a rule implemented as a function registered by the operation's name,
  which "inferred properties are still properties" rules out; [CAP-097: value domains of published standards](CAP-097.md#decided)),
  then shown that the question is the relation from an operation's argument domains to its result domain: "I wasn't
  expecting that to become an issue until CAP-232." Proposed and agreed ("yes"): domains as data stores each dialect's
  domains, their parameters and hand-populated properties, and each operation's argument and result schemas; the
  relation from argument domains to result domain, and how it is populated, are domain inference's. Until then
  `Dialect.infer`'s signatures stay as they are, marked as this capability's to replace, and evaluation's arithmetic
  (C's usual arithmetic conversions applied to the values it computes) is the evaluator's, as before.

## Decided by an agent, for review

Recorded in mbse-expressions' design, not marked as the user's: each *proposed* until reviewed. Moved from
[CAP-097: value domains of published standards](CAP-097.md), as what this capability restores.

- Value domains: conversions are `convert` (keeps the value) and `reinterpret` (keeps the bit pattern), with `pack` and
  `unpack` for packed domains.
- Evaluation in value domains: a value of a non-default domain is a typed value (`Domains.Value`), and a default
  domain's value stays the bare native; an operation's optional `domain` is the domain of its result, which `convert`,
  `reinterpret` and `unpack` need and `pack` does not; every IEEE 754 format is evaluated, `binary128` and the decimal
  formats as canonical text.
