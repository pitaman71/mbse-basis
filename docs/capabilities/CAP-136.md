# CAP-136: one finisher for every build

*Implements* [FEA-029: excluding imperative visitor expressions](../features/FEA-029.md). Index entry: [capabilities/README.md](README.md#CAP-136).

## Design

Not designed, planned or built. The problem is [FEA-029: excluding imperative visitor expressions](../features/FEA-029.md#design)'s: today a builder's caller finishes it with one of three methods, `create`, `update` or `clone`, so that an object's identity is a function of context.

### What `done()` resolves

Any caller calls `done()` without knowing whether the object is located, upserted, updated or cloned, and `done()`
resolves its identity from the schema: a singleton by its global name, an owned object by its path in its owner, a
keyed object by upsert, a counted object always new. Opened on an object, it updates it, or, where the spec changes
what identifies it, makes a new one, a clone. The analysis of every call of `create`, `update` and `clone`, and the
review of how a builder reports its changes to its parent, are [FEA-029: excluding imperative visitor expressions](../features/FEA-029.md#design)'s list; forbidding read-modify-write
in specs is [CAP-143: specs declarative, no read-modify-write](CAP-143.md).

It is coordinated with [CAP-126: schema objects read through the store protocol](CAP-126.md), so that schema building is not rewritten twice, and with
[CAP-173: spec items written through ordinary builders over a mutation sink](CAP-173.md), whose sink is the writer a spec callback would be given.

## Open questions

- **Ambiguities the schema cannot resolve**, found so far:
  - rename or clone: an identity the spec changes may mean the same object renamed, or a new one like it;
  - counted objects: nothing in the schema identifies one, so a clone of one cannot be inferred;
  - locate or upsert: where nothing matches, make one or refuse (the executor tells `exists` from `all`).
- **A link finding an existing object by path.** `Visitors.OfEntry.<link>(cb)` writes a new object today; whether a
  link should also find one by a path (the [store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md), Open, 4) depends on `done()`, under which the
  schema decides whether to find or make.
- **Concurrent builders (F4).** Two builders over the same object each hold a copy; the last `update()` wins and drops
  entries the other added. Is that the intended semantics of `update()`?
- **Cloning self-loops (F5).** `clone()` copies entries with the clone in place of the source, so a self-loop's clone
  links back to the original rather than to itself. Intended?

Both are pinned by tests (PRX-12, PRX-13) and bear on what a single `done()` does in place of `update` and `clone`.
