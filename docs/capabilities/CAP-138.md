# CAP-138: mutation expressions over frame streams

*Implements* [FEA-027: mutations as queries](../features/FEA-027.md). Index entry: [capabilities/README.md](README.md#CAP-138).

## As built: mbse-schemas

Met in mbse-schemas 0.22.0: the [store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md)'s 4e, the mutation vocabulary and an in-memory, sequential executor, released as 0.22.0. The expressions it refuses are [CAP-142: expressions evaluated in queries](CAP-142.md)'s.

### Frame streams

In the course of streaming query execution, mutator kinds consume and produce streams of frames. Mutation expressions comprise nested terms with operations that modify the frame stream between consumption and production. A query evaluator recursively evaluates each term, passing computed frame stream to each successive term. 

With `Schemas.OfPattern` the schema level declares the shape of a pattern and the instance level is used as frames (matches, effectively) for the pattern. In a frame:
- for each variable, assigns a value of the corresponding schema (as an instance of `Schemas.OfVariable`)
- for each symbol, binds a reference object that exists or is "putative" (as an instance of `Schemas.OfSymbol`) 

The frame stream is a stream of formatted frames (as instances of `Schemas.OfPattern`) each of which associates one or more named "symbols" with reference objects (which may or may not already exist) and zero or more named "variables" bearing schema-governed values.

The frame stream's shape, as defined by the symbols and variables that should be present, will have a shape that may be passed on from its parent during evaluation or may have symbols and variables added or removed.

Various kinds of terms in the mutation kind vocabulary can:

- directly address existing symbols
- pass symbols along
- add or remove symbols with upsert semantics
- route entries according to pattern conditions
- programmatically map or reduce frames in the stream
- add or remove variables

### Mutation structure

A mutation nests, roughly, as:

```
Mutations.OfTransaction [ -> Mutations.OfShard ] -> Mutations.OfTerm -> Mutations.OfPattern -> Mutations.OfObject -> Mutations.OfAdjacency -> Mutations.OfProperty
```

- `Mutations.OfTransaction` is the root: its uid and its one chain of terms, any term first (Object identity, Decided, 85).
- `Mutations.OfShard` is strictly optional: the query executor's division of the work, which it allocates; never in what
  a program submits nor in what a journal records (Object identity, Decided, 53 in [CAP-144: transactions sharded and run in parallel](CAP-144.md#decided), 56 in [CAP-129: journals replayed by execution](CAP-129.md#decided)).
- `Mutations.OfTerm`: one term of the chain (`OfMap`, `OfReduce`, `OfPartition`, `OfUpdate`, `OfUpsert`). Each
  term has just one pattern; `Mutations.OfPartition` forks the chain where paths must diverge.
- `Mutations.OfPattern`: the pattern's symbols, each the address of the mutations under it: a symbol names the object,
  located once in the pattern, so no verb carries a `ref` of its own.
- `Mutations.OfObject`: the mutations of the object one symbol binds.
- `Mutations.OfAdjacency`: that object's adjacencies, their entries inserted, removed or edited, each entry's links and
  properties through `Mutations.OfEntry` (`AsLink`, `AsProperty`). Entries change only through an adjacency: the
  relation-level verbs, `Mutations.OfRelation.*` on a relation's whole extent, go for now.
- `Mutations.OfProperty`: the value verbs (`Set`, `Clear`, `AsAny`, ...), nesting into value objects, unions,
  intersections and containers as they do today.

The verbs are what a program's builders write: a mutation builder is given whenever a property is called with a
callback, `<object_path>.<propName>(cb)` or `<rel_entry_path>.<propName>(cb)` ([FEA-026: deterministic object identity](../features/FEA-026.md),
Decided, 58).

### Mutation Expressions

Mutations are expressed as nested expressions, where each term expresses a streaming query using predicate logic. 

Every mutation expression term: 

- has a `then` clause containing at most one nested subterm
- has other clauses that direct evaluation of the mutation expression, its effects on the frame stream, and on transactional commits to persistent store (as variant-specific uses of `Schemas.OfPattern`).

In a nested mutation expression term, if symbol 'S' is already present in the consumed frame stream (e.g. defined by any of its ancestors), it is considered a reference to that inherited symbol, not a rebinding of the symbol to some other object.

A "query executor" evaluates these expressions over streams of frames. 

The query executor:
- recursively executes the mutation expression term's subterm
- for each mutation expression term, produces a stream of frames that it passes to the term's subterm
- consumes a stream of frames from its parent at each recursive call
- may filter the frame stream
- may upsert objects into the frame stream
- may update objects

The vocabulary of `Mutations.OfX.Y` tracks the vocabulary of Schema kinds: that is there exists a `Mutations.OfX.Y` for every schema kind X and every modification verb Y. `Mutations.OfX.Y` are serializable via meta schema.

The mutation vocabulary uses `Schemas.OfPattern` across its quantifier term vocabulary.

A transaction's frame stream starts as one frame, empty, the cross product of no extents, and its terms may be nested in any order: there is no root-only term (Object identity, Decided, 85, superseding `Mutations.OfAll`). A term refers only to symbols that a term before it binds, which validation checks. A symbol a pattern binds to existing objects may be of any kind of reference object (84): it ranges over the extant objects of its schema, a singleton's binding the singleton (77 in [CAP-137: patterns of symbols, variables and specs](CAP-137.md#decided)), and the frames are their cross product, filtered by the pattern's spec and constraints.

Normally the symbols and variables injected by every ancestor term in a mutation expression (`OfMap`, `OfReduce`, `OfUpsert`'s `exists`) are accumulated during recursive evaluation and passed through to descendants. There are three mutation kinds which route and/or multiplex the frame stream: `Mutations.OfPartition`, `Mutations.OfMap`, and `Mutations.OfReduce`

### Map

`Mutations.OfMap` programmatically expands each frame in the consumed frame stream into zero or more frames in the produced frame stream. 

```python
# associate case : add one symbol to every frame in stream
# symbol binds to an existing object(s) via visitor spec expression
# for any frame in the consumed stream, if the pattern's constraint cannot be satisfied for that frame, no frames are produced from that frame
# if association is not unique, complexity multiplies
#
# pred.requires : describes object to find and associate
# pred.spec : may give property values and links to other symbols
Mutations.OfMap.as_symbols(pred: Schemas.OfPattern).then(Mutations.OfTerm)
```

### Reduce

```python
...Schemas.OfCollector(lambda co: co
    .pattern(Schemas.OfPattern)
    .symbols([name: str...])
    .variables([name: str...])
    .commutative() # optional; a collector declaring neither is rejected for now by validation
    .associative() # optional
    .suffixes({ current: str, next: str })
    .computes(Schemas.OfExpression)
)

# drop-symbol case : drop one symbol from every frame in the consumed stream
# this may create apparent duplicates, keep only unique frames
# pred: has neither `suffixes` nor `computes` clause
Mutations.OfReduce.as_symbols(pred: Schemas.OfCollector).then(Mutations.OfTerm)

# drop-variable case : drop one variable, collate by all unique frames left
# this may create apparent duplicates, keep only unique frames
# pred: has neither `suffixes` nor `computes` clause
Mutations.OfReduce.as_variables(pred: Schemas.OfCollector).then(Mutations.OfTerm)
```

### Partition

`Mutations.OfPartition` routes the frame stream. Each branch represents a conditional arm. `first` and `last` specify that at most one arm with matching condition should be recursively executed. If `first` and `last` are both called it is a validation error. If neither are called every branch with matching condition is recursively executed. If no branch has a matching condition and the `none` clause is present, that one is recursively executed.

`Mutations.OfBranch` pairs a condition constraint with a mutation sub-clause.

```python
Mutations.OfPartition.first() # dispatch to first matching branch
Mutations.OfPartition.last() # dispatch to last matching branch
Mutations.OfPartition.branches([Mutations.OfBranch])
Mutations.OfPartition.none(Mutations.OfTerm)

Mutations.OfBranch.requires([constraints: Schemas.OfConstraint])
Mutations.OfBranch.then(Mutations.OfTerm)
```

### Update

`Mutations.OfUpdate` is used to update properties and adjacencies for symbols already in the frame stream: first in a transaction, it binds none, which validation refuses. 

```python
Mutations.OfUpdate # update
Mutations.OfUpdate.apply(pred: Schemas.OfPattern)
Mutations.OfUpdate.then(Mutations.OfTerm)
```

- `Mutations.OfTerm` a schema-governed union of every term, a transaction's root term and every `then` one of them: `Mutations.OfMap`, `Mutations.OfReduce`, `Mutations.OfPartition`, `Mutations.OfUpdate`, `Mutations.OfUpsert` (85)

### Mutations: the vocabulary

A pattern's spec (object identity 95 in [CAP-137: patterns of symbols, variables and specs](CAP-137.md#decided)), a `Mutations.OfPattern`, gives for each symbol the mutations
of the object it binds, *object verbs*:

```python
Mutations.OfObject.{AsProperty, AsAdjacency, Spec}
Mutations.OfAdjacency.{Insert, Remove, Clear}
```

`Mutations.OfObject.Spec`, `{"spec": {"items": [...]}}`, is a pattern's own spec, written as recorded: a list of
`Mutations.OfPattern`, whose payloads are bare. Where a pattern is a symbol or a definition, it gives the spec the
pattern holds, in place of any it held before; its shape is checked when it is read, and what it says when the pattern
is executed.

`Mutations.OfAdjacency.Remove` removes each entry that agrees with an entry it gives, every link and property given
equal to the entry's, and `Mutations.OfAdjacency.Clear` every entry an adjacency holds; a spec holds where what it
removes is absent (Store overhaul, 4j, as built). `Mutations.OfAdjacency.{Insert, Remove}` carry a list of
`Mutations.OfEntry`, each leaving out the link the object
fills, which carries `Mutations.OfProperty.*` and `Mutations.OfLink.*`, through `Mutations.OfEntry.{AsProperty, AsLink}`:

```python
Mutations.OfEntry.{AsProperty, AsLink}
Mutations.OfLink.{Set, Clear}
```

`Mutations.OfObject.AsProperty` and `Mutations.OfEntry.AsProperty` carry a list of *Value verbs*:

```python
Mutations.OfProperty.{Set, Clear, AsAny}
Mutations.OfContainer.{Insert, Remove, Append, Prepend, Clear, AsItems}
Mutations.OfAny.{Set, Clear, AsScalar, AsContainer, AsObject, AsUnion, AsIntersection}
Mutations.OfScalar.{Set, Clear}
Mutations.OfUnion.AsBranch
Mutations.OfIntersection.AsPart
```

- `Mutations.OfAny.AsObject` carries a list of `Mutations.OfObject.AsProperty`: the nested value verbs follow the
  property that holds the value object.
- `Mutations.OfUnion.AsBranch` and `Mutations.OfIntersection.AsPart` name a branch or a part and carry a list of
  `Mutations.OfProperty.*`, as a property does; writing a branch clears the others (`Visitors.OfUnion`).
- `Mutations.OfContainer.AsItems` carries a list of `Mutations.OfAny.*` applied in modulo order: with three mutations in
  the list, item 0 gets the first, item 1 the second, item 2 the third, item 3 the first, and so on. The list of items in the list is not required to utilize the entire list of mutations

Value verbs appear only nested in an object's or an entry's property.

A change can be written in more than one form (`OfProperty.Set`, or `OfProperty.AsAny` then `OfAny.Set`, ...); a reader accepts every form. Which the writer chooses is [CAP-169: mutations written in their smallest form](CAP-169.md).

`Mutations.OfX.AsY` has a list of `Mutations.OfY.*` 

The log's own verbs, `Mutations.OfObject.Exists` (a reentrant create, a noop where the identity exists), a relation's
`Insert`, `Remove`, `Clear` and `AsEntries`, `Mutations.Log` and `Mutations.Reference`, are gone (Store overhaul, 4f):
what they wrote, an upsert's spec writes, and an upsert finds what exists.

Nouns are used by verbs and appear nested in a verb:

```python
Mutations.OfContainer.Slice # a section of a container
Mutations.OfObject.Ref # identity only: an object's path (a schema object's from the root module, "."), or, in a spec, the symbol that binds it (object identity 81 in [CAP-123: schema objects identified by path](CAP-123.md#decided), 95 in [CAP-137: patterns of symbols, variables and specs](CAP-137.md#decided))
Mutations.OfObject.Def # an object with no path, defined where it is linked: its schema's name (a schema object's kind's, `Schemas.OfObject`) and its own mutations
```

- scalar payloads are untyped and interpreted according to their schema
- reference objects are symbols of a transaction's patterns, never nested as value objects are; a link refers to one by
  its symbol or its path
- an object is written once, in the spec of the symbol that binds it; elsewhere it is referred to

## Open questions

### Fork and join

The 'fork' form above, which lacks `expect` and `then` clauses on `Mutations.OfPartition`, recursively executes every conditionally activated branch as executing in parallel. The end of the mutation expression term tree is treated as a terminal where frames are disposed. Alternatively, 
`Mutations.OfPartition` can represent a fork-join pair where the final frame stream across all executed paths are joined and then passed to a follow-up mutation clause. The `none` `expect` `then` clauses must be provided.

Mutations.OfPartition.expect(Schemas.OfPredicate) # optional join schema
Mutations.OfBranch.then(Mutations.OfTerm)

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(object identity 58)** As the user decided (2026-10-19): `Visitors.OfMutation`: "Mutation visitors (builders) appear when a property visitor is called with a callback
  expecting it": "mutation builders are currently passed to the callback whenever <object_path>.<propName>(cb) or
  <rel_entry_path>.<propName>(cb) are invoked". The mutation verbs therefore stay ("why would you think mutations go
  away?").
- **(object identity 59)** A mutation's structure, "roughly": "Mutations.OfTransaction [ -> Mutations.OfShard ] -> Mutations.OfTerm ->
  Mutations.OfPattern -> Mutations.OfObject -> Mutations.OfAdjacency -> Mutations.OfProperty"
  ([FEA-027: mutations as queries](../features/FEA-027.md), Mutation structure). An adjacency's entries go through
  `Mutations.OfEntry` to their links and properties ("yes"); the shard is "strictly optional", the executor's (56 in [CAP-129: journals replayed by execution](CAP-129.md#decided)); a
  term has "just one" pattern, "one can use Mutations.OfPartition to fork paths if needs be"; `Mutations.OfAll` is
  the first term of a transaction's one chain. "Keep adjacency verbs, lose relation verbs for now": entries change
  only through an object's adjacency.
- **(object identity 84)** As the user decided (2026-10-20), correcting STREAMING_QUERIES.md, which required a singleton's symbol in `over`: "OfAll does not need a singleton! Its symbols may refer to any kind of reference object": each symbol of an
  `OfAll`'s pattern ranges over the extant objects of its schema, and a singleton's binds the singleton (77 in [CAP-137: patterns of symbols, variables and specs](CAP-137.md#decided)).
  (`OfAll` then went: 85.)
- **(object identity 85)** As the user decided (2026-10-20), "I'm sorta thinking Mutations.OfAll goes away and mutations can be nested in any order", on the three points that follow from it ("yes"): `Mutations.OfAll` goes: its role is `OfMap.as_symbols`, which binds symbols to existing objects, each ranging over
  its schema's extant objects (84), filtered by the pattern's spec and constraints, and which may come anywhere. A
  transaction starts from one frame, empty, the cross product of no extents. Any term may come first and follow any
  other: `Mutations.OfTerm` is the union of every term, a transaction's root term and every `then` one of them. That
  a term refers only to symbols some term before it binds (an `OfUpdate` first, binding none, is refused) is checked
  by validation, not by the schemas. This amends 59 ("`Mutations.OfAll` is the first term of a transaction's one
  chain") and STREAMING_QUERIES.md's rules on what may come at the root.
- **(object identity 91)** As the user decided (2026-10-20): Terms are selected as a union's branches ("yes"): a transaction's `mutations` and a term's `then` take the
  peer-shorthand list, each entry callback given the `Mutations.OfTerm` union, whose branch called selects the term:
  `.mutations([lambda mu: mu.upsert(lambda u: u.exists([...]).then([lambda w: w.update(...)]))])`. Their relations hold
  one entry each. The terms' members: `map` (`as_symbols`, `as_variables`, `then`), `reduce` (`as_symbols`,
  `as_variables`, `then`), `partition` (`first`, `last`, `branches`, `none`), `update` (`apply`, `then`) and `upsert`
  (`key`, `exists`, `then`).
- **(object identity 92)** Fixtures ("yes"): a test builds the data a case needs in one transaction, one pattern's symbols and one spec, with
  the mappings for keyed adjacencies ([CAP-107: one visitor protocol reads and writes data](CAP-107.md#decided)), rather than a transaction per object.
- **(object identity 93)** As the user decided (2026-10-20), on how 4e-1 builds them: "expression terms of any kind, including mutation expressions, should be reference objects": a transaction and its
  terms are reference objects of the Mutations schemas, linked by relations (`mutations` from a transaction to its root
  term, `then` from a term to the next, `exists`, `apply`, `as_symbols` and `as_variables` from a term to its pattern);
  the value verbs (`Set`, `AsAny`, ...) stay value objects. (79 made expression terms so.)
- **(object identity 94)** Where they live ("agreed"): a transaction's terms are counted objects of the store, reachable from no singleton, so
  that no snapshot writes them and they go when the program drops them; building a transaction's expression is the one
  write allowed outside a transaction, the expression not being the store's data; and the store holds a schema object
  with no name of its own weakly, so that a term's pattern goes with its transaction.
- **(mutations as queries, Resolved)** We cannot abandon mutation verbs as they are already essential for creating or modifying value objects. `Exists` as a top level mutation type goes away.

  It's possible mutation verbs are no longer needed in the specific case of counted reference objects, because we can now name every object that needs to be created or updated with a symbol. However, I am concerned about syntax bloat, particularly in cases such as nested expression terms.
