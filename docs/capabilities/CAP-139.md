# CAP-139: upserts find before they create

*Implements* [FEA-027: mutations as queries](../features/FEA-027.md). Index entry: [capabilities/README.md](README.md#CAP-139).

## As built: mbse-schemas

Met in mbse-schemas 0.22.0: the [store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md)'s 4e and 4f-1 (a counted object found only by what made it), released as 0.22.0.

### A counted object an upsert creates

A counted object an upsert creates in a mutation expression has an identity, though: the frame that reached the upsert,
an instance of the upsert's pattern, the upsert's `key`, and the symbol it is created for, which tells apart the objects
one upsert creates from one frame (61, 63). Running the expression again yields the same frame and key, so the upsert finds the object rather than
creating another. The query executor finds such an object by them, through an index it holds weakly, so that it keeps
no counted object alive; a program still cannot (40 in [CAP-118: singletons, owned and counted objects](CAP-118.md#decided)). On the wire the frame is written as any instance of its pattern
is, each symbol a reference and each variable its value, so a reference to such an object is
`{"$ref": {"frame": <frame>, "key": <key>, "symbol": <symbol>}}`, recursively where the frame binds another.

### Upserts

`Mutations.OfUpsert` is used to upsert frames each of which contains zero or more new objects; first in a transaction, it upserts from the one empty frame. Any symbol declared in `exists` which is not present in the frame stream is considered a reference that must be upserted. If the pattern's spec finds the object, that object will be bound, otherwise a new object is created and bound, and the spec written.

```python
Mutations.OfUpsert # upsert
Mutations.OfUpsert.key(key: str) # optional: tells apart the counted objects one upsert creates from one frame
Mutations.OfUpsert.exists(Schemas.OfPattern)
Mutations.OfUpsert.then(Mutations.OfTerm)
```

An owned object an upsert finds or creates is placed by its spec's owning entry, which gives its whole path: owner,
owning adjacency and the ownership entry's keys; its path is its identity, and `key` takes no part. A counted object an upsert
creates is identified by the frame that reached the upsert, its `key` and the symbol it is created for, so that running
the expression again finds it rather than creating another (Object identity, Decided, 60, 61 and
63).

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(object identity 54)** A putative counted object that a `Mutations.OfUpsert` names "becomes a creation of the transaction, named by its
  symbol" ("10. yes"). An upsert's `key` clause, which labelled the identities of the objects it created, was tried
  and dropped: "I am just removing 'key', not worth the trouble".
- **(object identity 60)** As the user decided (2026-10-19), on what names an object an upsert creates, the order frames arrive in mattering only to sequential numbering: An owned object an upsert finds or creates is placed by its symbol's locator, which gives its whole path, the owning
  entry's keys included: "For owned objects, Upsert key is unnecessary and does not participate". No key is generated
  from a pattern in an upsert, so nothing is numbered in the order frames arrive.
- **(object identity 61)** "For unowned reference objects, the frame and key should be sufficient to disambiguate": a counted object an upsert
  creates is identified by the frame that reached the upsert and the upsert's `key`, with no nesting path, symbol
  name, sequence number or transaction id. "instances of Schemas.OfPattern are frames", so a frame is written as any
  instance is. This narrows 55: a counted object a verb creates still has no identity beyond a document.
- **(object identity 63)** "upserted counted objects also include the symbol": a counted object an upsert creates is identified by the frame,
  the upsert's `key` and the symbol it is created for (amending 61), so that one upsert may create several from one
  frame.
- **(object identity 102)** A counted object an upsert names is found "Only by what made it": the frame, the upsert's key and the symbol it
  was created for (61, 63), never by its spec. A document's upsert is keyed by its uid, so reading one gives new
  counted objects (55 in [CAP-118: singletons, owned and counted objects](CAP-118.md#decided)), and replaying the same transaction while they are held finds them again. This changes 4e,
  which found one by its spec where nothing had made it. (Offered against keeping the spec match, with a term that
  always creates for documents.)
