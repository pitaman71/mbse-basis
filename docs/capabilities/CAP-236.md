# CAP-236: `has` translated to C

*Implements* [FEA-024: expressions as data](../features/FEA-024.md). Index entry: [capabilities/README.md](README.md#CAP-236). *Relates to* [CAP-229: the C expression dialect](CAP-229.md), [CAP-235: `has` translated to C++](CAP-235.md), [FEA-022: code generation](../features/README.md#FEA-022).

## Design

Not built. Today the C and C++ translator refuses `has`, naming the term (mbse-expressions' tutorial 8, "What has no
counterpart"): "a C struct always has its members, so there's nothing in C to translate it to". The user decided
(2026-11-03) that this is a planned gap, "filled by a CAP for C++ and a CAP for C".

C has no notion of an absent member, so what `has(x, name)` becomes depends on how an optional property is written in
C: a presence flag beside the member (`x.has_name`), a presence bitmask, or a pointer member null when absent
(`x.name != NULL`). The translation follows whichever code generation for C picks.

## Blocked

On code generation for C choosing how an optional property is represented ([FEA-022: code generation](../features/README.md#FEA-022)).

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **A planned gap, filled by a capability each for C++ and C** (2026-11-03): "planned gap filled by a CAP for C++ and a
  CAP for C".
