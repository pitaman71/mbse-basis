# CAP-176: a transaction's changes held in builders and mutation frames until journaled

*Implements* [FEA-006: persistence](../features/FEA-006.md). Index entry: [capabilities/README.md](README.md#CAP-176). *Relates to* [CAP-013: an in-memory store journaled to DynamoDB](CAP-013.md).

## As built: mbse-rest

Not met. A transaction that writes commits before it is journaled, since transactions on one store do not nest. Where
it is then refused (a frame lacks a symbol of its view's kind) or its journal fails, the service undoes it by reading
the whole store back from the persistence plugin ([CAP-013: an in-memory store journaled to DynamoDB](CAP-013.md)). That is correct, but costly for a large
store.

## Design

Nothing commits before the journal accepts it: a transaction's changes are retained entirely in builders and mutation
frames while the service journals it, and commit only once the plugin has journaled it. A transaction refused, or
whose journal fails, drops what it holds, so that nothing is undone and no store is read back. It needs mbse-schemas
to give a transaction's changes, held so, to the service that commits them.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **Nothing commits before it is journaled.** The user's preferred alternative to holding a transaction open while
  the service journals it, or rolling one back: "retain the changes entirely in builders and mutation frames".
