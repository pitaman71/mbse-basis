# CAP-176: a transaction's changes held in builders and mutation frames until committed

*Implements* [FEA-006: persistence](../features/FEA-006.md). *Relates to* [CAP-290: a service's store stacked, with no snapshot](CAP-290.md).

## As built: mbse-rest

Not met in mbse-rest's main, where a transaction that writes commits in memory before it is journaled, and one then
refused, or whose journal fails, is undone by reading the whole store back from what it persisted: correct, but costly
for a large store. Under [CAP-290: a service's store stacked, with no snapshot](CAP-290.md), the service's store sends a
transaction's changes to the store below before it commits, within it, and commits only where the store below accepts
them ([CAP-285: writes through, others' writes in](README.md#CAP-285)), so that one refused or failed below leaves
nothing written.

## Design

A transaction's changes are retained entirely in builders and mutation frames until it commits. A transaction
refused, or one whose persistence fails, drops what it holds, so that nothing is undone and no store is read back. Not
every persistence stack journals; where one does, as a store kept in a database does below mbse-rest's service, the
transaction commits only once the journal accepts it. It needs mbse-schemas
to give a transaction's changes, held so, to the service that commits them.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **Changes are held until the transaction commits.** The user's preferred alternative to holding a transaction open
  while the service journals it, or rolling one back: "retain the changes entirely in builders and mutation frames",
  "until committed. You should not assume from the existence of mbse-journals that all persistence stacks are
  journaled."
