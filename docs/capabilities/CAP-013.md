# CAP-013: an in-memory store journaled to DynamoDB

*Implements* [FEA-006: persistence](../features/FEA-006.md). Index entry:
[capabilities/README.md](README.md#CAP-013).

The service loads the store into memory at startup and executes
transactions over it. Each committed transaction is persisted to DynamoDB
as a journal entry, with occasional snapshots; startup reads the latest
snapshot and replays the journal after it.

- UI proposes a mutation query using a mutation template ([CAP-004: logical view templates](CAP-004.md))
- `mbse-rest/typescript5/mbse/Services/Rest/Client.ts` translates the mutation query into well-formed REST call(s)
- REST request is sent and received
- `mbse-rest/python3/mbse/Services/Rest/Service.py` unpacks the REST payload into mutation expression form
- mbse-schemas' executor runs the mutation expression over the in-memory store
- for a transaction that writes, `mbse-dynamodb/python3/mbse/Persistence/DynamoDB/Plugin.py` journals it to DynamoDB when it commits
- `Service.py` fills each frame's `assigns` and `entries` as the view kind defines ([CAP-012: logical view endpoints](CAP-012.md); decided by the agent, for review), serializes the frame stream and returns it as response data
- `Client.ts` reads the frame stream back for the UI

## As built

### The persistence plugin

`Persistence.Plugin`, a Python protocol whose every argument and result is mbse-schemas' plain form, so that a plugin
never holds a proxy:

```python
class Plugin(Protocol):
    def load(self) -> tuple[list[PlainData] | None, list[PlainData]]: ...  # latest snapshot, journal after it
    def journal(self, transaction: PlainData) -> None: ...  # a committed transaction that writes, its expression
    def snapshot(self, snapshot: list[PlainData]) -> None: ...  # Plain.ToPlain(store).Snapshot(), two transactions
```

- **Startup.** `Persistence.replay(store, plugin)` reads the snapshot (`Plain.FromPlain(store).Snapshot`), then
  executes each journaled transaction in order. Where the plugin holds nothing, the service runs the app's installs
  (`Schemas.install`, then `Seed.seed`) and gives the plugin a snapshot of what they wrote: the database is
  initialized by schema.
- **Journal.** A transaction is journaled after it commits, in commit order, when its expression has an `upsert` or an
  `update` term; a refused transaction writes nothing and is never journaled.
- **Snapshots.** Every `snapshot_every` journaled transactions (100 by default); after one, `load` gives only what
  is journaled after it.
- `Persistence.Memory` is the reference implementation. `mbse.Persistence.DynamoDB` (mbse-dynamodb) implements the
  same protocol. Every plugin must pass `PersistenceCases.CASES`, each a function given a maker of a fresh plugin,
  which checks the service's use of it through the protocol alone (`load`, and a `Counting` wrapper for how often it
  journals and snapshots), never a plugin's own attributes; mbse-rest runs them with `Memory`
  (`python3/tests/test_service.py`), mbse-dynamodb with its own plugin.

- **What the plugin has not journaled is undone.** Transactions on one store do not nest, so a transaction that
  writes commits in memory before the service can journal it or check its frames. Where it is then refused (a frame
  lacks a symbol) or its journal fails, the service reads the store back from the plugin (`Service.restore`): the
  snapshot, then the journal, as at startup. The store then holds exactly what the plugin holds.
- **A snapshot that fails** is logged and tried again after the next journaled transaction; the journal still holds
  every transaction, so nothing is lost and the request is answered as usual.
- **A plugin that fails at startup** (`load`, or the first snapshot) fails the start: `app()` raises.

### The DynamoDB plugin: its table

One table, with on-demand capacity, holds any number of stores.

| Attribute | Key | Holds |
|---|---|---|
| `store` (S) | partition | the store's name, `store` by default |
| `key` (S) | sort | `J#<number>#<part>` for the journal, `S#<number>#<part>` for snapshots; numbers zero-padded (20 and 6 digits), so that keys sort as numbers |
| `data` (B) | | one part of the record: its plain form as compact UTF-8 JSON, at most `part_bytes` (350 000) bytes |
| `parts` (N) | | on part 0 only: how many parts the record has |
| `since` (N) | | on a snapshot's part 0 only: the journal's length when it was taken |

- **Two append-only logs.** The journal numbers each committed transaction that writes, from 0, in the order `journal`
  is called (commit order, as the contract requires); snapshots are numbered in the order taken. A partition's keys
  sort the journal in commit order, so `load` is two strongly consistent `Query`s: the latest snapshot (read
  backwards, keys only, to find the highest number with a part 0, then its parts), and the journal from its `since`
  on. Neither ever scans.
- **Parts, for the 400 KB item limit.** A record of any size is cut into parts of `part_bytes`; a WorkTracker
  snapshot of the seed is about 80 KB (one part), and the tests write records of hundreds of parts.
- **A record is there exactly when its part 0 is.** Parts 1 and on are written first, part 0 last, with the condition
  `attribute_not_exists(key)`. A write that fails partway leaves parts without a part 0, which `load` passes over and
  the next record of that number writes over (parts beyond the count its part 0 gives are passed over too). So a
  failed write leaves nothing `load` reads, without a transaction, which DynamoDB bounds at 100 items and 4 MB.
- **One writer.** `load` sets the numbers to write next; a second service writing the same store since then finds
  part 0 taken, and its write is refused (`RuntimeError`) rather than interleaved.
- **The plain form is kept as JSON, not as DynamoDB maps.** The plugin is storage only (mbse-rest 12, in this capability): it
  never interprets mbse-schemas' plain form, and JSON keeps every value as mbse-schemas wrote it (DynamoDB's own
  number type would lose the difference between `1` and `1.0`, which mbse-schemas keeps strictly).

### Configuration

`Plugin()`, with no arguments, takes every setting from the environment, so that a service can make it by name; an
argument given overrides the environment (tests give them all).

| Variable | Argument | Default |
|---|---|---|
| `MBSE_DYNAMODB_TABLE` | `table` | `mbse-store` |
| `MBSE_DYNAMODB_STORE` | `store` (the partition key) | `store` |
| `MBSE_DYNAMODB_REGION` | `region` | boto3's own: `AWS_REGION`, `AWS_DEFAULT_REGION`, its config |
| `MBSE_DYNAMODB_ENDPOINT_URL` | `endpoint_url` | AWS's; `http://localhost:8000` for DynamoDB Local |
| `MBSE_DYNAMODB_CREATE` | `create` | `1`: make the table if absent (on-demand capacity), and wait until it is active; `0`, `false` or `no` not to |

Credentials are boto3's own (`AWS_ACCESS_KEY_ID`, `AWS_PROFILE`, ...). `client=` takes a boto3 client in place of
one the plugin makes, and `part_bytes=` (350 000) bounds each part. `Plugin.from_environment(environ, **options)` reads
a mapping given in place of the process's environment.

### How mbse-rest's service selects it

mbse-rest's service selects a plugin with
`MBSE_REST_PLUGIN=module:attribute`, calling the attribute with no arguments (`Service.plugin_of`). For this plugin:

```sh
MBSE_REST_PLUGIN=mbse.Persistence.DynamoDB.Plugin:Plugin
```

`mbse.Persistence.DynamoDB:Plugin`, the package's attribute, is the module `Plugin.py`, not the class, and is not
callable: the module path above names the class. `tests/test_plugin.py` makes the plugin by that name, as the service
would. Beyond that, the plugin needs nothing from the service: its settings are its own (`MBSE_DYNAMODB_*`, the AWS
environment). Since a snapshot writes the whole store, `MBSE_REST_SNAPSHOT_EVERY` (100 by default) sets how many journaled
transactions come between snapshots.

## Blocked

Reported, not worked around (mbse-rest's `AGENTS.md`): a gap in mbse-schemas.

**An install cannot be built as an expression without running it.** `store.transaction(install)` gives `install`
the store's schemas by name (`txn.Schemas`, `txn.work`) through a private wrapper; `store.Mutations.OfTransaction(
install)` does not (`TypeError: no member of the entry takes <empty>`). So installs are not journaled: the service
snapshots after them instead.

## Decided by an agent, for review

Where this capability was silent, the simplest default consistent with it and with mbse-schemas, each *proposed*
until reviewed, labeled with the repository and number it was decided under.

- **(mbse-rest 12)** **The plugin gives data, the service replays it** (`load` returns the snapshot and the journal), so
  that a plugin is storage only; first start runs the installs, then snapshots, since an install cannot be journaled ([Blocked](#blocked)); a snapshot every 100 journaled transactions.
- **(mbse-rest 21)** **Undo by replay**: what the plugin has not journaled is undone by reading the store back from it,
  since transactions do not nest and so cannot be held open while journaling. Where that fails, the service answers 503
  until it restarts, rather than serve a store that disagrees with its plugin.
- **(mbse-rest 22)** **503 for a journal that fails** (the transaction undone, safe to send again), 500 for the
  service's own faults; a snapshot that fails does not fail the request.
- **(mbse-dynamodb 1)** **One table, keyed by store and record**, rather than a table each for the journal and
  snapshots: one thing to make and configure, and several stores (demos, tests) may share it.
- **(mbse-dynamodb 2)** **Nothing is deleted.** A snapshot does not remove the journal before it or older snapshots: the
  history stays whole, a snapshot that fails partway falls back to the one before (with the journal from its `since`),
  and no write the plugin makes is destructive. Pruning, or a DynamoDB TTL on records older than the latest snapshot, is
  left for later.
- **(mbse-dynamodb 3)** **Parts of 350 000 bytes** of UTF-8 JSON, uncompressed, so that a record reads back as text in
  the console; compression (zlib) would cut cost and parts roughly tenfold, and can be added under a part 0 attribute.
- **(mbse-dynamodb 4)** **No `TransactWriteItems`**: atomicity comes from writing part 0 last, conditionally, so a
  record has no limit of 100 items or 4 MB.
- **(mbse-dynamodb 5)** **Strongly consistent reads** for `load` and the numbers, so that a restart sees every write
  made before it.
- **(mbse-dynamodb 6)** **A second writer is refused**, not merged: mbse-rest 13 ([CAP-012: logical view
  endpoints](../capabilities/CAP-012.md)) has one service, one lock, one store.
- **(mbse-dynamodb 7)** **The table is made when absent by default** (`create=True`, on-demand capacity), for demos;
  production sets `MBSE_DYNAMODB_CREATE=0` and makes the table with its own tooling.
- **(mbse-dynamodb 10)** **Settings from `MBSE_DYNAMODB_*`**, read by `Plugin()` with no arguments (as mbse-rest's
  `MBSE_REST_PLUGIN` calls it), each overridden by an argument; the region falls back to boto3's own.
