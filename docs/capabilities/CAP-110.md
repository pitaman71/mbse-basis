# CAP-110: a store's schemas read as one module

*Implements* [FEA-032: schema loading and wire alignment](../features/FEA-032.md). Index entry: [capabilities/README.md](README.md#CAP-110).

## As built: mbse-schemas

Met in mbse-schemas 0.26.4, though not by `root_module()`: it is met by schema objects' paths and references, as checked in the code of both languages and in the References suite at 0.26.4.
- **The root module** is a reference object in the store, the singleton `"."`.
- **Each module and schema** is a reference object identified by its path from that root module, through each module and then the schema by name ([CAP-123: schema objects identified by path](CAP-123.md#decided), object identity 80 and 81).
- **A schema's name is its path**, qualified with dots (`crm.Person`).
- **`References.of(store, schema)`** gives its path, and `References.resolve(store, reference)` gives back the schema object, or nothing where the store holds none ([CAP-130: references to objects, entries and frames](CAP-130.md)).

- **Modules are read as linked objects.** `store.module()` gives the root module, and `store.module("crm")` or `store.module("crm.sales")` a nested one. Each is a `Schemas.OfModule` whose adjacency `schemas` lists its schemas and nested modules through `Schemas.Defines`. The snapshot suite checks that the root module's name is None and that its `schemas` are its top-level modules and schemas, and that a snapshot writes the modules.
- **Lookup by name uses the flat registry, not the modules.** It goes through the store's registry, keyed by full dotted name (`registered`, `schema`, `name_of`, `names`), rather than walking the modules' `Defines` entries.

`Schemas.OfStore.root_module()` itself was never built, and nothing needs it now.

## Design

As mbse-schemas' framework design had it, `Schemas.OfStore.root_module()` "will return the hierarchical `Schemas.OfModule` of the schemas a store registers, by module-qualified name, as linked objects", replacing `Reflection`, removed with the old protocol ([CAP-109: schemas as linked objects in modules](CAP-109.md), Phase 5 design, point 6).

### Phase 5 of the meta-schemas overhaul

5. **Meta-schemas as linked objects**: links built with a schema given as itself (`.<link>.of(schema, spec)`);
`Schemas.OfAny.Schema` removed, a type given as itself (`Visitors.OfAny`, `Schemas.OfAny.Builder` and `Data` kept,
and `OfAny` added as a kind, a value of any type: [CAP-157: values of any schema, restricted or not](CAP-157.md#decided), "`OfAny` returns"); every schema a
reference object of its kind's meta-schema, every reference to one a link through a meta-relation, the ends at which
a schema is referred to anonymous adjacencies (built here, for any relation, as [CAP-109: schemas as linked objects in modules](CAP-109.md) records);
`OfModule` and `Defines`, nestable, names qualified with dots; `Schemas.OfStore.root_module()`, the root module,
registering schemas by module-qualified name, in place of `Reflection`; modules written as snapshots;
`Schemas.Module`, `Modules.reference` and `resolve`, and `Stores.META` removed.

## Open questions

- **Resolving qualified names.** A name qualified with dots names a schema through nested modules; whether an
  unqualified name resolves outward through the enclosing modules before the store, or only within its own module, is
  to be settled in phase 5. Name resolution stays closed either way: a name resolves or is refused.
  As built, and by construction rather than by the user's decision, a name is always the full dotted path from the
  root module: `.name("Loose")` is in the root module, and `.name("crm.sales.Order")` is in `crm.sales`. The registry
  resolves only that exact full name, and nothing resolves an unqualified name outward or relative to a module.
