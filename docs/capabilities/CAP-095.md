# CAP-095: Basic terms as data

*Implements* [FEA-024: expressions as data](../features/FEA-024.md). Index entry: [capabilities/README.md](README.md#CAP-095).

## As built: mbse-expressions

### Terms and the core vocabulary

An expression is an `Expressions.Framework.Expression`, a reference object whose `root` is a term, a value of
`Expressions.Framework.Term` held nested (see [The framework](../../../mbse-expressions/docs/EXPRESSIONS.md#the-framework), and the port's
[API](../../../mbse-expressions/docs/proposals/port/API.md)). Basic's terms are the framework's kinds and one of its own, each a branch of `Term`:

- `literal` : a basic scalar (`value`), and the name of its value `domain` when it is not the scalar's default
- `call` : a named operation (`callable`) applied to ordered `arguments`, over an open vocabulary of string names, and
  its result's `domain`
- `variable` : the value bound to a `name`
- `let` : binds a `name` to the value of one term (`value`) within another (`body`); nest lets for several names
- `quantifier` (Basic's, added to `Term` by `Basic.install`) : binds a `name` to each item of a `collection` within a
  `body`: `all`, `any` or `count` of the items for which the body holds

Every binding must implement a core vocabulary of operations. The core vocabulary is chosen so that any core expression
can also be interpreted as a constraint (e.g. by a solver or as a SystemVerilog constraint): operations are pure,
deterministic, and total, with no side effects or unbounded iteration.

| Group | Operations (arguments) |
|---|---|
| Access | `get(object, name)`: a property's value, unknown if absent; `has(object, name)`: whether it is present |
| Comparison | `eq`, `ne`, `lt`, `le`, `gt`, `ge` (2) |
| Boolean | `and`, `or`, `implies` (2), `not` (1) |
| Arithmetic | `add`, `sub`, `mul` (2), `neg` (1) |
| Bitwise | `bitand`, `bitor`, `bitxor` (2), `bitnot` (1); `shl`, `shr` (a value and a count) |
| Conversion | `convert`, `reinterpret`, `unpack` (1, with the operation's `domain`); `pack` (1) |
| Collections | `count(xs)`, `item(xs, i)`, `in(x, xs)`, `sum`, `min`, `max`, `unique` (1, but `item` and `in` 2); `entries(object, adjacency)` (2); the quantifiers `all`, `any`, `count` (`OfQuantifier`) |

Constraints that every binding must evaluate use only the core vocabulary. Operation names outside it are extensions
that a binding may or may not support. A union value is a record of its one branch, by name, so a constraint tests which
branch it holds with `has`, e.g. `has(get(this, 'reach'), 'email')`.

### Validation, storage and writers

`Expressions.DIALECT.validate(term, bound=(), core=False)` reports statically what evaluation would raise: missing
names and values, properties of the wrong scalar, wrong numbers of arguments to
core operations, variables not bound by an enclosing let or in `bound`, and, with `core`, operations outside the core
vocabulary. A term is a nested value, so it holds no cycle.

Terms are stored, serialized, validated and compared as any value of their schemas: `Framework.install` and
`Basic.install` define them in a store (each a module-scope `install(txn)`, run once each, in that order), a term is
built there in a transaction through the builders, and written nested, its kind the name of the branch it holds:
`{"call": {"callable": "not", "arguments": [{"literal": {"value": true}}]}}`. A literal's `value` is an `OfAny` of the
five basic scalars (Bool, Int, Float, Str, Bytes), which refuses any other value as it is written: bare where exactly
one of them writes that form (`1`, `1.5`, `true`, `-0.0`), otherwise wrapped, kind then schema
(`{"scalar": {"str": "x"}}`, `{"scalar": {"bytes": "AQ=="}}`, `{"scalar": {"float": "NaN"}}`), and read back without
guessing (mbse-schemas 0.26.3). A domain is named.

`Writer`s write terms through the builders, with methods, and evaluate nothing. `.name` reads a property (`get`), and
methods build the operations: `.eq(x)` ... `.ge(x)`, `.and_(x)`, `.or_(x)`, `.not_()`, `.implies(x)`, `.add(x)`,
`.sub(x)`, `.mul(x)`, `.neg()`, `.has(name)`, `.get(name)`. `variable(name)`, `literal(value, domain)`, `let_(name,
value, body)` and `operation(name, *arguments, domain=None)` start writers. A writer is a spec, written wherever a term
is, in a transaction (kept until mbse-codegen-python moves off them: Resolved, "Porting to the stabilized
mbse-schemas"):

```python
this = Expressions.variable('this')
with store.transaction():
    adult = store.Expressions.Framework.Expression(lambda e: e.root(this.age.ge(18).and_(this.has('email'))))
Evaluators.OfAny(adult, {'this': ann})   # True, False, or None when age is absent
```

In Python, `Python.Text.FromFunction(function)` reads the same expression from a function's source (a lambda, or a `def`
whose body is one `return`); each parameter becomes a variable. `.name` and `getattr` are `get`, `hasattr` is `has`,
`x.name is None` / `is not None` test presence, comparisons (including chains), `and` / `or` / `not`, `+` / `-` / `*`
and unary `-` map to the core operations, and `(lambda name: body)(value)` is a let. Collections are read in the forms
the Basic-to-Python translator writes, so that its text reads back: `len(xs)`, `xs[i]`, `x in xs` (and `not in`),
`sum(xs)`, `min(xs)` and `max(xs)` are `count`, `item`, `in`, `sum`, `min` and `max`; `all(body for x in xs)` and
`any(...)` are the quantifiers, an `if` restricting the items (`implies` in `all`, `and` in `any`), and `sum(1 for x in
xs if condition)` is `count`. The builtins are read only under their own names; `unique` has no Python spelling. Other names are read from the
function's closure and globals when `FromFunction` runs. The result follows the expression's rules, not Python's: `1 ==
1.0` is unknown. TypeScript has no counterpart, since a JavaScript function has no Python source to read.

```python
adult = Python.Text.FromFunction(lambda this: this.age >= 18 and this.email is not None)   # a writer (stage 2b)
```

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **Expressions are built and read only through mbse-schemas** (2026-10-14, from the `overhauls/meta-schemas` branch),
  applying mbse-basis P-018 ("No model should need code to read or write. Ever."). Reading or writing an expression
  through code that knows each kind's shape "violates P-018 and must be fixed", and `Writer`s and the builders' `set`,
  `argument` and `arguments` "should go away. You don't write bespoke builders or data classes either. You use
  mbse-schema proxies or generated classes as sourced in Visitor form." Writers stay until the dependents move off them
  (above, the port's decision 10).
- **Terms implement the visitor protocol and are value objects** (2026-10-14, from the `overhauls/meta-schemas`
  branch), as the user decided, "2 = Y": an expression tree is a value; a term is a value object, which holds its
  arguments in a container, in order, and is written nested in what holds it, with no identity, so the relation
  `Arguments` and every kind's `used_by` go; a term refers to a definition by name, as a module names a schema, since
  nothing links a value object. Its "1 = A", term classes of mbse-expressions' own implementing the protocol, is
  superseded by the decision above. Confirmed by the port (above, "Terms are value objects").

## Decided by an agent, for review

Recorded in mbse-expressions' design, not marked as the user's: each *proposed* until reviewed.

- (Superseded by "Porting to the stabilized mbse-schemas" and "Expressions are built and read only through
  mbse-schemas", above; mbse-schemas' `Bindings` is gone.) Expressions are a program's own classes bound to their
  meta-schemas with mbse-schemas' `Bindings`, not builders of
  their own: what is generic to any schema (visitor protocols over a state, finalizing, the store, value objects in
  properties) lives once, in mbse-schemas, and `Terms` gives only `read`, `make` and the DSL.
- (Superseded where arguments are a relation and terms reference objects: "Terms implement the visitor protocol and
  are value objects", above.) Expressions are `Expressions.OfAny`, `OfLiteral`, `OfOperation`, `OfVariable` and
  `OfLet`, each with `Data`,
  `Builder`, `Spec` and a meta-schema `Schema` that is an ordinary registered object schema tagged by `kind`. Arguments
  are an ordered relation (`index`, `unique(argument)`); a literal's schema has one property per native type.
- There is no `is` operation: unions discriminate by a tag property compared with a fixed value.
- `Python.Text.FromFunction` (Python only) reads an expression from a function's source with `ast`.
