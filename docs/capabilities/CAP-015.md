# CAP-015: transaction provenance

*Implements* [FEA-007: property kinds](../features/FEA-007.md). Index entry:
[capabilities/README.md](README.md#CAP-015).

Services retain a record of each transaction that writes, as mbse-schemas'
`Provenance` module defines it ([CAP-134: transactions recorded with provenance](CAP-134.md)): a `Provenance.OfTransaction` keyed by the transaction's
uid, with its `when` and `where`; its `Provenance.OfSession`, with the
session's locale, device and identity (`Provenance.Who`,
`Provenance.OfIdentity`); and `Provenance.CreatedBy` and
`Provenance.ModifiedBy` (the latest write only) linking the objects of
the schemas an app chooses.

- the service validates the user's token and writes the session's id and
  identity, and the transaction's `when`, into the mutation before
  executing and journaling it; the token itself is never recorded
- the UI provides the session's locale and device, and the transaction's
  geolocation where given, in the mutation
- the detail view ([CAP-007: detail view](CAP-007.md)) of an object whose schema has provenance also
  carries it: its `CreatedBy` and `ModifiedBy` entries, each transaction
  record, its session and the session's identity, in the frame's
  `assigns` and `entries`, so the UI fetches provenance with the object's
  detail and needs no request of its own

## As built

### Provenance

An app with a history lists its installs in `Schemas.INSTALLS` (`installs_of`): its schemas, `Provenance.install`
(mbse-schemas 0.26.0), and an install calling `Provenance.extend` for the schemas whose objects have a history; the
WorkTracker's are its comments.

- **The service stamps every transaction that writes** before executing and journaling it (`Service.stamp`): a `uid`
  where it has none, so that a replay finds the same record; `when`, from its clock, as UTC ISO 8601 text; and the
  session's `id` and `who`, the session the request names in the `x-mbse-session` header (else `<who>:default`) and
  the service's identity (`MBSE_REST_USER`, `demo` by default), keeping the client's `locale`, `device` and `where`.
  Its startup installs are given `when` from its clock too. The journal holds what was stamped.
- **The detail and adjacency views carry provenance**: for `x`'s detail, and for each `y` of an adjacency view, the
  records of the transactions that created it and last wrote it, each one's session and the session's identity
  (`assigns`), and the entries linking them, `Provenance.CreatedBy`, `ModifiedBy`, `InSession` and `Who`
  (`entries`). An identity has no properties: its name is its directory key, the last key of its reference's path.
- **The client** names its session with the `session` option (`new Client(base, { session: { id, locale, device }
  })`): its `id` goes in the `x-mbse-session` header of every call, and its `locale` and `device` into every edit and
  proposal (`Views.edit`, `Views.propose`). `Views.provenance(store, frame, reference)` reads an object's provenance
  from a frame: `created` and `modified`, each its `when`, `who`, and the session's `locale` and `device`.
- **The corpus** stamps reproducibly: a fixed clock and uids by count (`corpus-1`, ...).

## Decided by an agent, for review

Where this capability was silent, the simplest default consistent with it and with mbse-schemas, each *proposed*
until reviewed, labeled with the repository and number it was decided under.

- **(mbse-rest 28)** **The service stamps writes on what it receives**,
  the expression's plain form, so that the journal holds the stamped transaction; the session's id comes from a header
  while there is no token ([CAP-177: sessions and identities from a validated token](CAP-177.md)).
- **(mbse-react 30)** **The tab's session**: an id made once per browser
  tab and kept for its life (`sessionStorage`), the browser's locale (`navigator.language`) and a kind of device
  (`touch` or `desktop`, by its pointer), given to a live service's client, which names the session in a header and
  writes the locale and device into each write. Against the corpus no session is sent, so that requests stay the
  corpus's.
