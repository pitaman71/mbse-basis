# CAP-018: adjacency inspector

*Implements* [FEA-005: inspector views](../features/FEA-005.md). Index entry:
[capabilities/README.md](README.md#CAP-018).

Inspector view of an adjacency which permits viewing and modification
of property values across the entry and an "outbound" object that may
be extant or proposed.

The adjacency inspector view is anchored at:

- a relation schema
- designation of an "inbound" link name and an "outbound" link name
- identity of an object on the "inbound" side which must be extant
- optional identity of an object on the "outbound" side which may be proposed 

- "+" on every adjacency list opens it with a proposed outbound object of
  the schema that fills the relation's other link (the user picks one
  where several do); saving commits the new object and its entry in one
  transaction
- its editor shows the entry's and the outbound object's properties: text
  as markdown ([CAP-014: properties as markdown](CAP-014.md)), booleans as checkboxes ([CAP-022: booleans as checkboxes](CAP-022.md))

## As built

### Proposals

A proposal makes a new object through an existing one's adjacency: an `upsert` whose symbols are `x`, the inbound
object's `References.OfObject`, and `n`, given the new object's schema, and whose spec writes `x`'s entry in the
adjacency linking `n` through the relation's other link (with the entry's properties, where given) and `n`'s
properties, posted to `POST /views/detail`. The service commits and journals it; an owned object is placed in its
directory, its key given there (CMT-004 for the WorkTracker's next comment); the response is `x`'s detail with the new
entry.

- **The client**: `Views.propose(store, x, adjacency, link, schema, values, entry)` builds it, and
  `client.propose(...)` sends it.
- **The corpus**: `propose-thread` (a comment about a feature) and `propose-reply` (a reply resolving a thread).
- Editing an existing entry's properties with its linked object's, the rest of this capability, is not built yet.

## Decided by an agent, for review

Where this capability was silent, the simplest default consistent with it and with mbse-schemas, each *proposed*
until reviewed, labeled with the repository and number it was decided under.

- **(mbse-rest 27)** **A proposal is an `upsert` posted to the detail view**, its symbols `x` and `n`, as an edit is an `update` there (mbse-rest 26): the response is the
  inbound object's detail with the new entry.
- **(mbse-react 25)** **"+" on an adjacency** wherever its relation has
  exactly one other link and it is not the object's ownership adjacency (proposing a new directory means nothing); where
  several schemas fill the other link, the proposer offers a choice. Every named adjacency is shown as a list, empty or
  not, so that "+" can add the first.
- **(mbse-react 26)** **The proposer** shows a field for each editable property (text, boolean) of the new object's
  schema and of the relation's entries; only what the user filled is sent (`Service.propose`, mbse-rest's
  `client.propose`).
- **(mbse-react 27)** **After a save**, an edit's or a proposal's, the inspector's detail and every list are read again,
  since the service's views have changed (every view kept is dropped).
- **(mbse-react 29)** **Editing an existing entry's properties with its linked object's** (the rest of this capability) is not built yet.
