# CAP-301: simplification delegated to a surrogate dialect

*Implements* [FEA-024: expressions as data](../features/FEA-024.md). *Applies* [PRI-046: simplification, not evaluation](../PRINCIPLES.md#PRI-046). *Relates to* [CAP-203: evaluators delegating to per-language libraries](CAP-203.md), [CAP-180: ISO/IEC 11404 datatypes replace the Basic expression dialect](CAP-180.md), [CAP-295: simplification of single-dialect expressions with literal leaves](CAP-295.md), [CAP-305: simplification's options, chosen up front](CAP-305.md).

## Design

The user wrote this design on 2026-11-15, under the title "Simplifier: 'Built In' operations". It covers the second
of the two surrogates that this capability names, a language's own runtime:

> A dialect may define a simplifier as a utility class (or in the future as a proper MBSE transform).
>
> Expressions may contain references to free symbols, including the particular case where a symbol may be imported in
> some "enclosing context".
>
> The simplifier may be configured to bind such symbols by name (or path) to "native representation". For example,
> Typescript5 programs may make use of the built-in method `String.prototype.toUpperCase`. `String` can be registered
> as a "native representation", the built-in `String` class. This allows the simplifier - in the specific case where
> the arguments have been determined (each simplified to a literal) - to call the built-in function via the built-in
> class, compute the result, and simplify the whole term as the result wrapped as literal.

Since mbse-expressions 0.11.0, the TypeScript5 simplifier recognizes ECMAScript's built-in methods by name, through
the `ECMAScript` module's table of them. The simplifier leaves an expression that uses one of those methods in the
residual, and it gives that expression class (c), because the expression waits on this capability
([CAP-295: simplification of single-dialect expressions with literal leaves](CAP-295.md)). Under this design, the
caller registers a native representation in the scope, and the simplifier calls the registered native wherever the
expression's arguments have all folded to literals. When the caller registers nothing, the simplifier leaves the
expression in the residual, as it does now. Other dialects already let the scope provide what an expression calls:
Python3's scope allowlists modules, C++'s scope provides user-defined literal operators, and SystemVerilog's scope
provides `Subroutine`s. The registration of natives can therefore become one rule of the framework, which binds a name
or a path in the scope to a native implementation.

## Decided

- The user decided on 2026-11-15: "cross-language simplification is optional or deferred for CAP-301". The two
  implementations therefore need not simplify a call to a registered native alike. For example, the TypeScript
  implementation may register JavaScript's own `String` class, and the Python implementation need not model
  `String`'s methods. Any difference that results is a deliberate difference between the implementations
  ([PRI-040: deliberate differences listed](../PRINCIPLES.md#PRI-040)) until a later decision requires the two
  implementations to agree.

## Open questions

- **Purity.** A native such as `Date.now` or `Math.random` would make a simplification nondeterministic, which
  [PRI-013: nondeterminism passed in](../PRINCIPLES.md#PRI-013) forbids unless the caller passes the nondeterminism in.
  The framework could admit only pure natives, or it could make purity the caller's responsibility.
- **A result with no literal.** A native can return a value that has no literal, as `"a,b".split(",")` returns an
  array. The existing rule would apply: the simplifier writes the value as a display where the dialect has one, and
  otherwise leaves the subterm in the residual.
- **An error that a native raises.** The design must state whether the error raises, as the language would raise it,
  or whether the subterm stays in the residual. That choice could become one of the options that
  [CAP-305: simplification's options, chosen up front](CAP-305.md) proposes.
