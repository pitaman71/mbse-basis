# CAP-127: snapshots made of transactions

*Implements* [FEA-026: identity and transactions](../features/FEA-026.md). Index entry: [capabilities/README.md](README.md#CAP-127).

## As built: mbse-schemas

Met in mbse-schemas 0.22.0: the [store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md)'s 4f and 4f-4, a store's snapshot written as two transactions, released as 0.22.0.

### An identity read from a snapshot

Reading a snapshot or a journal is the one way an object is given an identity it did not get by being built: the same
path appearing again is an update of the owned object or singleton that has it, through its builder, where update is
allowed. A counted object read from a document is always a new one (55 in [CAP-118: singletons, owned and counted objects](CAP-118.md#decided)).

### Snapshots

Snapshots are made of transactions (45): reading one replays them. The counted objects a snapshot holds are numbered
within it (55 in [CAP-118: singletons, owned and counted objects](CAP-118.md#decided)), and later transactions reach them through what links them.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(object identity 45)** "snapshots are made of transactions".
- **(object identity 101)** As the user decided (2026-10-21), on step 4f's proposal (Store overhaul, 4f), each the option recommended: A store's snapshot is two transactions, "Schemas, then data": the first upserts its modules and schemas, the
  second its data, so that a schema the store held before is extended when the first commits (96 in [CAP-124: writes all-or-nothing in transactions](CAP-124.md#decided)), before the data
  uses it. (Offered against one transaction, in which data could not use such an extension, and against one per
  module.)
