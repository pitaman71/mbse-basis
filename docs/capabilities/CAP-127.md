# CAP-127: snapshots made of transactions

*Implements* [FEA-030: transactions](../features/FEA-030.md). Index entry: [capabilities/README.md](README.md#CAP-127).

## As built: mbse-schemas

Met in mbse-schemas 0.22.0: the [store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md)'s 4f and 4f-4, a store's snapshot written as two transactions, released as 0.22.0.

### An identity read from a snapshot

Reading a snapshot or a journal is the one way an object is given an identity it did not get by being built: the same
path appearing again is an update of the owned object or singleton that has it, through its builder, where update is
allowed. A counted object read from a document is always a new one (55 in [CAP-118: singletons, owned and counted objects](CAP-118.md#decided)).

### Snapshots

Snapshots are made of transactions (45): reading one replays them. The counted objects a snapshot holds are numbered
within it (55 in [CAP-118: singletons, owned and counted objects](CAP-118.md#decided)), and later transactions reach them through what links them.

### Snapshots, in order

A store's snapshot, `Plain.ToPlain(store).Snapshot()`, is two transactions (object identity 45 and 101, Decided, below; Store overhaul, 4f-4), each one upsert, written as a transaction on the wire is:

- **its modules and schemas**: the root module, then what each module holds, in the order it holds it, a module's
  contents following it, each a symbol of its meta-schema found where the store reading it holds it: a module by its
  path, the root module by none (its name cleared), a schema by its name (86); so that reading it makes them in the
  order each module held them. A schema no module holds follows them; so that a schema it held before is
  extended when the transaction commits (96); a schema object with no name of its own defined where it is linked
  (`{"def": ...}`); a schema the store was made holding is a symbol only where it holds an extension's entries linking
  schema objects, and then only its name and those entries are written;
- **its data**: each singleton, then what the singletons reach, in the order met, each a symbol: a singleton's binds the
  singleton, an owned object's is placed by its owner's entry (60), a counted object's is created; data that schema
  objects' extension entries link is reached from them, those schema objects symbols too, for those entries alone. Data
  nothing reaches is not written.

Each symbol's spec gives its properties, then its named adjacencies' entries, each entry once, from the first symbol
that holds it, then, a pattern's, its own spec (`spec`), so that a pattern is carried whole; an object neither transaction holds, a schema the store was made holding, is referred to by its path.
`Plain.FromPlain(store).Snapshot(snapshot)` executes them in order, each a transaction of its own, or a savepoint of the
one open, and gives the data the last binds, which the caller holds. Read again, a snapshot finds its schemas and its
singletons and owned objects, and makes its counted objects anew.

## Open questions

- **Snapshot determinism.** must two serializations of the same state produce identical output? Entries are now written
  with links and properties in the relation's declared order, and an adjacency's entries sorted by its key where the
  key is of ordered values, and objects keep their identities, but objects are written in first-reference order, and
  other adjacencies' entry order depends on history, so a round trip can reorder entries, and with them the objects
  (PLN-08; the `FamilyTree` and `University` examples compare snapshots up to that order). Full determinism would need
  a canonical order for entries keyed by links, or not keyed at all. (Possibly stale in part: the test plan's F6, a round trip reordering entries, is "Resolved in 4f-3: a document writes each entry once".)

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(object identity 45)** "snapshots are made of transactions".
- **(object identity 101)** As the user decided (2026-10-21), on step 4f's proposal (Store overhaul, 4f), each the option recommended: A store's snapshot is two transactions, "Schemas, then data": the first upserts its modules and schemas, the
  second its data, so that a schema the store held before is extended when the first commits (96 in [CAP-124: writes all-or-nothing in transactions](CAP-124.md#decided)), before the data
  uses it. (Offered against one transaction, in which data could not use such an extension, and against one per
  module.)

- **(framework design)** On update, loading a path the store already holds updates that object through its builder: what the snapshot holds is written, and what it omits is kept, as the user decided in "Reference identity", on update ([CAP-118: singletons, owned and counted objects](CAP-118.md#decided)): "merging should naturally fall out of the builder pattern". Framework schemas are never written, only referred to, and any other schema the store does not hold is a fatal error: the initial snapshot, 6 ([CAP-109: schemas as linked objects in modules](CAP-109.md#decided)).
