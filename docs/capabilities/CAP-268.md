# CAP-268: standards as tagged data

*Implements* [FEA-024: expressions as data](../features/FEA-024.md). *Relates to* [CAP-226: complete expression dialects](CAP-226.md), [CAP-085: standards record availability](CAP-085.md), [PRI-012: model published standards](../PRINCIPLES.md#PRI-012).

## As built: mbse-expressions

Built in mbse-expressions' domains as data, stage 4 (PR #31), in both languages, and released in 0.9.0; the choices
made where the decisions were silent are [the port's API, Settled in domains as data's stage 4](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-domains-as-datas-stage-4-for-the-users-review),
items 154 to 161, which hold the detail this section only bridges. Until then each dialect named its standards in code
(`STANDARDS`, and each kind's `standards`), which nothing but the tests read.

- **The model**, added by the framework's install: `Expressions.Framework.Standard`, a reference object, one edition of
  a standard, owned by the dialect that covers it; its properties, each optional, are its formal reference's parts,
  `bodies` (the standards bodies by reverse-domain name, one or a joint pair: `org.iso` and `ch.iec`), `number`
  (`9899`) and `revision` (a value of `Expressions.Framework.Revision`, the union of `year`, `edition` and `version`),
  and `names`, its common names (`C11`). `Expressions.Framework.Covers(dialect, standard)`, its property
  `designation`, unique `[dialect, designation]` and `[standard]`, owns each edition by its designation as its body
  writes it, as `Defines` owns a domain by its name, so an edition's path is its dialect's and its designation
  (`store.Instances.Expressions.C.Expressions.standards({"designation": "ISO/IEC 9899:2011"})`).
  `Expressions.Framework.HasStandard(kind, standard)`, a set, links an edition to each kind's schema it has, read from
  the schema through `Schemas.OfObject`'s extension adjacency `standards`. Every dialect's schema has the adjacency
  `standards`, beside `domains` and `operations` (API 154).
- **The reading interface**, `Framework.Standards`: `standards(dialect)`, `designation_of(standard)`, `tags(standard)`
  (its designation, then its common names), `find(dialect, tag)`, which takes either kind of reference (`find(C,
  "C11")` and `find(C, "ISO/IEC 9899:2011")` give the same edition), `properties(standard)`, `kinds(standard)` and
  `of(dialect, kind)` (API 155).
- **What each dialect covers**, written by its `define`, with each edition's kinds where the dialect has terms (API
  156): ISO/IEC 11404:2007, IEEE Std 754-2019, IEEE Std 1164-1993 and The Unicode Standard; the AMD64 psABI and
  AAPCS64; C's ISO/IEC 9899:2011, 2018 and 2024 (`C11`, `C17`, `C23`; `constant`, for `nullptr`, C23's alone); C++'s
  ISO/IEC 14882:2017, 2020 and 2024 (`C++17`, `C++20`, `C++23`; four kinds C++20's and C++23's alone); Python 3.0 to
  3.15, each with the kinds of the version it arrived in; and TypeScript 5.0 to 5.9. An extension and invalid syntax
  are in no edition. SystemVerilog, Patterns, MATLAB, Excel and LaTeX cover none, their code naming none (API 159).
- **What went**: every module's `STANDARDS`, `Terms.Kind`'s `standards`, and C's, C++'s, Python3's and TypeScript5's
  tables of standards by kind, each now the table its `define` writes from (API 158). A breaking change, in 0.9.0.
- **Tests**: FRM-13, new, in both languages; DOM-17 and DOM-19 read each standard and ABI dialect's edition from the
  store; the corpus's dialect cases hold their `Covers` entries, and its `standards` case writes C23's edition as one
  document, byte-identical in both languages (API 160, 161).

## Open questions

- **Whether Excel's formulas are recorded as ISO/IEC 29500-1's** (Office Open XML's formula grammar), and MATLAB's,
  Patterns' and LaTeX's as any standard: left for the user, since no code names one.

## Decided

As the user decided: adopted, each the rule as stated, quoted as given.

- **Standards as tags** (2026-11-05, on the complete dialects' stage 6 design, its Q10, [the dialects proposal's
  Decided](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/dialects/README.md#decided-for-stage-6-systemverilog-and-after-2026-11-05),
  where it is recorded in full): "label standards using the convention the standards body itself uses"; then "If we
  treat standards as tags, we could support both", and, to a standard reference that is either formal (a body by
  reverse-domain name, one or a joint pair; a number; a revision that is a year, an edition or a version) or common (a
  name such as `C11`), each edition stored with its designation and its common names as tags: "yes". Built with
  domains as data.
- **Standards as tagged data, a stage of its own** (2026-11-09, on mbse-expressions' domains as data, stage 1's
  review): "yes", after stage 3, every dialect's `STANDARDS` and `Kind.standards` among it, before the records and the
  release.

## Decided by an agent, for review

Recorded in [the port's API, Settled in domains as data's stage 4](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-domains-as-datas-stage-4-for-the-users-review),
items 154 to 161, not marked as the user's: each *proposed* until reviewed. Each builds the user's "Standards as
tags", above, and [CAP-226: complete expression dialects](CAP-226.md#decided)'s "each kind recording as data the
standards that have it".

- **(mbse-expressions 31, domains as data, API 154)** **The model**: an edition is an `Expressions.Framework.Standard`
  its dialect owns by its designation, through `Covers`, as `Defines` owns a domain by its name; it holds its formal
  reference's parts and its common names apart, by property, so that a reference by body, number and revision needs
  no parsing of the designation. Each kind's schema records the editions that have it through `HasStandard`, a set,
  read through `Schemas.OfObject`'s extension adjacency `standards`, as `Schemas.OfAny` reads its `domain`.
- **(mbse-expressions 31, domains as data, API 155)** **The reading interface**, `Framework.Standards`, as above. Found
  while building: a kind's schema is a schema object, not a `Readers.OfObject`, so `of` takes the dialect and reads its
  editions' `kinds`, rather than the kind's own `standards`, which FRM-13 reads directly.
- **(mbse-expressions 31, domains as data, API 156)** **What each edition holds**: the bodies' own designations and
  common names (WG14's `C11`, `C17`, `C23`; WG21's `C++17`, `C++20`, `C++23`; Arm's `AAPCS64`), the Python Software
  Foundation's and Microsoft's release names (`Python 3.12`, `TypeScript 5.0`), and a body's reverse-domain name its
  web domain reversed (`org.iso`, `ch.iec`, `org.ieee`); a number, a revision or a body only where the designation or
  the code names one, so none for Unicode's or the psABIs' revisions, AAPCS64's document number, or the x86-64
  psABI's body, which names only its editors. Each define writes its editions' kinds from the table its kinds'
  `standards` came from, read through its transaction from its dialect's union.
- **(mbse-expressions 31, domains as data, API 157)** **A define's frame binds each edition**: a dialect covering one as
  `standard`; one covering several, each by its common name or its published name spelled as an identifier (`C11`,
  `Cpp17`, `Python_3_8`, `TypeScript_5_0`).
- **(mbse-expressions 31, domains as data, standards' design)** **The order of editions** is the order each define
  writes them, oldest first; read back from a snapshot they come by designation, as mbse-schemas writes a relation's
  entries sorted by its key ([PRI-001: declaration order](../PRINCIPLES.md#PRI-001)'s exception), so nothing claims
  their order but the define's.
- **(mbse-expressions 31, domains as data, API 159)** **SystemVerilog, Patterns, MATLAB, Excel and LaTeX cover no
  edition**, their code naming none: SystemVerilog's are stage 6's, which records them in this model
  ([CAP-231: the SystemVerilog expression dialect, complete](CAP-231.md)).
- **(mbse-expressions 31, domains as data, API 160)** **The corpus's `standards` case**: C23's edition written as one
  document, pinning an edition's properties and kinds byte for byte, C23 since its kinds differ from C17's; the
  dialects' singletons' documents hold their `Covers` entries.
- **(mbse-expressions 31, domains as data, standards' design)** **The cost**: Python3's define writes 16 editions and
  444 `HasStandard` entries, TypeScript5's 10 and 410, C's 3 and 61, C++'s 3 and 101; the suites run Python3's and
  TypeScript5's defines only where they read their standards or their domains (FRM-13, DOM-21, the corpus).
- **(mbse-expressions, stage 6, API 177)** **SystemVerilog's editions**: IEEE Std 1364-1995, 2001 and 2005 and IEEE
  Std 1800-2005 to 2023, body `org.ieee`, number `1364` or `1800`, revision the year, common names `Verilog-1995` ...
  `SystemVerilog-2023` as mbse-programs labels them, bound by those names spelled as identifiers (`SystemVerilog_2023`);
  each of the six dialects lists only its own kinds, from mbse-programs' `SINCE`; `Expressions`, `Types` and
  `Preprocessor` cover all eight, `Patterns`, `Assertions` and `Constraints` the five of IEEE 1800. This supersedes item
  159's "SystemVerilog covers none" ([the port's API, Settled in stage 6](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-stage-6-systemverilog-for-the-users-review)).
