# CAP-097: value domains of published standards

*Implements* [FEA-024: expressions as data](../features/FEA-024.md). *Relates to* [CAP-232: domains inferred for terms](CAP-232.md), [CAP-180: ISO/IEC 11404 datatypes replace the Basic expression dialect](CAP-180.md), [CAP-267: C and C++ terms read under the ABI their holder names](CAP-267.md), [PRI-012: model published standards](../PRINCIPLES.md#PRI-012), [PRI-018: no model needs code to read or write](../PRINCIPLES.md#PRI-018).

## As built: mbse-expressions

### Value domains

As built in mbse-expressions 0.9.0, by domains as data's stages 1 to 3 (PRs #27, #28 and #30), in both languages: a
domain has one form, the stored one, schema-governed data in a store like any other model, and no domain is a class
or a function (Decided, "One form of a domain"). Until then the stored domains of 0.7.0 were read into code objects
(`Domains.read` and its data classes), and every dialect but Basic had code domains alone. Only intrinsics'
implementations, and evaluation's arithmetic over the values it computes, are code
([FEA-024: expressions as data](../features/FEA-024.md#decided), schema extension 9). A term carries no domain
(Decided, below): giving each term its domain is [CAP-232: domains inferred for terms](CAP-232.md)'s. The settled
points are the port's [API](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md),
Settled in stage 3, 16 to 29, and Settled in domains as data's stages 1 to 3, 112 to 153.

- **A domain is an `Expressions.Framework.Domain`**, a reference object holding its `kind`, owned by the dialect that
  defines it by name through `Expressions.Framework.Defines(dialect, name, domain)`, unique `[dialect, name]` and
  `[domain]`, so that its path is its dialect's singleton then its name (`dialect.domains({"name": "octet"})`), which
  snapshots write and documents refer to. `Expressions.Framework.HasDomain(schema, domain)`, unique both ways, relates
  it to its schema, a named `Schemas.OfAny` restricted to the scalar it narrows, which reads it through the extension
  adjacency `domain` (Decided, "Every domain a schema"). A token's domain and a 4-state type's have no schema, since no
  basic scalar holds their values. A domain's name is its `Defines` entry's, as its standard names it; its schema's
  is spelled as a dotted identifier where the name is not one (`modulo(256)` as `modulo_256`, `unsigned long long` as
  `unsigned_long_long`, `std::float16_t` as `std_float16_t`, `_Float16` as `Float16`, mbse-schemas refusing a symbol
  that begins with `_`) (API 123, 131).
- **A domain's kind is its dialect's, then its kind**: `Expressions.Framework.DomainKind` is a union of the dialects'
  unions of kinds, `Expressions.<path>.DomainKind`, as `Expressions.Framework.Term` is of their `Term`s (Decided,
  "`DomainKind` stays two-level"), so that a domain's `kind` is written
  `d.kind(lambda k: k.as_value(lambda a: a.as_union(lambda u: u.ieee754(lambda v: v.ieee754(lambda f: f.format("binary32"))))))`,
  and C's and C++'s `nullptr_t` are each their own (API 113).
- **A published standard is a dialect of its own** (Decided, A; and E, [CAP-180: ISO/IEC 11404 datatypes replace the Basic expression dialect](CAP-180.md#decided)): four standard dialects, each a family with one
  dialect, `Expressions`, a singleton of its own schema with no terms, own the kinds their standards define and the
  domains named as their standards name them, and every other dialect's domains are instances of their kinds or of
  its own (API 112):

  | Dialect | Its kinds (tag: schema `Expressions.<Family>.Expressions.<Of...>`) | Its domains |
  |---|---|---|
  | `ISOIEC11404.Expressions` | `boolean`, `integer`, `modulo`, `bitstring`, `octet`, `octetstring`, `state`, `packed`, and `Packs` | `boolean`, `integer`, `octetstring`, `octet`, `modulo(256)` |
  | `IEEE754.Expressions` | `ieee754` | `binary64`, `binary32` |
  | `IEEE1164.Expressions` | `ieee1164` | `std_logic` |
  | `Unicode.Expressions` | `unicode` | `string` |

  ISO/IEC 11404's, as its own definitions name them, are
  [CAP-180: ISO/IEC 11404 datatypes replace the Basic expression dialect](CAP-180.md#as-built-mbse-expressions)'s.
  Patterns holds no kind and no domain: it uses the standard dialects' domains as any dialect does (E, above).
- **A language's own kinds are its dialect's** (Decided, B and H): SystemVerilog's `logic` (4-state) and `bit`
  (2-state), each `width` and `signed`; Python3's `str` (code points, lone surrogates included) and the tokens
  `nonetype` and `ellipsis`; TypeScript5's `string` (UTF-16 code units) and the token `null`; MATLAB's `string` and
  Excel's `text`, UTF-16 code units too; Excel's `error`, its `members` the error codes; and C's and C++'s `nullptr_t`,
  each its own (API 115, 141, 150).
- **What a domain means is its properties, inferred ones included** (Decided, "Inferred properties are still
  properties"): its kind's parameters and the properties that follow from them alike, populated by hand in each
  dialect's `define` until constraint resolution computes them ([CAP-043: constraints resolved in any direction](CAP-043.md)):

  | Kind | Parameters | Inferred, populated by hand |
  |---|---|---|
  | `integer` | `width`, optional (unbounded without it); `signed`; `overflow`: `wrap`, `saturate` or `raise` | `least`, `greatest` (absent where unbounded), `ordered` |
  | `modulo` | `modulus` | `least`, `greatest`, `ordered` |
  | `ieee754` | `format`: `binary16`, `binary32`, `binary64`, `binary128`, `decimal32`, `decimal64` or `decimal128`, absent where IEEE 754 names none; `rounding`: one of the standard's rounding-direction attributes | `width`, `radix`, `precision`, `emax` (IEEE 754-2019's parameters of the format), `ordered` |
  | `bitstring`, `octetstring` | `width` (an octet string's fixed or variable) | `ordered` |
  | `ieee1164` | `width`, optional: one state without it (`std_logic`), that many with it | `ordered` |
  | `state` | its `members` | `ordered` |
  | `packed` | its `codes`, one per member of the state it packs; the state and its representation linked by `Packs(packed, domain, representation)` | `ordered` |
  | SystemVerilog's `logic`, `bit` | `width`, `signed` | `least`, `greatest` (of its known values), `ordered` |
  | `boolean`, `octet`, `unicode`, and the languages' string, token and error kinds | (`error`: `members`) | `ordered` |

  `ordered` is true of `integer`, `modulo`, `octet`, `ieee754`, `octetstring`, `unicode`, `packed`, `logic`, `bit`
  and the string kinds, false of the others. What a result is fitted into is an integer's own `overflow` or a
  modulo's own `modulus`; the relation from an operation's argument domains to its result domain is
  [CAP-232: domains inferred for terms](CAP-232.md#decided)'s, and no kind links another domain (API 114).
- **Each dialect's `define` writes its domains** (stage 3), run after the installs in a transaction of its own,
  idempotent, only for the types its language's standard, or a commonly used adjacent standard, defines (Decided, "The
  scope of stored domains"), each named as its standard names its type, with its parameters and its inferred
  properties, each but a token's and a 4-state type's related to its schema:
  - C's (C11 to C23), C++'s (C++17 to C++23) and the two ABI dialects' are
    [CAP-267: C and C++ terms read under the ABI their holder names](CAP-267.md#as-built-mbse-expressions)'s: C's own
    `bool`, `int8_t` to `int64_t` (11404's `integer`, `overflow` `raise`), `uint8_t` to `uint64_t` (11404's
    `modulo`), `_Float16` to `_Float128`, `_Decimal32` to `_Decimal128` and `nullptr_t`; C++'s `bool`, the same
    exact-width types, `std::float16_t` to `std::float128_t`, `std::bfloat16_t` and its own `nullptr_t`; and each ABI's
    the types the C and C++ standards leave to the implementation (API 131, 132).
  - SystemVerilog's (IEEE 1800-2023): `logic`, `reg`, `integer` and `time` of its kind `logic`; `bit`, `byte`,
    `shortint`, `int` and `longint` of its kind `bit`; and `real` and `shortreal`, IEEE 754's `binary64` and `binary32`
    (API 141, 142).
  - Python3's `bool`, `int` (11404's `integer`, unbounded), `float` (`binary64`), `str`, `bytes` (11404's
    `octetstring`) and the tokens `NoneType` and `ellipsis`; TypeScript5's `boolean`, `number`, `bigint`, `string` and
    the token `null`; MATLAB's `double`, `logical` and `string`; Excel's `number`, `logical`, `text` and `error`, its
    members Excel's fifteen error values (API 149 to 152).
  - LaTeX stores none: its code domains (`number`, `text`, `truth`) stay inference's (Decided, K and N).
- **Not domains**: compound values, which have schemas (a struct, a record, an array, a string literal's type), `RegExp`
  and Python's `complex`, a value schema of Python3's ([CAP-227: the Python3 expression dialect](CAP-227.md#decided));
  a type a program declares (its own enums and typedefs); a family of types such as C's `_BitInt(N)` or
  SystemVerilog's sized vectors, whose type is computed from the term's own width and signedness; and what no standard
  in scope defines (`__int128`, `__float128`, `__fp16`). There is no synonym machinery: each standardized name gets its
  domain, `int32_t` beside `int`, `reg` beside `logic` (Decided, H and "The scope of stored domains").
- **The reading interface**, `Framework.Domains` (TypeScript the same, camelCase), over a stored domain's
  `Readers.OfObject`: `kind_of(domain)`, its kind `(dialect, tag, record)`, the dialect's tag first (Decided, "`kind_of`
  gives the dialect too"), "a domain needs a kind" where it holds none; `properties(domain)`, its kind's properties set,
  parameters and inferred alike; `name_of(domain)`, the name its dialect defines it by, or None; `domains(dialect)`, a
  dialect's domains by name; `operations(dialect)`, its operations by name; and `arity(operation)` (API 117, 140).
- **What reads the stored domains** (Decided, K): C's, C++'s and SystemVerilog's evaluation, inference and validation
  read every named type they use (a literal's type and its range, a cast's target, `int` for C's promotions, `size_t`
  for `sizeof`, `bool` for a comparison, SystemVerilog's `real` for a `shortreal` among integrals) from the stored
  domains through the term's holder, and build of each the working value the arithmetic computes on (`CType`,
  `SvType`); their code type tables (`CType`'s `TYPES`, `SvType`'s) are gone (API 133 to 137, 143 to 145). A literal
  out of range is reported against the domain its dialect stores for it. A lone term that reads a named type is refused
  ([CAP-098: dialects over one framework](CAP-098.md#decided), "No lone terms"). The other dialects' evaluators compute
  on natives and read no domain; their code domains (Python3's `Int`, MATLAB's `Double`, ...) are inference's
  `OfTypes`, as Patterns' natives are, marked as [CAP-232: domains inferred for terms](CAP-232.md)'s to replace (API
  124, 149).
- **Domains name standards.** `ieee754` is IEEE 754-2019's binary and decimal formats, with their values, special
  values and overflow (to infinity, with its exceptions) as the standard defines them; `decimal32` is among them since
  stage 3. A format IEEE 754 does not name is an `ieee754` domain with no `format`, held by its parameters: x87's 80-bit
  extended format (IEEE 754-2019's binary64 extended format: `width` 80, `radix` 2, `precision` 64, `emax` 16383), an
  ABI's `long double`, and C++23's `std::bfloat16_t` (`width` 16, `radix` 2, `precision` 8, `emax` 127; Decided, M, in
  [CAP-230: the C++ expression dialect](CAP-230.md#decided)); `Ieee754`'s arithmetic takes a format by its name or by
  those parameters (API 140). This supersedes 0.7.0's "a format outside it (fp8, `bfloat16`, x87's 80-bit format)
  would be a domain of its own, named for its specification". `ieee1164` is VHDL's nine-valued `std_logic`;
  SystemVerilog's four-state `logic` is its subset `{0, 1, X, Z}`, its own kind. `integer` is two's complement, the
  only signed representation C23 and C++20 allow, so ones' complement and sign-magnitude are not domains.
- **`bitstring` and `octetstring` are unformatted.** `octetstring(n)` and `bitstring(8n)` hold the same patterns, but
  they are separate domains.
- **`unicode` values are sequences of code points, compared by code point.** An encoding (UTF-8, UTF-16, UTF-32) is
  representation only: equal code points are equal strings in any encoding. Canonical equivalence is not equality. A
  lone surrogate is not a value of `unicode` (it is of Python3's `str`). A `unicode` domain has no width: a maximum
  length is a constraint of the data, and belongs in the schema.
- **`state` is the generic enumeration**: one bit's states, an enumeration of mbse-schemas, its members unordered; a
  `packed` state orders by its representation. **Packing is its own domain**: a state paired with a fixed-size domain
  and the code of each member in it, so one state can be packed
  several ways; an enumeration is not an integer (Decided, in
  [CAP-180: ISO/IEC 11404 datatypes replace the Basic expression dialect](CAP-180.md#decided)). The corpus's and the
  tests' own `state` and `mode`, fixtures no language or standard defines, are owned by ISO/IEC 11404's singleton,
  since mbse-schemas requires every domain an owner (Decided, "The corpus's and the tests' own domains" and R).
- **Operations as data, beside the domains.** A dialect names its operations through
  `Expressions.Framework.Operates(dialect, name, operation)`, unique `[dialect, name]` and `[operation]`, owning
  nothing: an operation is a `Schemas.OfExpression` its module owns (`Expressions.Patterns.Expressions.<name>`), its
  pattern's variables its arguments, positional in their declared order, its `result` its return (API 20, 21). Since
  stage 2, validation of a Patterns call reads them through the term's holder
  ([CAP-098: dialects over one framework](CAP-098.md#domains-as-data-in-the-framework)). The container constructors
  `list` and `mapping` are framework kinds (API 23). Other dialects' operations as data are a follow-up: each has its
  singleton, its vocabulary code (API 28).
- **Tests**: DOM-17 (the standard dialects and the reading interface), DOM-18 (each language's kinds), DOM-19 (C's,
  C++'s and the ABI dialects' domains), DOM-20 (SystemVerilog's) and DOM-21 (Python3's, TypeScript5's, MATLAB's and
  Excel's) pin each domain, its kind, its hand-populated properties and its schema, the same values under the same IDs
  in both languages; the corpus's `domains` case and one data case per dialect (`c_domains`, ..., `excel_domains`) pin
  each dialect's domains' names and order byte for byte, and CONF-04 each one's kind as read back (API 118, 147, 153).

## Design

### Domains and scalar values (mbse-schemas' schema extension, 2)

Moving `.bits` and `.bytes` means associating a domain to a scalar schema: built as `HasDomain` between a domain and
its schema, a named `Schemas.OfAny` restricted to the scalar it narrows (As built, above). A literal's value was an
`OfAny` of the five basic scalars ([CAP-095: Basic terms as data](CAP-095.md)), and since mbse-expressions 0.8.0 is any
value ([CAP-233: literals of any value](CAP-233.md)), so no value properties per scalar are needed.

### Relocating things from mbse-schemas (mbse-schemas' schema extension, 3)

Definitely:

- constraining the size of Schemas.OfScalar : move to mbse-expressions via `HasDomain` per above
- allowing schemas to define parameters on definition and bind them to expressions on instantiation : keep in mbse-schemas except for typing via `HasDomain`
- allowing Schemas.OfScalar (maybe others) to be bound to an expression

### Parameters (mbse-schemas' schema extension, 4)

In mbse-schemas, a parameter can only denote a schema
In mbse-expressions, a parameter can denote a schema or a domain

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- (Superseded by the port's stage 3, below: a term carries no domain, and domains are objects their dialect defines
  by name.) **A term's domain is a registered name until the port's stage 3** (2026-10-30, "yes", on what the port's
  stage 2b raised; [the port](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/README.md#decided), Decided), translators'
  conversions registering the domains they hand back included. Stage 3 makes domains objects that dialects define by
  name ([FEA-024: expressions as data](../features/FEA-024.md#decided), Decided, "Porting to the stabilized
  mbse-schemas", 4), in place of the process-wide registry.
- **The port's stage 3** (2026-10-30, reviewing a first draft that made domains objects a term named;
  [the port](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/README.md#decided-for-stage-3), Stage 3's model, Decided,
  1 to 6, and the answers on A, B and C):
  1. **A term carries no domain.** "Terms do not designate their schema. Whatever reference object owns the root term
     must specify its schema." Every kind loses `domain`, the framework's and each dialect's. This supersedes "wait,
     all terms have a domain" (2026-10-28) and mbse-schemas' Schema extension, Decided, 21's "A term has a domain"
     ([FEA-024: expressions as data](../features/FEA-024.md#decided)).
  2. **No domain inference yet**, and what needs a term's domain deferred with it: [CAP-232: domains inferred for terms](CAP-232.md#decided),
     where it is recorded.
  3. **Terms hold values.** "terms are not restricted to scalars. Terms can have any value (Schemas.OfAny)"; then
     "yes restrict `literal` to scalars, but also provide container constructors as terms". A `literal` stayed an
     `OfAny` of the five basic scalars (the agent's gloss of "scalars"); new kinds construct containers from terms.
     *Superseded* (2026-11-02): a literal holds any value ([CAP-233: literals of any value](CAP-233.md#decided)).
  4. **Expressions deal in values.** "CORRECTION: 'expressions only deal in scalars' -> 'expressions only deal in
     values'" (Schema extension, Decided, 13).
  5. **Every domain a schema.** "(i) can we make every domain a schema too?", and on the proposal that answered it
     (A): "you can choose to keep the schema and domain separate and track them through a relation with unique, or use
     schema extension". Chosen: both kept separate and related, since an extension adds only an adjacency to a
     relation of two links and no properties, so a domain's parameters need an object of their own either way. The
     domain's schema is a named `Schemas.OfAny` restricted to its scalar, defined in its dialect's module
     (`Expressions.Basic.uint8`); the domain is an `Expressions.Framework.Domain`, holding its `kind`;
     `Expressions.Framework.HasDomain(schema, domain)`, unique both ways, relates them, and an extension adjacency
     `domain` on `Schemas.OfAny` reads it from the schema.
  6. **Dialects model their operations.** "(ii) dialects also define operation models which arguments as
     Schemas.OfVariable and return value as Schemas.OfAny", and on the proposals for it and for container
     constructors (B and C): "okay for now". An operation is a `Schemas.OfExpression` its dialect names, its pattern's
     variables its arguments and its `result` its return; `list` and `mapping` are framework kinds.
- **Each dialect a singleton by name** (2026-11-01, confirming the coordinating agent's proposal built on the user's
  direction of 2026-10-30, "It's not hard to add an ownership path to the schema" and "ah, schema *extension* is the
  preferred form"): "yes, each dialect has a singleton by name"; with Decided, 4 of the port, it owns its domains
  through `Defines(dialect, name, domain)` (As built, above).
- **One form of a domain: the stored one** (on mbse-expressions' proposal, domains as data). Asked why
  there was a "working" domain, a code object, beside the stored one, the user agreed there should be none: "Yes, write
  it up". It applies "Dialects should be models" and [PRI-018: no model needs code to read or write](../PRINCIPLES.md#PRI-018),
  against which stage 3's "what a domain means stays code, as intrinsics' implementations are", an agent's proposal
  never put to the user on its own, had grown to cover the domains themselves.
- **Inferred properties are still properties** (2026-11-04), correcting the proposal's first draft, "What a domain
  means becomes functions": "no. inferred properties are still properties. For now they must be hand populated, but
  eventually they will be computed by constraint resolution." A domain stores its parameters (width, signedness,
  overflow, format, rounding) and the properties that follow from them (its least and greatest values, whether it is
  ordered, ...) alike, as properties of its kind; the inferred ones are populated by hand in each dialect's define until
  constraint resolution computes them ([CAP-043: constraints resolved in any direction](CAP-043.md)). No domain is a
  class or a function.
- **`Anything` and `Opaque`** (2026-11-04, the proposal's question 3): "agreed. Schemas.OfAny kind of handles that": no
  stored "anything" domain; where nothing is known, a result's domain is absent, its value an unrestricted
  `Schemas.OfAny`.
- **Kinds shared per standard** (2026-11-04, the proposal's question 4): "proceed with this for now. I will review":
  Patterns' kinds (two's complement, IEEE 754, IEEE 1164, ...) shared, each dialect's domains instances of them under
  its own names. *Superseded* (2026-11-06) by A and E, below: a standard's kinds are its own dialect's, and Patterns
  holds none; "Patterns' kinds" recorded an inheritance from Basic, not a choice.
- **A. No pool of shared kinds** (2026-11-06, on stage 1's design): "Do we need "pure shared" types at all? I don't mind
  dialects depending on other dialects such as IEEE-754 for example." Read so: a published standard is a dialect of its
  own, its kinds its own, and a dialect's domains are instances of the kinds of the dialects it uses, its install
  depending on theirs. This supersedes "each install stands alone" (the port's API, 35) where a dialect uses another's
  kinds, and refines question 4, above: a kind is shared by being its standard dialect's, not by belonging to a common
  pool. Which kinds are ISO/IEC 11404's, and Patterns holding none, is E
  ([CAP-180: ISO/IEC 11404 datatypes replace the Basic expression dialect](CAP-180.md#decided)).
- **B. A language's own domains are its dialect's** (2026-11-06): "yes, SV specific domains are part of the SV dialect
  (that seems obvious to me). Type inference tokens like `nullptr_t` should get their own domain here". So
  SystemVerilog's 4-state types are SystemVerilog's domains, of its own kind; by the same rule Python's `str` and
  TypeScript's `string` are their dialects' own; and a type inference token, such as `nullptr_t`, has a stored domain.
- **H. What is not a domain** (2026-11-06; E to H each approved "yes", as the coordinating agent put it): (1) To `complex`: "what is Python's `complex` ? Seems
  like an object to me". It is two IEEE 754 binary64 floats, `real` and `imag`, immutable and compared by value: not a
  domain but a value schema of Python3's ([CAP-227: the Python3 expression dialect](CAP-227.md#decided), J). (2)
  `RegExp`: not a domain. (3) Excel's error values: Excel's own domain, of its own kind, its members the error codes.
  (4) Compound values: not domains; they have schemas. The tokens (`nullptr_t`, Python's `None`'s and `...`'s types,
  TypeScript's `null`) each have a domain of their own, as B decided.
- **Names are the standards' own** (2026-11-09, on [stage 1's review](https://github.com/pitaman71/mbse-expressions/pull/27#pullrequestreview-5832969295)):
  to naming the standard dialects' domains by their standards: "yes, adopt names the standard uses for datatypes it
  defines (is this even a question?)"; and to the kinds keeping their tags: "there is no need to preserve the old tags
  imo". So every domain and kind is named by its standard's own identifier, its tag and its schema too, with no alias
  for the old names. How ISO/IEC 11404's are named is
  [CAP-180: ISO/IEC 11404 datatypes replace the Basic expression dialect](CAP-180.md#decided)'s. IEEE 754's
  (`binary64`), IEEE 1164's (`std_logic`) and Unicode's names were already their standards' own, and stay.
- **`DomainKind` stays two-level** (2026-11-09), as built: the dialect, then its kind, the pattern of `Term`, which the
  user decided ("Framework.Term -> Dialects.C.Term / Framework.Term -> Dialects.Cpp.Term";
  [CAP-226: complete expression dialects](CAP-226.md#decided)). Its examples are written in builder calls, not wire
  format ([PRI-019: fluent builder syntax](../PRINCIPLES.md#PRI-019)).
- **`kind_of` gives the dialect too** (2026-11-09): "yes, dialect too". `Domains.kind_of` (`kindOf`) returns
  `(dialect, tag, record)`, the dialect's tag in `Expressions.Framework.DomainKind` first, so that C's and C++'s
  `nullptr_t` are told apart, in both languages.
- **mbse-domains is not a priority** (2026-11-09): asked whether the standard dialects belong in the repository
  mbse-domains, which [CAP-211: text as words, phrases, paragraphs and documents](CAP-211.md) and
  [CAP-212: dates, times, durations and intervals in ISO 8601](CAP-212.md) plan: "refactoring domain dialects out of
  mbse-expressions is not a priority right now". They stay in mbse-expressions, beside the dialects that use them.
- **K and N** (2026-11-10, on stage 3's design): "K,N - agreed".
  - **K. The code type tables go.** C's, C++'s and SystemVerilog's code type tables (`CType` and its `TYPES` in C's
    `Domains`, which C++ shares; `SvType` and its `TYPES` in SystemVerilog's) go. Evaluation and inference read every
    named type they use (a literal's, a cast's target, `int` for the promotions, `size_t` for `sizeof`, `bool` for a

    on, built from a stored domain, and the conversions as code ([CAP-232: domains inferred for terms](CAP-232.md#decided)).
    A lone term is refused, consistent with "there is no valid programming context where a lone term needs a domain or
    schema" ([CAP-098: dialects over one framework](CAP-098.md#decided)), by mbse-schemas' `TypeError`. A breaking
    change, in 0.9.0.
  - **N. LaTeX stores no domains.** Its code domains (`number`, `text`, `truth`) stay inference's,
    [CAP-232: domains inferred for terms](CAP-232.md)'s to replace, as the other dialects' `OfTypes` do.
- **The scope of stored domains** (2026-11-10, on stage 3's questions L and O): "we do not need a domain for every type,
  just those standardized in by the language itself or by commonly used adjacent standards like cstdint. Adjacenct
  standards may be their own dialect"; then: "by "intrinsic types" for C/C++ this means those that cross the ABI". So:
  - A domain is stored only for a type the language's standard defines, or that a commonly used adjacent standard
    defines. For C and C++ those are the types that cross the ABI: the fundamental arithmetic types; `nullptr_t`; and
    the `<stdint.h>`/`<cstdint>` and `<stddef.h>` typedefs (`int32_t`, `size_t`, ...). Where each is held is
    [CAP-267: C and C++ terms read under the ABI their holder names](CAP-267.md#decided)'s.
  - A type a program declares gets no stored domain: a program's own enums and typedefs. This supersedes "For stage 3:
    C's and C++'s enums are to be stored as enumerations packed into their integer types"
    ([CAP-180: ISO/IEC 11404 datatypes replace the Basic expression dialect](CAP-180.md#decided), "An enumeration is
    not an integer").
  - No synonym machinery: L's options drop, and with them the question. Each standardized name gets its domain as its
    standard defines it, `int32_t` beside `int`, `reg` beside `logic`.
- **The corpus's and the tests' own domains** (2026-11-10, settling what O left open). Told that `state` (an
  enumeration of `IDLE` and `RUN`) and `mode` (`packed`, packing `state` into an `octet`) are fixtures the conformance
  corpus and some tests invent to exercise `packed`, that no language or standard defines them, and that the scope rule
  means a dialect stores only what its standard defines, the user was given this recommendation and answered "agreed":
  the corpus case and the tests write them as plain `Expressions.Framework.Domain` objects, owned by no dialect; there
  is no `Defines` entry for them in the ISO/IEC 11404 singleton, or any other; there is no test dialect. Not built:
  mbse-schemas refuses a domain with no owner as the model stands, so how to settle that was put as question R, below.
- **R: (a), by the agent's check** (2026-11-10). The user left it to the agent: Excel's error values packed into their
  `ERROR.TYPE` codes, if Microsoft's documentation of `ERROR.TYPE` gives those codes, `state` and `mode` then going;
  otherwise (a), the fixtures kept in ISO/IEC 11404's singleton, and noted. The options were: (a) keep them in ISO/IEC
  11404's singleton, the record noting why, no model change; (b) a domain no dialect defines a counted object, which
  [CAP-133: no durable references to counted objects](CAP-133.md) forbids holding; (c) mbse-schemas letting an owner
  adjacency be optional, a sibling's change; (d) no invented fixtures, the user's option, Excel's error values packed
  into their `ERROR.TYPE` codes. *(agent)* The documentation (Microsoft Support, "ERROR.TYPE function", checked
  2026-11-10) gives codes for eight error values only, `#NULL!` 1 to `#GETTING_DATA` 8, and "Anything else" `#N/A`:
  none for the seven Excel's `error` domain holds since (`#SPILL!`, `#CALC!`, `#FIELD!`, `#BLOCKED!`, `#CONNECT!`,
  `#BUSY!`, `#UNKNOWN!`). So no `packed` domain can pack Excel's errors into documented codes, and `state` and `mode`
  stay in ISO/IEC 11404's singleton: fixtures no standard defines, owned there because mbse-schemas requires every
  domain an owner.
- **The links between dialects** (2026-11-10). Told what stage 3 built that links one dialect to another, after saying
  "I am a little concerned about over-exerting ourselves to try to link between dependent dialects", the user answered
  each:
  - The holder-to-ABI relation, `Expressions.Framework.HasAbi`: "yes, keep it"
    ([CAP-267: C and C++ terms read under the ABI their holder names](CAP-267.md#decided)).
  - IEEE 754's properties, `width` among them, written on the other dialects' `ieee754` domains: "yes, this is
    critical for precision". Kept as built.
  - `Framework.Domains.domains(dialect)` and the lookups that read one dialect's domains from another's terms (C's and
    C++'s through their holder's ABI, SystemVerilog's own): "this is what I want to review". Kept, and listed for the
    user's review (Decided by an agent, below, and
    [CAP-267: C and C++ terms read under the ABI their holder names](CAP-267.md#decided-by-an-agent-for-review)).

## Decided by an agent, for review

Recorded in mbse-expressions' design, not marked as the user's: each *proposed* until reviewed.

- An `ieee1164` domain of a `width` is VHDL's `std_logic_vector`, its value that many states, the most significant
  first; without one it is a single `std_logic`. SystemVerilog's binary vectors and those with x or z bits are its
  counterparts.
- A `state` (0.7.0's `enum`) is unordered unless packed, when it orders by its representation. (The conversions moved
  to [CAP-232: domains inferred for terms](CAP-232.md), which restores them; a literal stored without a domain, and
  writers leaving defaults out, went with the literal's `domain` at stage 3.)
- (Superseded where a term's domain is named: by stage 3, Decided, above, a term carries no domain.) A literal holds its
  domain by value, as a value object, written by name when the domain is registered and by value
  otherwise; domains compare by structure. A packed domain packs an enum into a fixed-width integer or bits, with an
  integer code per member.
- Value domains name published standards where one exists (`Ieee754`, `Ieee1164`), rather than free representation
  parameters: no float format by widths and flags, no ones' complement or sign-magnitude integers, no `Decimal` apart
  from IEEE 754's decimal formats. (*Superseded* in part: "with only the parameters the standard defines" was
  corrected by the user, [PRI-012: model published standards](../PRINCIPLES.md#PRI-012); and Basic is Patterns, which
  holds no domain, [CAP-180: ISO/IEC 11404 datatypes replace the Basic expression dialect](CAP-180.md#decided), E.)

Recorded in [the port's API](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md),
Settled in domains as data's stages 1 to 3, items 112 to 153, not marked as the user's: each *proposed* until reviewed.
Those most worth reviewing:

- **(mbse-expressions 27, domains as data, stage 1's review)** **The kinds `ieee754`, `ieee1164` and `unicode` keep
  their names**, each the standard's own designation, as their families are, where the standards were silent on a
  name for the kind.
- **(mbse-expressions 27, domains as data, API 112)** **The standard dialects' shape and names**: each a family with
  one unversioned dialect, `Expressions`, by the namespace rule; ISO/IEC 11404 spelled as ISO writes it, without the
  slash a name cannot hold (`ISOIEC11404`), as IEEE 754 is without its space; each a singleton of its own schema, a
  branch of `Expressions.Framework.Dialect`, with no `Term`, holder or `Terms.Dialect` until it has terms (a standard
  dialect's shape stands as the agent's choice, as the user had it, [CAP-098: dialects over one framework](CAP-098.md#decided), G).
- **(mbse-expressions 27, domains as data, API 114)** **Which properties are inferred**: `ordered` on every kind; an
  integer's, a modulo's and SystemVerilog's `logic`'s and `bit`'s `least` and `greatest`; IEEE 754's `radix`,
  `precision` and `emax`, IEEE 754-2019's parameters of each interchange format. `ordered` is true of the kinds listed
  in As built, false of the others, as the code domains' `ORDERED` had it.
- **(mbse-expressions 27, domains as data, API 117)** **The reading interface's names**, `kind_of`, `properties`,
  `name_of`, `operations` and `arity`, and "a domain needs a kind" where a domain holds none.
- **(mbse-expressions 30, domains as data, API 131)** **A schema's name is spelled as a dotted identifier where its
  type's is not one** (`unsigned_long_long`, `std_float16_t`), and drops a type's leading `_`
  (`Expressions.C.Expressions.Float16` for `_Float16`): mbse-schemas reads a symbol beginning with `_` as a private
  member's; the dialect's `Defines` name keeps it.
- **(mbse-expressions 30, domains as data, stage 3's design)** **A domain's value is the native its evaluation already
  holds**: an int for an integer or a modulo, a float for `binary16` to `binary64`, and canonical text for `binary128`,
  the decimal formats and the formats IEEE 754 does not name, as `Ieee754` holds `binary128`, so their schemas narrow
  `str`. `bool` is 11404's `boolean`, `ordered` false.
- **(mbse-expressions 30, domains as data, API 140)** **IEEE 754's kind gains `width`**, inferred, the format's width in
  bits (IEEE 754-2019's `k`), on every `ieee754` domain, which SystemVerilog's types read in place of `Ieee754.WIDTHS`;
  and `Ieee754` takes a format by its parameters (radix, precision, emax) where IEEE 754 names none, its values text:
  x87's extended format is IEEE 754-2019's binary64 extended format (§3.7), with no interchange format to name, so an
  `ieee754` domain with its parameters and no `format`, as the user decided of `std::bfloat16_t`

  interchange formats'.
- **(mbse-expressions 30, domains as data, API 141)** **SystemVerilog's 2-state types are its own kind, `bit`**, as IEEE
  1800 names its 2-state integral type, beside the 4-state `logic`; a 4-state domain has no schema, since no basic

- **(mbse-expressions 30, domains as data, API 143 and 145)** **SystemVerilog reads a named type through the holder only
