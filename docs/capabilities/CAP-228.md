# CAP-228: the TypeScript5 expression dialect

*Implements* [FEA-024: expressions as data](../features/FEA-024.md), [FEA-008: expressive program models](../features/FEA-008.md). *Relates to* [CAP-226: complete expression dialects](CAP-226.md), [CAP-036: complete kinds for Python, TypeScript and C and C++](CAP-036.md), [CAP-092: every construct of TypeScript's standards](CAP-092.md), [CAP-227: the Python3 expression dialect](CAP-227.md), [CAP-233: literals of any value](CAP-233.md).

## As built: mbse-expressions

Built in mbse-expressions' stage 4 of [the complete dialects](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/dialects/README.md#stages-proposed-once-decided)
(main at 8804e1e, PR #18) and released in 0.8.0, in both languages, its schemas named by the namespace rename
(`Expressions.TypeScript.TypeScript5`, [CAP-226: complete expression dialects](CAP-226.md#decided), Decided); every choice made where the decisions were
silent is in [the port's API, Settled in stage 4 (TypeScript5)](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-stage-4-typescript5-for-the-users-review),
items 70 to 85, which hold the detail this section only bridges. `TypeScript5` is a new dialect, complete by
[CAP-226: complete expression dialects](CAP-226.md)'s rules: every expression of TypeScript 5 (5.0 to 5.9) and the
JavaScript it holds, as typescript-estree has them, with JSX as an extension; function, arrow and class bodies stay
mbse-programs' statements. Reading TypeScript's every construct is
[CAP-092: every construct of TypeScript's standards](CAP-092.md)'s; mbse-programs has no bridge to it yet.

- **The kinds**: `Expressions.TypeScript.TypeScript5.Term`, whose holder is `Expressions.TypeScript.TypeScript5.Expression`, has 46
  branches: mbse-programs' 35 expression kinds (2 of them JSX), each `Expressions.TypeScript.TypeScript5.<Name>` in its names and
  shapes, properties in source order, tagged by its name lowercased (`binaryexpression`, `tsasexpression`);
  TypeScript5's `constant`; the helpers an expression's place mixes with expressions (`spreadelement`, `elision`,
  `property`, `jsxemptyexpression`, `tsemptybodyfunctionexpression`); three patterns (`arraypattern`,
  `objectpattern`, `assignmentpattern`); and the framework's `error` and `missing` (items 70 and 72). Only
  `arrayexpression` reuses a framework kind, `list` (item 73). Each kind records TypeScript 5.0 to 5.9 as its
  standards, JSX's none, as data nothing reads yet (item 80).
- **The sublanguages**: `Expressions.TypeScript.TypeScript5.Pattern` (14 branches: the four patterns, the terms a target may be,
  and `property`, `elision` and `tsparameterproperty`), held by parameters and an assignment's `left`; and
  `Expressions.TypeScript.TypeScript5.Type` (43 branches: mbse-programs' 37 type nodes and the terms a type holds), held by `as`,
  `satisfies`, `<T>x`, annotations, type arguments and constraints. A schema is a branch of every union whose
  positions hold it, with no wrapping level (Decided, below; item 71). Since stage 5 each also lists `error` and
  `missing`, 16 and 45 branches in 0.8.0 (API 101).
- **The helpers**: what a kind holds that is not a term (a template's elements, decorators, annotations, type
  parameters and arguments, signatures, JSX's names, attributes and children), and a type or a pattern within a kind,
  is read by `Terms.form` as a `Terms.Part`, as Python3's helpers are; `Expressions.tree(term)` reads a term with its
  helpers nested, and mbse-programs' checks and what each kind binds read them there (items 72, 78 and 79).
- **Constants**: a boolean, a number, a bigint or a string is TypeScript5's `literal`,
  `Expressions.TypeScript.TypeScript5.Literal`, refining the framework's and adding what its text encodes; `null` and a regular
  expression are TypeScript5's own `constant` ([CAP-233: literals of any value](CAP-233.md#as-built-mbse-expressions),
  As built; item 74).
- **Bodies absent**: a function's, a class's and an empty body's statements are not a property; an arrow's expression
  body is a term, absent for a block (item 75).
- **Printing**: `Text.ToText` ports mbse-programs' printer for expressions, patterns, types and JSX, byte-identical in
  both languages, by TypeScript's precedence; an absent body is printed `{}` (item 83).
- **Completeness as data**: `grammars/typescript5-estree.json` lists typescript-estree's 168 node types
  (@typescript-eslint/types 8.71.0, TypeScript 5.9.3), each mapped to a kind of `Term`, a branch of `Type` or
  `Pattern`, a helper, or listed as not an expression with its reason. DIA-23 checks it in both languages; DIA-21 checks
  the kinds, unions, literals, checks, bindings and evaluation, DIA-22 printing; the corpus's `typescript5` case holds
  every kind (items 84 and 85).
- **Evaluation stays shallow**, as decided ([CAP-226: complete expression dialects](CAP-226.md#decided), Decided): a
  literal alone is evaluated, by its role; every other kind, `constant` among them, is refused by name, "TypeScript5
  binaryexpression is not evaluated" (item 82). There is no translator, and no writer: terms are written through the
  builders (items 81 and 82).

## Decided

As the user decided (2026-11-03, in building stage 4,
[the proposal's Decided](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/dialects/README.md#decided)):
adopted, each the rule as stated, quoted where the wording matters.

- **A sublanguage's union holds the terms its positions hold, as branches.** Asked how a property holds a kind from
  two unions, where mbse-programs types it as a mix of a term kind and a sublanguage's kind (an arrow's parameter `x`
  is an `Identifier`, a term; `a.b = 1`, `x! = 1`, `(x as T) = 1` and `(x) = 1` have targets that are terms; a type's
  entity name is `Identifier | ThisExpression | TSQualifiedName`; a literal type holds `Literal | UnaryExpression |
  TemplateLiteral`; an import type an `ObjectExpression`), shown (a) a `term` branch in each sublanguage's union,
  holding `Term`, a level of wrapping on the wire; (b) one schema listed as a branch of several unions; (c) a union of
  its own for each mixed position (`Target`, `EntityName`); (d) the pattern kinds in `Term`, as typescript-estree's
  `Expression` has them, the user: "(b) as you recommended". `Pattern` lists, beside its own pattern kinds, the term
  kinds typescript-estree's `DestructuringPattern` allows (`identifier`, `memberexpression`) and, for an assignment's
  target, the expression kinds valid there (`tsnonnullexpression`, `tsasexpression`, `tssatisfiesexpression`,
  `tstypeassertion`, `parenthesizedexpression`); `Type` lists `identifier` and `thisexpression` for entity names, and
  what else a type position holds (`TSLiteralType.literal`'s terms, `TSImportType`'s), each directly, with no wrapping
  level; which terms are allowed where beyond the schema is a constraint. The rule for every dialect is
  [CAP-226: complete expression dialects](CAP-226.md#decided)'s.
- **Names that only declare stay `Identifier` terms.** Asked whether names that only declare (`TSMappedType.key`,
  `TSNamedTupleMember.label`, `TSTypeParameter.name`, `TSQualifiedName.right`) are a `str`, as Python3's are where
  mbse-programs has an `Identifier` node, or stay mbse-programs' `Identifier`, the user: "yes, stay `Identifier`
  terms".
- **Every dialect has a `Pattern` union for its binding targets.** Asked "is this done consistently across
  typescript5 and python3? can it be?", and shown (i) each dialect following its own grammar (`TypeScript5` a
  `Pattern` union, `Python3`'s targets holding its `Term`) or (ii) a uniform rule, the user: "(ii)".
  `Expressions.TypeScript.TypeScript5.Pattern` is that union for TypeScript5; the rule is
  [CAP-226: complete expression dialects](CAP-226.md#decided)'s, and Python3's union
  [CAP-227: the Python3 expression dialect](CAP-227.md#decided)'s.

## Decided by an agent, for review

Recorded in [the port's API, Settled in stage 4 (TypeScript5)](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-stage-4-typescript5-for-the-users-review),
items 70 to 85, not marked as the user's: each *proposed* until reviewed. Those most worth reviewing:

- **(mbse-expressions port, API 71)** **`Term` lists three pattern kinds**, `arraypattern`, `objectpattern` and
  `assignmentpattern`, the reverse of (b)'s direction (a pattern kind a branch of `Term`, not only a term a branch of
  `Pattern`): one `property` serves an object literal and an object pattern, its `value` holding `Term`, as
  typescript-estree's `Expression` lists the first two and its `Property.value` the third. So
  `ParenthesizedExpression.expression`, mbse-programs' `Expression | Pattern`, holds `Term`.
- **(mbse-expressions port, API 71)** **`error` and `missing` are `Term`'s alone**: invalid syntax within a type or a
  pattern has no branch yet. *Superseded* in stage 5 by API 101: every dialect's `Type` and `Pattern` list them
  ([CAP-229: the C expression dialect](CAP-229.md#decided-by-an-agent-for-review)).
- **(mbse-expressions port, API 72 and 79)** **Patterns and types within a kind are read as helpers**, `Terms.Part`s,
  as are the helpers a place does not mix with expressions; and the framework now reads a union of value objects,
  pairs among them, as a helper, where before it was an attribute. mbse-programs' checks apply within them, which the
  framework's validation does not read.
- **(mbse-expressions port, API 72)** **The helpers an expression's place mixes with expressions are `Term`'s kinds**
  (`spreadelement`, `elision`, `property`, `jsxemptyexpression`, `tsemptybodyfunctionexpression`), as Python3's
  `starred` is.
- **(mbse-expressions port, API 75)** **Bodies absent**: `functionexpression`, `classexpression` and
  `tsemptybodyfunctionexpression` have no body property; an arrow's optional `body` holds an expression body as a
  term, as Python3's lambda's ([CAP-227: the Python3 expression dialect](CAP-227.md#decided-by-an-agent-for-review),
  API 54), absent for a block; a printer writes an absent body `{}`, where mbse-programs writes the statements it
  relates.
- **(mbse-expressions port, API 83)** **An arrow's lone unconstrained type parameter printed `<T,>`**, as mbse-programs
  writes it for a `.tsx` file, so the text reads alike in both.
- **(mbse-expressions port, API 83)** **A number with no `text` printed as JavaScript's `String(number)`**, in Python
  too (`Text.number`), a bigint with its `n`, a string in its `quote` or `"` with JavaScript's escapes.
- **(mbse-expressions port, API 74)** **Literals divided by what a schema holds**, as Python3's: a number's value a
  float (binary64), a bigint's an int, so `n` is the value's type, not an attribute; `null` and a regular expression
  TypeScript5's `constant`, a regular expression not a kind of its own; `undefined` an `identifier`.
- **(mbse-expressions port, API 81)** **No writers**: TypeScript5's terms are written through the builders.
