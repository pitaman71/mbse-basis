# CAP-092: every construct of TypeScript's standards

*Implements* [FEA-008: expressive program models](../features/FEA-008.md).

## Blocked

The tree-sitter grammars lag the standards; until each language reads through its reference front end
([FEA-008: expressive program models](../features/FEA-008.md#design)), what they do not parse is not read.

### TypeScript: where tree-sitter-typescript 0.23.2 departs from TypeScript 5

As the user decided ([CAP-026: Python, TypeScript and C and C++ read as written](CAP-026.md#decided)), mbse-programs'
TypeScript5 parser lists every place where tree-sitter-typescript 0.23.2, the latest release, departs from TypeScript 5,
numbered, each with how it is handled
([its docstring](mbse:mbse-programs/python3/mbse/Programs/TypeScript5/Parse.py), "Where tree-sitter-typescript 0.23.2
departs from TypeScript 5"), and its suite asserts each (TS5PRS-13). What it cannot parse, a pre-pass rewrites, keeping
every other character's offset, and the converter puts back (attributes on `export ... from`, `import.defer(...)`, a
mapped type without a value type, `keyof readonly T[]`, an anonymous `export default function (...)` signature, ...);
what it misreads, a pre-pass rewrites or the converter corrects (`` f<T>`x` ``, `new a!.b()`, `new new a()()`, ...);
what it accepts and TypeScript rejects is kept as invalid syntax. What remains:

- `await`, `yield` and `interface` as names (`x = yield + 1`), read as tree-sitter reads them: how TypeScript reads them
  depends on the enclosing function, on whether the file is a module and on a compiler option, which the text does not
  show;
- `get` or `set` on a line of its own before a field (`get\nx = 1`), which TypeScript rejects and tree-sitter reads as
  two fields;
- an anonymous `export default function(a): T;` signature written without a space before its parameters, which still
  does not parse.

## Open questions

- **A parser that covers TypeScript 5.9.** tree-sitter-typescript 0.23.2 needs a pre-pass and corrections, and still
  departs in the three places listed above. typescript-estree is exact but exists only in JavaScript; a later
  tree-sitter-typescript would close the gap, and the converter is the only part that would change.
- **Precise error positions**, as for Python: see [CAP-038: every construct of Python's standards](CAP-038.md#open-questions).
- **A regular expression's body.** mbse-programs keeps a regular expression literal's pattern as text, with no kinds
  for it, so its reader leaves mbse-expressions' `TypeScript RegExp` unwritten until it parses one (as regexpp does),
  as reported in mbse-expressions' retrofit
  ([CAP-281: Python's, ECMAScript's and C++'s regular expressions as data](CAP-281.md)).
