# CAP-290: a service's store stacked, with no snapshot

*Implements* [FEA-006: persistence](../features/FEA-006.md), [FEA-045: a Python, FastAPI and DynamoDB service stack](../features/FEA-045.md).

mbse-rest's service serves a store given a store below, a database's, and persists by its journal alone: no snapshot
is taken or read, and a client is sent a store's schemas as the install transactions that made them. Its client
implements every method of the store interface. It is mbse-rest's part of [the stacked stores
proposal](../../proposals/STACKED-STORES.md), over a store kept in a database such as
[CAP-289: journals kept in DynamoDB](README.md#CAP-289)'s.

## Design

As built in mbse-rest 0.2.0.

### The service

```python
from mbse.Services.Rest import Service

api = Service.app(installs, below=None, seed=None, origins=())  # a FastAPI application
```

- `below`: the store below, an mbse-schemas store; one in memory where None. The service's store is a
  `Builders.Store` over it, which loads what it is asked for and writes each transaction through to it
  ([CAP-285: writes through, others' writes in](README.md#CAP-285)), so that the store below's journal is the only
  record. `Service.store_of(name)` makes one by name: `memory`, or `module:attribute`, called with no arguments
  (`mbse.Persistence.DynamoDB.Store:Store`, mbse-dynamodb's, configured by its own `MBSE_DYNAMODB_*`).
- `installs`: each runs in the store below and in the service's store, and is served to clients as the install
  transaction that made the schemas. `seed`, where given, runs after them as any transaction, where the store below is
  new (`Service.fresh`).
- The persistence plugin interface is gone: `MBSE_REST_STORE` names the store below, and `MBSE_REST_PLUGIN` and
  `MBSE_REST_SNAPSHOT_EVERY` are refused where set. `MBSE_REST_WINDOW` sets how many of the latest committed
  transactions the change feed keeps (10 000).

### The endpoints a store below needs

Beside the logical views ([CAP-012: logical view endpoints](CAP-012.md)):

| Method and path | Response |
|---|---|
| `GET /schemas` | the install transactions that made the store's schemas, in order ([CAP-002: named schema list](CAP-002.md)) |
| `POST /schemas` | an install transaction, run in the store below and the service's store, then served with the others; the installs |
| `POST /documents` | the document of the object at the path given, a one-transaction document ([CAP-128: graphs sent as one-transaction documents](CAP-128.md)), or null |
| `POST /transactions` | a transaction's expression, committed: `{"position": n, "effect": e}`, `e` the transaction as the store committed it, its record among it; refused (400) as its store refuses it; 503 where the store below fails, nothing written |
| `GET /changes?after=n&feed=id&wait=s` | each transaction the store committed after position `n`, in order, as its effect; long-polled; 410 for a position the feed no longer keeps, or another feed's |

### The client

`Store.ts` and `Store.py`, a `Builders.Store` whose store below is the service, in TypeScript and Python: it holds the
service's schemas from their install transactions, loads objects on demand, sends each transaction's changes, and
each install, to the service before it commits, and takes what the service committed of it into its own commit, its
followers given it then, once; each transaction it reads from the change feed it applies to the objects present in it,
as any store applies the store below's, its own changing nothing.

The choices made where this capability is silent are in [the stacked stores
proposal](../../proposals/STACKED-STORES.md#decided-by-an-agent-for-review), under mbse-rest 19.

## Decided

- **Provenance is recorded once, in the lowest store.** As the user decided (2026-11-14): in a stack of stores, a
  transaction's provenance ([CAP-134: transactions recorded with provenance](CAP-134.md)) is recorded once, in the
  lowest store.
