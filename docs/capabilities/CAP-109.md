# CAP-109: schemas as linked objects in modules

*Implements* [FEA-031: schemas as extensible data](../features/FEA-031.md). Index entry: [capabilities/README.md](README.md#CAP-109).

## As built: mbse-schemas

Met: mbse-schemas 0.26.3 (origin/main): phase 1 of the schema builders, then modules in the store, a store written as transactions, and the old builders' removal (The meta-schemas and their builders, as built, below).

### Status

How mbse-schemas' lists become relations and its meta-schemas become linked objects, so that the schema model is
built from the same constructs it offers: objects, relations and their entries. This is the plan of the work. What is
decided is under Decided, below, "The meta-schemas overhaul" and "Schema builders align
with their meta-schemas", which this does not restate. V1 to V5 are built, and so is phase 1 of the schema builders
(Plan): the meta-schemas as reference objects and relations, their builders and the store, in Python, which
[CAP-109: schemas as linked objects in modules](CAP-109.md#the-meta-schemas-and-their-builders-as-built) describes. The rest is
not. It changes the module format, so every repository that reads schemas adapts.

### Why

- **One construct for many.** A list, a dict, a map and a relation's entries are four ways to hold a variable number
  of things. `OfIndexed` holds the first three apart from relations, with its own builders, visitors, wire forms,
  validation and comparison, and every code generator renders both.
- **Meta-schemas without invented containers.** A module holds its schemas in `Schemas.Module.Entry` value objects,
  and a type is `Schemas.OfAny`, a union of the kinds and `named`: containers that exist only to hold schemas, which
  the schema model would not offer a modeler. As linked objects, schemas refer to each other by relations, as any
  model does.
- **Modules as relations.** A module defines its schemas by a relation, `Defines`, so that modules can nest, and a
  module's dictionary of schemas is entries like any other.

### V1, schema-level changes

- V1. **Schema-level changes** (built): `validate()` refuses `as_*` names; `Schemas.OfEntry`, with its meta-schema, a
`Schemas.OfEntry.Builder` building the `Schemas.OfEntry.Data` that `Schemas.OfRelation.Data.entry` holds; `OfNative` renamed `OfScalar`, written `{"scalar": {"format": ...,
"token": ...}}`; a link targets only reference objects, and a value object has adjacencies only to one-link
relations; `Schemas.OfSymbol`, a predicate's symbol and an entry's link; `Schemas.OfPredicate`, a module definition
of its own (`predicate`), registered by name. A link may
have a schema, which `validate()` checks and modules write; `Validators` does not yet check a link's target against
it.

#### The meta-schemas

Every meta-schema is a reference object schema named `Schemas.OfX` (`Schemas.X` until the store overhaul), each
store's own, reached by its path (`store.Schemas.OfObject`; [Store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md)), so
every schema object is a reference object (Decided: "we already decided
at least one time to make schema objects references. all of them.").

- **Kinds.** `Schemas.OfScalar`, `OfObject`, `OfUnion`, `OfIntersection`, `OfContainer` and `OfAny` are the schemas of
  values: only such a schema is anything's schema, refined, indexed, contained or allowed. `OfRelation`, `OfPredicate`
  and `OfModule` are not schemas of values ([VOC-026: schema](../VOCABULARY.md#VOC-026): schema, never "type"). Every kind has the properties `name` and `description`, each kind declaring
  them itself (its `parameters` are `Parametrics`', an extension installed before use, since Store overhaul 4m;
  [CAP-112: parameters modeled as schema data](CAP-112.md)): there are no abstract bases (`Schemas.Schema`, `Type` and `Typed` are gone since 0.17.0;
  [Store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md), Decided, 20 and 21).
- **Members.** `Schemas.OfProperty` and `OfSymbol` have a `description` and a `schema` (a union's branch and an
  intersection's part, `Member` objects until 0.18.0, are entries since); `OfParameter` has a `description` only: a parameter is a name, a symbol standing for
  what a use of the schema binds, named by its set's entry (`Parametrics.Defines`; `Schemas.HasParameter` until 4m). A member's name is not its own: it is the `name`
  property of the entry that links it to its owner (`HasProperty`, ...), since a member is named within its owner.
- **Other schema objects.** `OfAdjacency` (a `description`, and `me`), and `OfModule`, which defines schemas and
  modules (its `schemas`).
- **Properties hold values** (Decided: a property "has as schema which must be OfAny and that can hold scalars,
  containers, value objects, or any nesting thereof"): a kind's `name` and `description` (a scalar's `format` and
  `token` until 0.18.0), an object schema's `ref`, `pattern` and `singleton`, a union's or intersection's `flat`, a container's
  `layout`, a relation's `uniques` (a container of containers of names), a member's and an adjacency's `description`,
  an adjacency's `me`, and the `name` of a keyed relation's entry.
- **Names, by exception** (Decided, "I think we need to make an exception ..."): within a schema, its relation's links
  and properties are named by string, never referred to: an adjacency's `me` and a relation's `uniques` are properties
  holding names.
- **Every reference is a relation** of two links, `Schemas.<Relation>`, with an adjacency named at the end that
  declares it and an anonymous one at the end referred to ([CAP-167: schemas refined by other schemas](CAP-167.md#decided), "Refinement, identities and relations": an
  anonymous adjacency lets an object fill a link, with no member). Each kind declares the adjacencies of every relation
  it is at an end of (Store overhaul, Decided, 10), so each schema of values declares the anonymous
  adjacencies to it.

| Relation | Links: first, second (their kinds) | Named at the first | Constraint, as `unique` clauses state it |
|---|---|---|---|
| HasSchema (`Typing` until 0.19.0) | member (Property, Symbol; a Member until 0.18.0), schema (of values) | `.schema` | one: `unique(schema)`, the member determines its schema |
| Refines | refinement, refined (of values) | `OfObject.refines`, `OfContainer.refines` (`OfScalar.refines` until 0.18.0) | one |
| Indexing, Containing | container (Container), index / element (of values) | `OfContainer.index`, `OfContainer.element` | one |
| AnyOf | any (Any), schema (of values) | `OfAny.schemas` (`types` until 0.19.0) | none: open, a list in declaration order |
| Relating | adjacency (Adjacency), relation (Relation) | `OfAdjacency.relation` | one |
| HasParameter (until 4m: `Parametrics.HasParameters` and `Defines` since) | owner (every kind), parameter (Parameter); property `name` | `.parameters` | keyed: `unique(owner, name)`, `unique(parameter)` |
| HasProperty | owner (Object, Relation), property (Property); `name` | `OfObject.properties`, `OfRelation.properties` | keyed |
| HasAdjacency | owner (Object), adjacency (Adjacency); `name` | `OfObject.adjacencies` | keyed |
| HasBranch, HasPart | owner (Union / Intersection), schema (of values; `type` in 0.18.0); `name`, `description` (since 0.18.0; a Member object until then) | `OfUnion.branches`, `OfIntersection.parts` | named: `unique(owner, name)` |
| HasSymbol, HasLink | owner (Pattern / Relation), symbol / link (Symbol); `name` | `OfPattern.symbols`, `OfRelation.links` | keyed |
| HasVariable | owner (Pattern), variable (Variable); `name` | `OfPattern.variables` | keyed |
| Requiring | pattern, constraint (Expression) | `OfPattern.requires` | list |
| Matching, Resulting, Computing | expression (Expression / Collector), pattern; expression, schema; collector, expression | `pattern`, `result`, `computes` | one |
| Defines | module (Module), schema (every kind); `name` | `OfModule.schemas` | keyed |

Applications (`OfApply`, `Applying`, `HasArgument`, `Binding`, `ArgumentTerm`), terms (`Term`, `Form`, `Operands`),
widths (`BitWidth`, `ByteWidth`) and a predicate's `requires` (`Requires`) are gone since 0.17.0: they are
mbse-expressions' and mbse-patterns' (Schema extension, Decided, 5 to 7 in [FEA-024: expressions as data](../features/FEA-024.md#decided)).

"One" is `unique(second)`: the first end determines the second, so the adjacency holds at most one entry. "Keyed" is
`unique(owner, name)` and `unique(member)`, with the entry's `name`: the member determines its owner and its name, so a
member has one owner, and the owner and the name determine the member ([CAP-155: `unique` clauses on relation schemas govern relation cardinality](CAP-155.md)). The builders do
not yet refuse a member linked into a second owner; validation of the meta-schema relations will. A relation's links and properties are its own
(`Relation.links`, `Relation.properties`), with no entry schema between: `Schemas.OfEntry` has no meta-schema here.

#### The builders

Each `Builders.OfX.Builder` is a writable `Visitors.OfObject` over `Meta.X`, in [CAP-107: one visitor protocol reads and writes data](CAP-107.md)'s
form (Decided: "Schemas.OfX.Builder must implement Visitors.OfX"); read-only, it reads the data it is given and refuses
every write.

- **Members.** `osv.<propName>`, a `Visitors.OfProperty`, and `osv.<adjName>`, a `Visitors.OfAdjacency` with `insert`,
  `remove`, `as_iterable` and iteration over its entries; called with a `Specs.Callback`, each writes or visits through
  it and returns the builder. A container-valued property (a relation's `uniques`, or one of an extended schema) hands over a `Visitors.OfContainer`.
  An entry's link to its referent is a member, `env.<linkName>`: called, it links the referent given, or builds one
  through the callback, new, or the one the entry links, updated in place; read, it gives the referent, read-only.
  Members and an adjacency's relation are built through a link; a schema, a refined schema, an index and an element are
  linked as objects that exist (Decided: "a link to a
  type takes a schema that exists, not a callback that builds one").
- **Shorthands** ([CAP-107: one visitor protocol reads and writes data](CAP-107.md)): a property takes its value whole, of exactly its schema
  (`.ref(True)`, `.layout("dense")`); an adjacency takes an iterable, each item an entry, the object to link, or a
  callback taking `OfThem.Visitor`, which writes the entry's `name`, its link (`t.property(p)`), and the linked object's
  members (`t.schema([T])`). Where a relation allows one entry, the shorthand replaces it, and `insert` raises until it
  is removed; an entry linking a referent held is elided.
- **`as_*`.** `as_schema()` is `Meta.X`, and a member's `as_schema()` its property or adjacency in `Meta.X`;
  `as_properties` and `as_adjacencies` follow the meta-schema's order. (`as_identity` went in 4g of the store overhaul:
  a schema object's path is read by `Paths.of`, Object identity, Decided, 81 in [CAP-123: schema objects identified by path](CAP-123.md#decided).)
- **The data stores members its own way** (Decided: "the Data class can store `Schemas.OfObject.Data.properties` any
  way it wants"), and the builder adapts each adjacency to it: a dict of members by name, or a tuple in order; a field
  holding the referent. A keyed member's name is written to the member's data.
- **Derivation happens at finalization**, in `_finalize`: a refinement takes the `ref`, index and element of what it
  refines unless it is given them (a scalar's token too, until 0.18.0). No member's write has a side effect besides it (Decided: "shortcuts are
  refused"), so `.singleton(...)` no longer sets `ref`.
- **Finalizing** is `create()`, `clone()` or `update()`; none validate. A clone clones the
  members it owns, each with an identity of its own; an object schema's inherited members stay shared.

#### Building in a store

`Builders.Store` is the store, a store of proxies (`Proxies.OfStore`) that also holds schema objects, and the canonical
form of building is
`store.moduleName.[...moduleName].schemaName(cb)` (Decided: "This is the new canonical form for store-centric
building"): a callback creates, an object and a callback update, an object alone clones, and the call returns the
object. `store.Schemas.<Kind>(...)` builds a schema object, for `Scalar`, `Object`, `Union`, `Intersection`,
`Container`, `Any`, `Relation`, `Predicate`, `Property`, `Parameter`, `Symbol`, `Member`, `Adjacency` and `Module`;
any other registered name builds data, through the proxy builder.

- **The meta-schemas are in every store**, registered under their names, with the basic scalars (`Schemas.OfBool`,
  ...) and the mutation schemas.
- **A store links only what it holds.** A builder in a store refuses a link to a schema object the store does not
  hold, built outside any store or in another ([CAP-161: isolated stores, with no global registry](CAP-161.md)); a store's basic scalars are its own, linked by its
  paths, `store.Schemas.OfInt` and so on.
- **Identities.** Superseded in 4g of the store overhaul (Object identity, Decided, 80 and 81 in [CAP-123: schema objects identified by path](CAP-123.md#decided)): a schema object is
  held by its store and found by its path, a named schema's its name's parts from the root module, a member's its
  owner's then its name; one with no name of its own has none, and one schema object alone links it. A name is
  registered once, of any kind, and a module and a schema do not share a path.
- **Registration.** A named schema is registered under its name as it is created, so `store.crm.Person(...)` builds
  data right after `store.Schemas.OfObject(lambda o: o.name("crm.Person") ...)`; a renamed schema is registered again
  under its new name.

Built since: modules in the store, defining schemas and modules through `Defines`; a store written and read as a log
of mutations ([CAP-127: snapshots made of transactions](CAP-127.md), steps 1 and 2 of the serialization design), then, from store overhaul 4f, as two transactions; TypeScript; and the old builders, `Modules` and
`Stores.META` removed (Plan, phase 3). Not built yet: subsequent snapshots ([CAP-164: subsequent snapshots sent as transactions](CAP-164.md)), step 3.

### Phase 5 design: the draft's questions

The phase 5 draft (Plan; as Decided, below, "The meta-schemas overhaul" decides it) put eight points, each
with a question, for review. The schema builders answer most of them; each point says how, or that it is still open.

1. **What a schema is in memory.** Answered: `Schemas.OfX.Data` stays, bespoke, and its builder is the linked view of
   it, a visitor of its meta-schema that adapts the data's storage (Decided, "Schema builders align with their
   meta-schemas": "Schemas.OfX.{Builder, Data, Schema} are necessarily bespoke", "little to no effect on the
   `Schemas.OfX.Data` and `Schemas.OfX.Schema`"; The builders, above). The data are not proxies and need not implement
   the visitors ("Dataclasses do not have to implement Visitors or Readers"). How the linked form goes over the wire is
   point 7.
2. **Which elements are objects.** Answered: every schema of every kind and every member is a reference object, the
   members linked to their owner by relations (Decided, the same entry, which answers this question by name; The
   meta-schemas, above). As built, the member relations are `Has*`, a member's name is its entry's, and terms and
   arguments were reference objects too, until 0.17.0 removed them.
3. **The type links.** Built as separate relations, not one `Typing` with a `role`: `Typing`, `Indexing`,
   `Containing`, `Applying`, `AnyOf`, `Relating`, and `Refines`, `Binding`, `ArgumentTerm`, `Requires`, `BitWidth` and
   `ByteWidth` (The meta-schemas, above); the user named the referred end of `Typing` and `AnyOf` `schema` (Decided:
   `e2.schema(Contact)`). The other relations' names and splits were proposed in building and await the user's review.
   Since 0.17.0, `Applying`, `Binding`, `ArgumentTerm`, `Requires`, `BitWidth` and `ByteWidth` are gone (The
   meta-schemas, above).
4. **Anonymous adjacencies.** Answered and built, for any relation ([CAP-167: schemas refined by other schemas](CAP-167.md#decided), "Refinement, identities and relations";
   VAL-15); the meta-schemas declare one at every end referred to. A snapshot writing an entry under its named ends
   only, and `Reachable` following named adjacencies, wait for the wire format (point 7).
5. **Identities.** Superseded: since 4g of the store overhaul a schema object's identity is its path (Building in a
   store, above), a named schema's its name's parts from the root module, a module's its dotted name's; an unnamed
   schema object has none, and is written nested where it is linked, so a store's snapshot is reproducible without
   naming patterns.
6. **Modules and names.** The meta-relation is built, `Defines(module, name, schema)` (Decided: "a module is an object
   in a store, alongside schemas and data"); modules in the store and their nesting are built too;
   `root_module()` and qualified names are not. Still open: Open questions, "Resolving qualified names".
7. **The wire.** Answered by the serialization design ([CAP-127: snapshots made of transactions](CAP-127.md), [CAP-129: journals replayed by execution](CAP-129.md)): a store is written as a log of mutations, schemas
   included, through the meta-schemas (as transactions since store overhaul 4f); `Schemas.Module`'s old form, `Modules`, `Stores.META` and
   `Schemas.OfAny.Schema` are removed.
8. **Building a link's target inline.** Answered for types by the later decision: a link to a type takes a schema that
   exists, never a callback that builds one (Decided, "Schema builders align with their meta-schemas", a property's
   type). A link whose target is of one kind (a member, a term, an argument, an adjacency's relation) builds it
   through that kind's builder, so no schema is given; `.<link>.of(schema, spec)`, which Decided, "The meta-schemas
   overhaul" records, is not built.

### Schema builders as visitors

This follows Decided, below, "Schema builders align with their meta-schemas", and the
user's rules: every schema object is a reference object, and every reference is a relation. A property holds a value
of any kind: a scalar, a container, a value object, or any nesting of them.
It was proposed in building, for the user's review, and landed in Python (phase 1, docs/META_SCHEMAS.md, Plan) as
`Framework.Builders`, on top of `Schemas.OfX.Data`, which is unchanged; suite BLD runs it. The old builders were
removed in phase 3.

This is the record of the proposal and its work items. The design as built, the meta-schemas (their kinds, members,
relations and constraints), the builders and building in a store, is in
[CAP-109: schemas as linked objects in modules](CAP-109.md#the-meta-schemas-and-their-builders-as-built),
and what the user decided under Decided, below, "Schema builders align with their
meta-schemas".

### Work items

1. **Wire format.** Modules and Plain read and write schemas through these meta-schemas like any other model, as
   linked reference objects, and the conformance corpora are regenerated.
2. **Modules in the store.** A module is an object in the store, alongside schemas and data. The module named by a
   schema's prefix (`crm`) defines it through `Defines`.
3. **Cloning owned members.** Done: a clone clones the members it owns, with identities of their own; inherited ones
   stay shared.
4. **Landing.** The meta-schemas, builders and store move into `Schemas.py` and `Proxies.py`, with the shorthands in
   proxies too, mirrored in TypeScript. The call sites migrate to the canonical form.
5. **The meta-schemas in the store.** Done: each `Builders.Store` holds them, `Schemas.Module` aside, which every
   store holds in its old form until the wire format moves.

### The kinds

Every kind of schema element is a reference object of its kind's meta-schema, `Schemas.OfX`; each kind is defined in the item linked.

| Kind | An instance represents | Its schema represents | Its meta-schema represents |
|---|---|---|---|
| `OfScalar` ([CAP-156: the five basic scalars with boundless domains](CAP-156.md)) | a host value: bool, int, float, str or bytes | one of the five basic scalars | `Schemas.OfScalar`: a basic scalar |
| `OfObject` ([CAP-108: relations as scalable containers](CAP-108.md#value-objects-and-reference-objects)) | a value object, or a reference object | its properties and adjacencies, and whether it is a reference (`.ref()`) | `Schemas.OfObject`: an object schema |
| `OfUnion`, `OfIntersection` ([CAP-153: unions and intersections of named branches and parts](CAP-153.md)) | a value holding one named branch, or every named part | its branches or parts, by name | `Schemas.OfUnion`, `Schemas.OfIntersection` |
| `OfContainer` ([CAP-108: relations as scalable containers](CAP-108.md)) | elements by index | its index and element schemas, and its layout | `Schemas.OfContainer` |
| `OfAny` ([CAP-157: values of any schema, restricted or not](CAP-157.md)) | a value of any schema | the schemas it is restricted to, or none | `Schemas.OfAny` |
| `OfRelation`, `OfEntry`, `OfAdjacency` ([CAP-155: `unique` clauses on relation schemas govern relation cardinality](CAP-155.md)) | an entry linking reference objects, with its properties | its links, properties and `unique` clauses; an object's end of it | `Schemas.OfRelation`, `Schemas.OfEntry`, `Schemas.OfAdjacency` |
| `OfProperty` | a value held under a name | its name and its schema, an `OfAny` | `Schemas.OfProperty` |
| `OfParameter` ([CAP-112: parameters modeled as schema data](CAP-112.md)) | what is bound where its definition is referred to | its name | `Schemas.OfParameter` |
| `OfModule` | a namespace of schemas, nesting | its name and what it defines | `Schemas.OfModule` |

Each kind, property, adjacency, branch and part takes a `description`, documentation that no validation, conversion or comparison reads; what has a schema names it `schema` ([VOC-026: schema](../VOCABULARY.md#VOC-026)).

## Open questions

- **A value object held by an entry of a relation of two or more links, with adjacencies.** The entry is written under
  each object it links, so the value object is too, with one `$id`; reading would count the copies as one object, as
  it counts the entry once. Until then, only a one-link relation's entries may hold value objects with adjacencies.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(object identity 2)** Namespaces are modules: "Use Schemas.OfModule instead of Schemas.Namespace".
- **(object identity 73)** As the user decided (2026-10-20), on what needs a meta-schema: "Needs meta-schemas: Schemas.OfX, Schemas.HasY. Should not need meta-schemas: Mutations.OfX, Mutations.HasY,
  Locators.OfX, Locators.HasY": the locator schemas are ordinary schemas each store holds, as `Paths` and
  `Mutations` are, a locator is data, and their relations are ordinary relations (amending 64 in [CAP-137: patterns of symbols, variables and specs](CAP-137.md#decided)'s "an ordinary schema",
  which the first build of 4d made meta-schemas).
- **(object identity 97)** A kind union ("yes, a kind union"): a relation's link may have as its schema a union of reference object schemas,
  whose branches name the kinds (`Mutations.OfTerm`: `map`, `reduce`, `partition`, `update`, `upsert`). An entry's
  builder has a member per branch, and calling one (`w.update(cb)`) builds through the link an object of that
  branch's schema; validation accepts such a union as a link's schema and still refuses it as a property's; a linked
  object is of one of its branches' schemas. A generic rule, for any relation. With it, a data builder that builds a
  schema object through a link (a term's pattern) builds it with that meta-schema's builder, and
  `Schemas.OfPattern.spec` holds the recorded `Mutations.OfPattern` values, its builder member giving each callback the
  frame visitor (95 in [CAP-137: patterns of symbols, variables and specs](CAP-137.md#decided)).
- **(schema extension 3)** Unions: "continue using Unions for kinds for now and posit unification for the future" (of unions with branches
  and intersections).
- **(schema builders)** an int width reads as `Form("literal", {"value": 8})` ("leave it that way. forms may go away but not yet");
- **(schema builders)** "all schema objects are reference objects and all reference objects get an ID on creation";
- **(schema builders)** "`type` *never* needs to be provided on the symbol. that relationship is inferred from adjacencies";
- **(schema builders)** the exception for names within a schema: `me` and `uniques`;
- **(schema builders)** the canonical form of building in a store: a call with a callback creates, an object and a callback update, an
  object alone clones.

- **(framework design)** **A union's branches and an intersection's parts are relation entries** (0.18.0; [Store overhaul, Decided,
  4](../../../mbse-schemas/docs/proposals/store-overhaul/README.md#decided-here)), as the user decided, "`Meta.Member` -> relation meta-schemas":
  an entry of `Schemas.HasBranch` or `Schemas.HasPart` links the owner and the member's type, and carries its `name`
  and `description`; `Schemas.Member` and its builder are gone. The owner and the name determine the entry (its
  clause, since 0.26.4: [CAP-153: unions and intersections of named branches and parts](CAP-153.md#decided), "A union's branch names are unique"); a type may be linked by several. A branch has no identity of its own, and an unnamed type takes the first to link it's
  (`crm.Shape#branches.1`, SNP-02). Builders write them as before (`t.name("p").schema([A]).description("...")`).
- **(framework design)** **Schema builders align with their meta-schemas** (2026-10-14), as the user decided. The framework design required "To make
  schemas fully serializable, `Schemas.OfX.Builder` must implement `Visitors.OfX`", which the schema builders do not:
  their fluent clauses are a second API beside the meta-schemas, and 15 of them collide with the members the
  meta-schemas name. The user: "If the meta-schema does not align with visitor and proxy builder, the framework is
  broken"; "Visitor protocols should only name members `as_*`", and `as_*` names are refused as property and link
  names (V1). This comes next, before the dependents, since mbse-expressions "cannot be
  written correctly without it". How each collision is resolved is to be proposed for the user's review. The user
  then decided:
  - "Schemas.OfX.{Builder, Data, Schema} are necessarily bespoke"
  - "Schemas.OfX.Builder must implement Visitors.OfX"
  - "Visitors.OfX should support the usage examples in @VISITOR_PATTERN.md as faithfully as possible. This should have
    little to no effect on the `Schemas.OfX.Data` and `Schemas.OfX.Schema`."
  - "Dataclasses do not have to implement Visitors or Readers" (the user's correction of "... Visitors or Builders",
    which they "mistyped"); "the `properties` member of the dataclass can be a list of adjacency entries or whatever
    the underlying storage model is".
  - an object schema's `properties`, which the meta-schema lists as a container while the builder's member is an
    adjacency: "the Data class can store `Schemas.OfObject.Data.properties` any way it wants.
    `Schemas.OfObject.Builder` must be smart enough to wrap that adjacency in an a class that adapts your storage choice
    to the Visitors.OfAdjacency protocol. If that means `Schemas.OfObject.Data.properties` ends up being
    `List[Schemas.HasProperty.EntryData]` so be it".
  - "NO LONGER A GOAL: correct implementation of Schemas.OfX.{Builder, Data, Schema} will be a lot easier and cleaner
    if the bespoke Schemas.OfX.Data classes use members the same way that proxies do to store properties and relation
    adjacencies"
  - the form: "@worktrees/meta-schemas/mbse-schemas/docs/VISITOR_PATTERN.md is the correct form": an adjacency's

- **(framework design)** **The meta-schemas overhaul** ([Meta-schemas overhaul](CAP-109.md), which plans it; its collections superseded
  by Containers, above), as the user decided: of
  what the 8 to 11 Oct exploration (the `scalars` branch) learned, "definitely re-apply ASAP": "Dictionary of
  registered schemas lives as a relation on OfModule (possibly nestably)", "Meta-schemas use relations instead of
  hallucinated containers", and "Relations completely subsume collections : Adaptive storage for relation adjacencies
  as list, set, dict, etc. subsumes OfIndexed and requires 1-ary relations". The decisions the exploration recorded for
  these, as the user made them there, and those made since:
  - a relation may have one link, its entries holding values for their one owner, as the user decided ("eliminating
    OfIndexed necessitates (a)"): a list of plain values is a one-link relation whose entries hold a value, which no
    second object stands for;
  - "whether it is a set or a list depends entirely on the use of `unique`. Absent unique, it's an open relation": a
    relation with a `unique` clause holds a set of entries (an entry equal to one held is one entry), keyed from an
    end as `OfRelation.Data.key` gives; a relation without one is open, and from each end its entries are a list, in
    the order added, equal entries kept, its index their position ("index is implied"), stored nowhere. `.unique()`,
    naming nothing, makes a relation a set;
  - a list is declared inline in its adjacency ("you can use lambda builder shorthand within the adjacency so the
    relation doesn't need a separate decl"): `r.name("tags").me("owner").of(lambda rel:
    rel.links("owner").properties(text("value")))`. Code generators name such a relation where they need one;
  - "relation entries may be written on every named adjacency. If for any reason entries appear for the same relation
    on multiple lists, deserialization must dedup the entries according to `unique` if present or value if not": in a
    relation with a `unique` clause, entries equal by value are one; in an open relation, the k-th entry equal to a
    given one in one list is the k-th in another, so equal entries the lists repeat are not merged;
  - "make the adjacency handle it": iterating an adjacency gives its entries, and "adjacency offers projections for
    links and values", as amended: projection is a method, `project(name)` ("perhaps projection should be a method
    `.project(name)` rather than an attribute of the adjacency"), and lookup by key is `at(key)` (a `KeyError` for
    none), so no link or property name collides with anything; the adjacency member stays a tuple (a frozen array) of
    its entries, indexed by position, as "Adjacencies, as specified" (below) requires. An adjacency's key is the
    complement of the first `unique(S)` clause, in declaration order, whose complement holds the owner's link, less
    that link; with no such clause, or an empty key, there is no `at`;
  - `Paths` reads `unique(S)` backwards (`S` as the key), which the user confirmed is wrong; it reads keys as
    adjacencies do, and paths keep naming objects for transforms ("we can keep paths");
  - an adjacency's entries are written as an array of entries, sorted by their key where a `unique` clause gives one
    and its values are ordered, and in the order added otherwise; there are no compact forms (`["a", "b"]`, `{"k": v}`);
  - in codegen, "a relation whose properties boil down to a tuple of integer-like-things should be automatically
    promoted to an indexable. Similar cases may be inferred if unambiguous for map, dict, etc."; a promoted indexable
    iterates over entries, "to keep it simple";
  - "a value object held by an entry cannot have adjacencies" "should go": a one-link relation's entry is written once,
    with its owner, so a value object it holds is written once too, and may have adjacencies of its own;
  - extents go "completely away in favor of shape constraints", which the user confirmed for this overhaul ("agreed"):
    a bound on an index, a capacity or a tensor's shape is a constraint on the type of the property that keys the
    entries, not part of the schema; a parameter bound into such a constraint gives a tensor's shape ([CAP-112: parameters modeled as schema data](CAP-112.md));
  - the schema model's own lists need only a consistent order ("declaration order or key sorted order, as long as it's
    consistent"), and the user chose declaration order: a schema's member lists (parameters, properties, links,
    branches, parts, adjacencies, uniques, applications' arguments, and a form's attributes and arguments) are open
    relations, in declaration order, so that a schema read back equals the one built; only a module's schemas are
    keyed by name and sorted by it; reading refuses a member name listed twice;
  - `OfApply` binds by name only ("OfApply - bind by name only"), kept in this overhaul ("yes"): positional arguments
    go, `.arguments` takes them by name (Superseded by Parameters are names only (0.17.0): `OfApply` is mbse-expressions');
  - every schema is a reference object of its kind's meta-schema, and every reference to a schema is a link, through
    meta-relations (`Properties`, `Adjacencies`, `Applies`, `Parameters`, `Typing`, `Defines`, and a union's branches
    and an intersection's parts while those kinds remain); `Schemas.Module.Entry`, `Schemas.Module.Definition`,
    `Schemas.OfAny` (amended: its meta-schema only, `OfAny` returns, below), `Modules.reference` and `resolve`, and
    `Stores.META` go;
  - a link builds its target with a schema given as itself, `.<link>.of(schema, spec)`, never by name or inferred
    (the exploration's "builder notation for ambiguously typed link targets", which the meta-schemas need: a
    property's type is a link that schemas of several kinds may fill);
  - "any relation, even a meta-relation, is stored as adjacencies which can be added later"; the ends at which a
    schema is referred to are anonymous adjacencies (mbse-schemas' former TODO list, "Anonymous adjacencies": "it denotes the relation has no
    storage on the object. It merely denotes that this object may participate in a particular link `me` of the
    designated relation"), built in this overhaul for any relation, as the user agreed ("yes");
  - a module is an `OfModule` that defines schemas by `Defines(module, name, schema)`, and may define modules, so that
    modules nest; a schema defined through nested modules is named with their names "qualified with dots", as the user
    decided. A module is written as an object snapshot of the schemas it defines and the unnamed schemas they reach.
    "`Schemas.OfStore.root_module()` returns an instance of hierarchical `Schemas.OfModule` which registers schemas by
    module-qualified name" ("yes, add root_module");
  - Basic's operations on lists change with it, as the user decided: mbse-expressions' EXPRESSIONS.md, Resolved,
    "Basic's collection operations go now".

  What follows from these, as built (phase 4, `OfIndexed` removed): `Schemas.OfIndexed`, its meta-schema
  (`Schemas.Indexed`) and its extents; `Visitors.OfIndexed`, `OfItem` and `as_indexed`; `Proxies.OfIndexed.Map`;

  It excludes what that exploration built for the open-world and scalars overhaul, which is deferred: undeclared

  `OfScalar`. Nothing of it is built.
