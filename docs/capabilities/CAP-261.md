# CAP-261: layout driven by any journal entry

*Implements* [FEA-056: fungible diagramming keeps agents and humans in the loop](../features/FEA-056.md).

The layout engine follows a journal entry it is given, any transaction, by its resolved effect
([CAP-269: transactions resolved into their effects](README.md#CAP-269)): it sections the effect into the model's
mutations, anticipates what they remove, applies them, and calls the container layout and placement functions they
imply, so that a diagram's layout is a function of its journal alone, with no caller that knows the entry's kind, in
Python and TypeScript.

## Decided

The user's decisions:

- **Effects, not expressions**: the driver reads a transaction's resolved effect rather than decoding the transaction
  as written, which mixes mutations with queries ("Okay let's do option 2"); re-partitioning mutations and queries is
  later work, in [the priorities](../../proposals/PRIORITIES.md).
- **Grid settings are mutations**, and **every mutation is followed** ("yes to 1 then 2"): a grid's span, axis and
  cell rotation are written by mutations, which the driver follows like any other, and a shape made at the top level
  is placed in the diagram's grid ([CAP-280: the grid in the logical layout](CAP-280.md)).
- **Rejection is consistent**: an entry that violates a declared constraint "may be recorded and transmitted but any
  pair of recipients considering that transaction must consistently reject it". The driver, one recipient among many,
  rejects nothing by checks of its own.
- **Never a snapshot**: a diagram is stored, communicated and analyzed in journal form
  ([FEA-056: fungible diagramming keeps agents and humans in the loop](../features/FEA-056.md#decided)); the driver's store is fed by entries alone.

## Decided by an agent, for review

Where the user's decisions were silent, the simplest default consistent with them, each *proposed* until reviewed,
labeled with the repository and number it was decided under.

- **(mbse-diagrams 12)** **Names.** `Framework.Driver`: a `Driver`, one per layout store, whose `follow(effect)`
  returns the container layout's adjustments and the placement mutation it ran, and whose `placement(diagram)` gives a
  diagram's placement as followed.
- **(mbse-diagrams 12)** **Sectioning.** The driver reads the effect's plain form, the journal entry itself: each
  relation entry inserted or removed, by its relation and links, and each property set or cleared. The changes it acts
  on: containment entries and new members, a shape's grid changing; adjacency specs made, deleted (by their owner's
  key) or changed (their shapes or rotation); a grid made or its settings set; the diagram's defaults set.
- **(mbse-diagrams 12)** **Order.** Before the entry: each shape leaving its grid removed (`Container.removing`, and
  placement's), then each spec deleted or changed unjoined, where neither of its shapes is leaving, whose removal
  drops it. After: each grid made or set configured, then the defaults, then each shape added, in the order the entry
  names them, then each spec adjoined. Placement then follows what the entry and the adjustments touched, and the grids
  that shapes left.
- **(mbse-diagrams 12)** **What it cannot follow it leaves**, refusing nothing: a shape no grid holds is not placed,
  a spec between shapes with no cells is not taken, and an entry that changes nothing is no entry.
- **(mbse-diagrams 12)** **Placement where its schemas are**: a layout store without the physical layout's schemas is
  followed by the container layout alone.
- **(mbse-diagrams 12)** **The bench is two stores**, as a viewer is: each step's mutation runs in a source store,
  observed, and its effect is the journal entry a driver follows in the layout store the suites read; a replay is a
  fresh driver following the journal. Every placement value is as it was before the driver.

## Open questions

- **Deleting a shape** ([CAP-266: shapes deleted](README.md#CAP-266)) is not yet followed: an entry that removes a
  shape's owning entry is applied, and the layouts are not adjusted to it.
- **An entry naming an object a store does not hold** cannot be decoded there: the reference's schema is implied by
  its path, which through `Logical.Owns` many schemas share, so that mbse-schemas refuses to read it, before the driver
  sees it. Every such store refuses it alike, but as a failure to read rather than as the consistent rejection of an
  entry that violates a declared constraint.
