# CAP-128: graphs sent as one-transaction documents

*Implements* [FEA-030: transactions](../features/FEA-030.md). Index entry: [capabilities/README.md](README.md#CAP-128).

## As built: mbse-schemas

Met in mbse-schemas 0.22.0: the [store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md)'s 4f-3, a document written as one transaction, released as 0.22.0.

### Reachable documents

A Reachable document, the one graph a program sends without its store (an expression tree, a syntax tree), is one
transaction (51): its creations are the counted objects reachable from the root, the root first, numbered in
first-reference order (55 in [CAP-118: singletons, owned and counted objects](CAP-118.md#decided)), under a uid the caller gives; the owned objects and singletons the graph links are referred to by path, not
included, and resolved in the reader's store, reading aborting where one is missing. Reading the
document applies it as a transaction. A document that must carry owned objects too is a store's snapshot.

### Documents

A document of objects, `Plain.ToPlain(store).Reachable(schema, root, uid)` or `.OfObject`, is one transaction
(object identity 51 and 55, Decided, below; Store overhaul, 4f-3), written as a transaction on the wire is: one
upsert, keyed by the uid where the caller gives one, whose symbols are the objects the document holds and whose spec
gives what holds of each.

- The objects it holds: the root, `"0"`, and, for Reachable, the counted objects reachable from it through the objects
  it holds, each named by its number in the order the document meets them, through each object's named adjacencies in
  its schema's order and their entries in the order written. Each symbol names its schema by the schema's path; the
  schema must be one the store holds.
- Its spec: each object's properties that are set (`as_property`), then its named adjacencies' entries (`as_adjacency`,
  `insert`), each entry once, from the first object the document holds that holds it, sorted by the key its relation
  declares where every entry has each of the key's values and they are ordered. An entry's links refer to a symbol,
  `{"ref": {"symbol": "1"}}`, or, for an object the document does not hold (an owned object, a singleton, a schema
  object), its path, `{"ref": {"path": ...}}`. A counted object it does not hold cannot be referred to: writing such a
  document is refused. An owned root is written with the entry that owns it, so its owning adjacency must be named.
- Reading executes it, within the store's open transaction as a savepoint, else as a transaction of its own, and gives
  the object `"0"` binds; the root schema given must be one it is of. A document with no uid is keyed afresh by each
  read, so that each read makes new counted objects; one under a uid, read again while what it made is held, finds
  those (object identity 102 in [CAP-139: upserts find before they create](CAP-139.md#decided)). Its spec is checked against its symbols' schemas before it runs.

Reachability is its own visitor, `Reachable.of(root)`, which returns the root and every reference object reachable through adjacencies, value objects' included, in first-reference order; `Plain.ToPlain(store).Reachable` uses it.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(object identity 36)** (Superseded by 51.) The Reachable format lists its objects ("Objects as a list (Recommended)", 2026-10-17): `{"root": <path>,
  "objects": [{"path": <path>, "schema": "Contact", "properties": {...}}, ...]}`, a reference `{"$ref": <path>}`, with
  no `$schema`: the path finds the object, and its entry in `objects` names its schema, as `Exists` does.
- **(object identity 49)** A counted object on the wire ("fine"): a reference `{"$ref": {"tx": <uid>, "n": <index>}}` beside `{"$ref": <path>}`
  and a global name, its `Exists` carrying no id, its position among the transaction's creations being its index.
  (Superseded by 55: a counted object is numbered only within the document that writes it.)
  (A singleton needs no form of its own: "why do singletons need a separate syntax?" Its reference is its path, of
  no steps, `{"singleton": "crm.Book", "next": {"target": {}}}`.)
- **(object identity 51)** The Reachable format (superseding 36), "precisely": a Reachable document is one transaction, whose creations are
  the counted objects reachable from the root, the root first, under a uid the caller gives, references within it by
  index alone; the owned objects and singletons it links are referred to by path (a singleton's has no steps), not included, and
  resolved in the reader's store, reading aborting where one is missing. A document carrying owned objects too is a
  store's snapshot. Its uses: a graph sent across a process or language boundary (mbse-programs' Verilog reader),
  the corpora of expression and syntax trees (mbse-expressions, mbse-programs), round trips in tests, and copying a
  component into another store.
