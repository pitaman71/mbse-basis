# CAP-230: the C++ expression dialect

*Implements* [FEA-024: expressions as data](../features/FEA-024.md), [FEA-008: expressive program models](../features/FEA-008.md). *Relates to* [CAP-226: complete expression dialects](CAP-226.md), [CAP-229: the C expression dialect](CAP-229.md), [CAP-100: six languages' expression dialects](CAP-100.md), [CAP-036: complete kinds for Python, TypeScript and C and C++](CAP-036.md), [CAP-093: every construct of C's and C++'s standards](CAP-093.md), [CAP-091: Ccpp expressions bridged to C and C++ source](CAP-091.md).

## As built: mbse-expressions

Built in mbse-expressions' stage 5 of [the complete dialects](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/dialects/README.md#stages-proposed-once-decided)
(PR #19 and its follow-up, PR #23) and released in 0.8.0 (v0.8.0, at ff7c762), in both languages; every choice made
where the decisions were silent is in [the port's API, Settled in stage 5 (C and Cpp)](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-stage-5-c-and-cpp-for-the-users-review),
items 87 to 107, which hold the detail this section only bridges. `Cpp`, `Expressions.Cpp.Expressions` since the
namespace rename ([CAP-226: complete expression dialects](CAP-226.md#decided), Decided), is a complete dialect by
[CAP-226: complete expression dialects](CAP-226.md)'s rules: every expression of C++17, C++20 and C++23 (ISO/IEC
14882), in mbse-programs' Ccpp names and shapes; a lambda's body stays mbse-programs' statements, and C++26's pack
indexing, reflection, splices and contracts are outside it. With [CAP-229: the C expression dialect](CAP-229.md) it
replaces the Ccpp dialect ([CAP-100: six languages' expression dialects](CAP-100.md)). Reading C++'s every construct
is [CAP-093: every construct of C's and C++'s standards](CAP-093.md)'s, and a bridge to C++ source
[CAP-091: Ccpp expressions bridged to C and C++ source](CAP-091.md)'s.

- **The kinds**: `Expressions.Cpp.Expressions.Term` has 39 branches, each a value object
  `Expressions.Cpp.Expressions.<Name>` with mbse-programs' properties in source order, tagged by its name lowercased
  (`lambdaexpression`, `namedcastexpression`): C's but `variable`, `genericselection` and
  `compoundliteralexpression`, and `userdefinedliteral`, `idexpression`, `thisexpression`, `lambdaexpression`,
  `foldexpression`, `requiresexpression`, `functionalcastexpression`, `namedcastexpression`, `typeidexpression`,
  `awaitexpression`, `sizeofpackexpression`, `noexceptexpression`, `newexpression`, `deleteexpression`,
  `throwexpression`, `yieldexpression` and `packexpansion` (item 87). C++ defines its own copy of each kind it shares
  with C, holding its own terms (item 89). Each kind records as data the standards that have it, C++17, C++20 and
  C++23 (`requiresexpression`, `awaitexpression`, `yieldexpression` and `designatedinitializer` C++20's and C++23's)
  (item 95): since 0.9.0, as the editions C++'s `define` covers, ISO/IEC 14882:2017, 2020 and 2024
  ([CAP-268: standards as tagged data](CAP-268.md)).
- **Names**: every name used as an expression is an `idexpression` holding C++'s `Name` union (`identifier`,
  `qualifiedname`, `templateid`, `operatorname`, `conversionname`, `literaloperatorname`, `destructorname`, and
  `decltypespecifier` where a name's place holds it), so `Term` has no `variable` (Decided, below); every other name is
  a name node wherever mbse-programs has one (item 88). A reference's name may be a name node: an identifier's
  spelling is its name, and any other name (`std::cout`, `f<int>`) has none, resolved by the scope alone, the terms it
  holds checked in scope (item 107).
- **The sublanguages and helpers**: `Type`, a type name (`typeid`) or invalid syntax, which `Term` lists too;
  `Pattern`, `identifier` or invalid syntax, held by an init capture's name, the one target a C++ expression binds
  (Decided, below); the helpers' unions named after mbse-programs' categories (`Name`, `Capture`, `Requirement`,
  `Designator`, `Initializer`, `Specifier`, `Declarator`, `Parameter`, `TemplateParameter`, `ExceptionSpecification`,
  `AttributeSpecifier`), read by the framework as `Terms.Part`s (item 89). What each kind binds: a lambda's parameters
  and init captures, and a requires expression's parameters, within it (item 91).
- **Constants**: `Expressions.Cpp.Expressions.Literal` refines the framework's
  ([CAP-167: schemas refined by other schemas](CAP-167.md)) and adds what its text encodes, as C's does, with a raw
  string's `raw` and `delimiter` ([CAP-233: literals of any value](CAP-233.md)); `userdefinedliteral` holds a
  `literal` and its `suffix` (`10_km`); C++'s `constant` holds `nullptr` (item 90).
- **Bodies**: a lambda's is not held, and is printed `{}` (item 93).
- **Writers**: C's, derived, writing an identifier used as an expression as an `idexpression` (item 94).
- **Printing**: `Text.ToText` ports mbse-programs' printer, byte-identical in both languages, by C++'s precedence
  (`<=>`, `.*`, `->*`), a raw string in its delimiter's parentheses (item 97); `FromText` is mbse-programs'
  ([CAP-226: complete expression dialects](CAP-226.md#decided), Decided).
- **Completeness as data**: `grammars/cpp-tree-sitter.json` maps each of tree-sitter-cpp 0.23.4's 206 named node
  types to a kind, a branch of `Type` or a helper, or lists it as not an expression with its reason. DIA-26 checks it in
  both languages, DIA-24 the kinds, names, scopes and evaluation, DIA-25 printing; the corpus's `cpp` case holds every
  kind (items 100, 103 and 107).
- **Domains as data** (0.9.0): C++'s `define` writes the types C++'s standard fixes, `bool`, `int8_t` to `int64_t`,
  `uint8_t` to `uint64_t`, C++23's `std::float16_t` to `std::float128_t`, `std::bfloat16_t` (an `ieee754` domain with
  no `format`: `width` 16, `radix` 2, `precision` 8, `emax` 127; Decided, M) and its own `nullptr_t`, as stored domains
  ([CAP-097: value domains of published standards](CAP-097.md#value-domains)). C++ has no `_FloatN` or decimal types;
  every other type it reads is its holder's ABI's, which C++ shares with C
  ([CAP-267: C and C++ terms read under the ABI their holder names](CAP-267.md)). A C++ literal is typed by C++'s names:
  `1.0f16` is a `std::float16_t`, `1.0bf16` a `std::bfloat16_t`, and `1.0df`, which C++ does not write, has no stored
  type.
- **Evaluation stays shallow**, as decided ([CAP-226: complete expression dialects](CAP-226.md#decided), Decided):
  C++'s interpreter is C's over its dialect, with `idexpression` in place of `variable`, a character literal a `char`;
  every other kind, and a name that is not an identifier ("Cpp idexpression of a name that is not an identifier is not
  evaluated"), is refused by name (item 96). Patterns <-> Cpp shares Patterns <-> C's rule set, a Patterns `variable`
  C++'s `idexpression` of the identifier (item 98).

## Decided

As the user decided (2026-11-04, following up stage 5,
[the proposal's Decided](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/dialects/README.md#decided)):
adopted, each the rule as stated, quoted where the wording matters.

- **C++ writes a name used as an expression only as `idexpression`.** Shown "C++ uses only `idexpression`,
  mbse-programs' one kind, so `variable` isn't listed in C++'s union... C keeps `variable`, since C's grammar has a
  plain identifier expression", the user: "1, 2: confirmed". `x` is an `idexpression` of the identifier `x`,
  `std::cout` of a qualified name, as mbse-programs and tree-sitter-cpp have it.
- **C++'s init capture holds its name as a `Pattern`.** Shown "C++'s init capture holds its name as a `Pattern`,
  which becomes `Identifier` plus the invalid-syntax kinds", the user: "3 = (a) is fine". An init capture's `name`
  (`[n = 1]`) holds `Expressions.Cpp.Expressions.Pattern`, the binding target "Every dialect has a `Pattern` union"
  asks for ([CAP-226: complete expression dialects](CAP-226.md#decided)).
- **The writers stay, for code generation**: "4. for codegen, we keep the writers separately because they emit code
  not just wire format for the model" ([CAP-229: the C expression dialect](CAP-229.md#decided)).

- **M: `std::bfloat16_t` is an IEEE 754 domain** (2026-11-10, on mbse-expressions' domains as data, stage 3's design,
  approved as a whole with "yes"): `std::bfloat16_t` is defined by C++23 (ISO/IEC 14882:2023, the extended
  floating-point types, from P1467) in IEEE 754's parameters: radix 2, 16 bits, precision 8, emax 127. So the C++
  dialect stores it as a domain of IEEE 754's kind with those parameters; parameters a standard does not define are
  allowed, under [PRI-012: model published standards](../PRINCIPLES.md#PRI-012) as corrected ("adding extra parameters
  does not count as a "second order invention""). Asked along the way, the user: "what is the standad that defines
  bfloat16? _Float32x?". The answer given: C++23 defines `std::bfloat16_t`, in those parameters; C23's Annex H defines
  `_Float32x`, leaving its format to the implementation, which under an ABI that ABI fixes
  ([CAP-267: C and C++ terms read under the ABI their holder names](CAP-267.md#decided)).

## Decided by an agent, for review

Recorded in [the port's API, Settled in stage 5 (C and Cpp)](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-stage-5-c-and-cpp-for-the-users-review),
items 87 to 107, not marked as the user's: each *proposed* until reviewed. Beside those
[CAP-229: the C expression dialect](CAP-229.md#decided-by-an-agent-for-review) names, the ones most worth reviewing:

- **(mbse-expressions port, API 98)** **C++'s character and quoted string translated by what they are**: a string
  written with its quote (`"s"`) is Patterns' string, since a quote is not C++'s spelling; a character (`'a'`, a
  `char`), a literal with a suffix or a prefix, and a cast have no Patterns counterpart and are refused by name.
- **(mbse-expressions 30, domains as data, stage 3's design)** **C++'s library typedefs keep C's names**: a type C++'s
  library declares under a name C's library also declares (`<stdint.h>` and `<stddef.h>`, and `<cstdint>` and
  `<cstddef>` in `std`) keeps that name, `int32_t`, `size_t`, `nullptr_t`, so that one ABI dialect names each type once
  for both languages, and C++'s casts already write them so; a type only C++'s library declares is named as C++ does,
  in `std` (`std::float16_t`, `std::bfloat16_t`).
- **(mbse-expressions port, API 107)** **A reference's name may be a name node**: `Terms.name_of` and
  `Terms.reference_name` read an identifier's spelling as the name, and any other name node as none; validation
  requires a named lexical reference bound, and checks the terms a name node holds.
