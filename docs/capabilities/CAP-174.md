# CAP-174: a spec that clears then inserts holds when re-run

*Implements* [FEA-027: mutations as queries](../features/FEA-027.md). Index entry: [capabilities/README.md](README.md#CAP-174). *Relates to* [CAP-140: entries removed through a spec](CAP-140.md).

## Design

Not built. As [CAP-140: entries removed through a spec](CAP-140.md) built it (the [store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md)'s 4j), a spec's verbs apply in the
order it gives them, each where it does not hold, and a spec holds of a frame when what it removes is absent. A spec
that clears an adjacency and then inserts X into it (`a.clear().insert(...)`) so never holds while X is present: each
run removes X and inserts it again. The store ends as it was, but the run writes.

## Open questions

- **Whether `clear` holds where the adjacency holds only what the same spec inserts after it**, so that the spec
  holds and a re-run writes nothing. Found while building 4j, for the user to decide.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **A spec that clears then inserts is tech debt** (2026-10-22, approving 4j's semantics of `remove` and `clear`): "note as
  tech debt". The semantics stand as built; this capability is that tech debt.
