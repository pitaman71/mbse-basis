# CAP-278: C's and C++'s type names and preprocessor directives as data

*Implements* [FEA-024: expressions as data](../features/FEA-024.md), [FEA-008: expressive program models](../features/FEA-008.md). *Relates to* [CAP-229: the C expression dialect](CAP-229.md), [CAP-230: the C++ expression dialect](CAP-230.md), [CAP-226: complete expression dialects](CAP-226.md), [CAP-267: C and C++ terms read under the ABI their holder names](CAP-267.md).

## As built: mbse-expressions

Built in mbse-expressions' retrofit of [the complete dialects](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/dialects/README.md#stages) (its *Retrofit's design*, C and C++), for 0.10.0,
in both languages, by stage 6's decisions: types and preprocessors are dialects, "the preprocessor is a dialect per
family (C's, shared by C and C++ as each standard defines it ...)", and a struct's or an enumeration's members, where
mbse-programs models them as nodes, are data ([CAP-226: complete expression dialects](CAP-226.md#decided)). The choices
made where the design was silent are [the port's API, Settled in the retrofit](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-the-retrofit-for-the-users-review), items 246 to 260.

- **`C Types`** and **`Cpp Types`** (`Expressions.C.Types`, `Expressions.Cpp.Types`): C's and C++'s `Type` unions,
  `typeid`, moved into dialects of their own, with C's type-name helpers; an enumeration's enumerators are data, its
  `EnumSpecifier` keeping `body` and gaining `enumerators` and `trailing_comma`. A cast's, a compound literal's and a
  generic association's type, and C++'s every type position, hold their `Term`; each holder names its ABI, as C's does.
- **`C Preprocessor`** (`Expressions.C.Preprocessor`): mbse-programs' directives, `#include`, `#define`, `#if`,
  `#ifdef`, `#elif`, `#elifdef`, `#else` and the others, `defined(name)` in C's and C++'s conditions, and comments;
  one dialect both read, recording C's and C++'s six editions. A condition's macros' names are bound within it.
- **Each** records its editions as data, prints through C's family printer, is checked complete against tree-sitter-c's
  and tree-sitter-cpp's node types kept as data (DIA-26), and is refused by evaluation by its own name ("C Types
  typeid is not evaluated"); a cast reads its type rather than evaluate it.
- **Tests**: the suites CTY, XTY and CPD, nine cases each; DIA-24, DIA-26, FRM-01, FRM-02, FRM-11, FRM-13 and CONF-04;
  the corpus cases `c_types`, `cpp_types` and `c_preprocessor`.

## Decided by an agent, for review

Recorded in [the port's API, Settled in the retrofit](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-the-retrofit-for-the-users-review), not marked as the user's: each *proposed* until reviewed.
Two differ from the design and are the ones most worth reviewing:

- **(mbse-expressions, retrofit, API 247)** **An enumerator is a kind**, of C Types and of Cpp Types, not a helper of a
  union `EnumeratorItem`, and a directive's items hold `Expressions.Framework.Term`, not a union of unions `Item`: the
  framework reads a helper union one level deep, so the design's unions could not hold the directives among an
  enumeration's items.
- **(mbse-expressions, retrofit, API 249)** **A type's position is a term slot**: a cast's type is its form's argument
  0, a generic association a pair, so a type's problems are labelled ("type: invalid syntax 'int int'").
- **(mbse-expressions, retrofit, API 246)** The family's shared reading in an internal module, `C.Expressions.Kinds`,
  breaking TypeScript's import cycle between C Preprocessor and C++.
- **(mbse-expressions, retrofit, API 250, 251)** C's type-name helpers move to C Types and C++'s stay; editions list
  their dialect's own kinds only.
- **(mbse-expressions, retrofit, API 252 to 255)** The preprocessor's shape and checks, what it binds (a condition's
  macros), its six editions, and one printer for the family.
