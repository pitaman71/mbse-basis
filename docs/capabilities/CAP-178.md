# CAP-178: an object's provenance read through its own named adjacencies

*Implements* [FEA-030: transactions](../features/FEA-030.md). Index entry: [capabilities/README.md](README.md#CAP-178). *Relates to* [CAP-134: transactions recorded with provenance](CAP-134.md), [CAP-020: provenance display](CAP-020.md).

## As built: mbse-schemas and mbse-rest

Not met. `Provenance.extend` gives each schema with a history anonymous adjacencies to `Provenance.CreatedBy` and
`Provenance.ModifiedBy` ([CAP-134: transactions recorded with provenance](CAP-134.md#the-model)), so that an object has no member for its records and they are
read from the records' side. mbse-rest's detail and adjacency views so find an object's provenance by a map over
every `Provenance.OfTransaction` record (`Views._history`): fine for a demo, slow for a long history.

## Design

The recorded object's schema has named adjacencies to `CreatedBy` and `ModifiedBy`, and an object's records are
read from its own side, through them, as any adjacency is.

## Open questions

- **What the adjacencies are named**, and whether `Provenance.extend` names them or the app does.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **Provenance adjacencies are named on the recorded object**: "it makes no sense at all for CreatedBy and MotifiedBy
  to be anonymous on the target object side".
