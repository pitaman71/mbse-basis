# CAP-180: ISO/IEC 11404 datatypes replace the Basic expression dialect

*Implements* [FEA-024: expressions as data](../features/FEA-024.md). *Relates to* [CAP-095: Basic terms as data](CAP-095.md), [CAP-097: value domains of published standards](CAP-097.md).

## As built: mbse-expressions

Built in part by mbse-expressions' domains as data, stage 1 (PR #27), in both languages, and released in 0.9.0: the
datatypes. The choices made where the decisions were silent are [the port's API, Settled in domains as data's stage
1](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-domains-as-datas-stage-1-for-the-users-review),
items 112, 113 and 123.

- **The ISO/IEC 11404 dialect**, `Expressions.ISOIEC11404.Expressions` (Python `mbse.Expressions.ISOIEC11404.Expressions`,
  TypeScript `@mbse/expressions/ISOIEC11404/Expressions`), a standard dialect with no terms
  ([CAP-097: value domains of published standards](CAP-097.md#value-domains)), holds 11404's kinds, each named as
  11404 declares it, its tag and its schema alike (`Expressions.ISOIEC11404.Expressions.OfBoolean`, ...): `boolean`,
  `integer` (with `width`, `signed` and `overflow`, which 11404 does not define), `modulo` (`modulus`), `bitstring`,
  `octet`, `octetstring` and `state`, and `packed`, which 11404 does not name, with `Packs`. Its `define` writes the
  domains `boolean`, `integer`, `octetstring`, `octet` and `modulo(256)`, whose schema is
  `Expressions.ISOIEC11404.Expressions.modulo_256`, and covers ISO/IEC 11404:2007
  ([CAP-268: standards as tagged data](CAP-268.md)).
- **Basic's datatypes left it**: Patterns, as Basic is named since the complete dialects, holds no kind and no domain;
  its eight domains are the standard dialects' (`bool`, `int` and `bytes` are 11404's `boolean`, `integer` and
  `octetstring`; `uint8` is 11404's `octet`, for codes, and `modulo(256)`, for wrapping arithmetic; `float` and
  `binary32` IEEE 754's `binary64` and `binary32`; `std_logic` IEEE 1164's; `str` Unicode's `string`), and Patterns
  uses them as any dialect does.
- **Not built**: Patterns' terms and operations are not replaced, and 11404's datatype operations (Equal, InOrder,
  Add, Multiply, Negate, ...) are not modeled; 11404's ordered `enumerated` (§8.1.3) is added only when a dialect first
  needs an order (Decided, "`state` is the generic enumeration").

## Design

Deferred, as the user wrote it, from the experimental coding of 8 to 11 October to a future open-world and
scalars overhaul:

- "ISO/IEC 11404 replaces Basic expression dialect"
- "Datatype operations are modeled, not coded"

## Decided

As the user decided, on mbse-expressions' domains as data: adopted, each the rule as stated, quoted as given.

- **E. An ISO/IEC 11404 dialect, and Patterns holds no kinds or domains** (2026-11-06, on stage 1's design; E to H each
  approved "yes", as the coordinating agent put it). To the design's "don't invent a standard where none exists" (its
  (a)) the user answered that it is at odds with its (b): ISO/IEC 11404 is a published standard, which has the six
  kinds (integer, boolean, bit string, octet string, enumerated, packing), so by
  [PRI-012: model published standards](../PRINCIPLES.md#PRI-012) they are its dialect's, as this capability has it
  ("ISO/IEC 11404 replaces Basic expression dialect", "Datatype operations are modeled, not coded"). In stage 1 the
  ISO/IEC 11404 dialect holds those six kinds beside the IEEE 754, IEEE 1164 and Unicode dialects; replacing Patterns
  entirely, and modeling 11404's operations, stay this capability's. (Their names, *revised* 2026-11-09: the kinds are
  named as 11404 declares them, `enumerated` read as 11404's unordered `state`, and packing is not an 11404 datatype;
  and two kinds are added, 11404's `octet` and `modulo`; both below.) And: "I am sensing repeated suggestions to
  consolidate things under `Patterns` and I don't know where that comes from". Where it came from: Patterns was Basic,
  which held the scalar kinds and domains, never moved out when it was renamed for its quantifiers over `OfPattern`;
  the proposal's question 4 recommended "Patterns' `integer` kind, shared", writing that inheritance into a decision
  ([CAP-097: value domains of published standards](CAP-097.md#decided), "Kinds shared per standard"); and the package
  root re-exported Patterns' `Domains`, `Evaluators`, `Expressions` and `Partials` as "the neutral form of every
  constraint" (no longer: [CAP-098: dialects over one framework](CAP-098.md#decided), "The package root exports
  `Framework` alone"). So Patterns' eight domains and its kinds move to the standard dialects, and Patterns uses their
  domains as any dialect does.
- **Names are the standards' own** (2026-11-09, on stage 1's review;
  [CAP-097: value domains of published standards](CAP-097.md#decided)): ISO/IEC 11404's are its declarations'
  lowercase names. The kinds `bool`, `bits`, `bytes` and `enum` are `boolean`, `bitstring`, `octetstring` and `state`
  (`OfBoolean`, `OfBitstring`, `OfOctetstring`, `OfState`); `integer` was already 11404's. Where the standard was
  silent: `enum` is 11404's `state`, and `packed` keeps its name, each decided below.
- **`state` is the generic enumeration** (2026-11-09). The agent's choice, for review, of 11404's `state` (§8.1.2: "a
  finite number of distinguished but unordered values", its one operation Equal) for the unordered `enum` kind is
  accepted. Told that 11404's `enumerated` (§8.1.3) is its ordered counterpart, to be added when a dialect first needs
  an order (SystemVerilog's `.first()`, `.next()` and `.prev()`), the user said: "yes, well, then that is a generic
  enough enum, eh?". So `state` is the generic enumeration, and `enumerated` is added only when a dialect needs an
  order.
- **`packed` keeps its name** (2026-11-09), which 11404 does not define: the agent's choice, for review, is decided,
  as the user put it, "packed and packs does not go" (An enumeration is not an integer, below).
- **`uint8` split by 11404's own definitions** (2026-11-09). Stage 1 first renamed the domain `uint8` `octet`, from
  11404's "`type octet = new integer range (0..255)`" (§10.1.7). But `uint8` was an integer of width 8, unsigned,
  wrapping on overflow, and that is not 11404's `octet`: "Each value of datatype Octet is a code", its properties
  "ordered, bounded, exact, non-numeric, finite", its operations only "(Equal, InOrder) from Integer", so it has no
  arithmetic. It is 11404's `modulo` (§10.1.2): "`type modulo (modulus: integer) = new integer range(0..modulus)
  excluding(modulus)`", "ordered, exact, numeric", its operations "Equal, InOrder from Integer; Add, Multiply,
  Negate", Add and Multiply giving the integer result's remainder by the modulus: wrapping arithmetic. The user's rule
  settles it, "yes, adopt names the standard uses for datatypes it defines (is this even a question?)", as the user
  confirmed (2026-11-09): "didn't you already resolve that?". So, each as 11404 defines it:
  - **`octet`** is a kind of its own (`OfOctet`): codes 0 to 255, ordered, with no arithmetic and no `overflow`; its
    one property is `ordered`. ISO/IEC 11404's `define` writes the domain `octet` of it.
  - **`modulo`** is a kind (`OfModulo`), with 11404's parameter `modulus` and the inferred `least`, `greatest` and
    `ordered`; the `define` writes `modulo(256)`, 8-bit wrapping arithmetic, beside `octet`.
  - **Each use of `uint8`.** Where a value is a code, it is `octet`: the representation a packed domain packs a state
    into. Where it is arithmetic, it is `modulo(256)`. C's `uint8_t` is C's, and stays.
  - **`integer` keeps `width`, `signed` and `overflow`**, as decided (below).
- **The integer kind keeps its parameters** (2026-11-09): asked whether 11404's `integer` may carry `width`, `signed`
  and `overflow`, which 11404 does not define, against [PRI-012: model published standards](../PRINCIPLES.md#PRI-012)'s
  "with only the parameters a standard defines": "PRI-012 is overstated, adding extra parameters does not count as a
  "second order invention" IMO". They stay; PRI-012's wording is corrected to match.
- **An enumeration is not an integer** (2026-11-09): "models should not conflate integers and enums as C does". So
  `packed` and `Packs` stay, keeping an enumeration apart from the integer that represents it; nothing is removed.
  ~~For stage 3: C's and C++'s enums are to be stored as enumerations packed into their integer types, not as integer
  domains.~~ (*Superseded* 2026-11-10 for stage 3 by the scope of stored domains: an enum a program declares gets no
  stored domain; [CAP-097: value domains of published standards](CAP-097.md#decided). The rule stands: where an
  enumeration is stored, it is not an integer.)

## Decided by an agent, for review

Recorded in [the port's API, Settled in domains as data's stage 1](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-domains-as-datas-stage-1-for-the-users-review),
items 112, 113 and 123, not marked as the user's: each *proposed* until reviewed.

- **(mbse-expressions 27, domains as data, API 123)** **The domain's name, `modulo(256)`**, is 11404's own notation,
  its type generator applied to its modulus, as a dialect's `Defines` entry can hold it. Its schema's name cannot:
  mbse-schemas' names are dotted identifiers. So the schema, and the define's symbol for it, spell it `modulo_256`
  (`Expressions.ISOIEC11404.Expressions.modulo_256`).
- **(mbse-expressions 27, domains as data, API 123)** **Which `uint8` is which**: a packed domain's representation (the
  corpus's `domains` case, EXP-06, DOM-03, DOM-05) is `octet`; arithmetic (EXP-13, DOM-05, DOM-17, tutorial 7's T07.5
  and tutorial 8's introduction) is `modulo(256)`.
