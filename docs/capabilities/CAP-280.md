# CAP-280: the grid in the logical layout

*Implements* [FEA-056: fungible diagramming keeps agents and humans in the loop](../features/FEA-056.md).

A container, a shape or the diagram, owns at most one grid, through `Logical.Owns` as `grid`, and containment links a
child to that grid, so that a child is contained only by a grid and a container has only one. A grid's span, axis and
cell rotation are its own properties, written by mutations. The container layout takes them, rearranges a grid's cells
when they change, and owns each cell through `HasCells`, keyed by its row and column, in Python and TypeScript.

## Decided

The user's decisions (2026-11-11), on the grid model:

- **A grid is on an ownership path**: "A container owns exactly one grid which contains the children." A child
  contained by no grid, or a container with two, cannot be written, so that neither needs a check that could reject a
  transaction.
- **Grids and cells are reference objects, cells owned through `HasCells`**: "The grid and cells should both be a
  reference object. Cells are linked to it (and owned by it) via a HasCells relation. The coordinate of the cell should
  be a property or properties on the relation as well as in the cell." `Container.HasCells` carries `row` and
  `column`, which key a cell among its grid's; `Container.OfCell` holds them too.
- **A container owns its grid through `Logical.Owns`**: "1 yes, `Logical.Owns`", rather than a relation of its own.
- **The module split**: "2 yes, that's fine". `Logical` defines the grid, `Logical.OfGrid`, and containment, since a
  child is contained only by a grid; `Container` defines what it derives, the cells, `Container.Holds`, the rules and
  the grid's counters, as an extension of `Logical.OfGrid`.
- **Span stays a grid property, a positive int**: "OK I can accept span as a grid property." A span of 0 would only
  restate a span of 1 along the other axis, which `grows` already gives.
- **Grid settings are mutations**: a grid's span, axis and cell rotation are written by mutations, and the layout
  follows them, rather than being set by a call to the container layout.
- **The diagram's grid holds the top-level shapes, with no entry**: "A - we resolved this before", the decision
  [FEA-056: fungible diagramming keeps agents and humans in the loop](../features/FEA-056.md#decided) records, that removing a containment entry "shifts it to the diagram
  level". The diagram's grid holds every member of the diagram that no shape's grid holds, so that removing a shape's
  entry alone moves it to the top level, deleting nothing, and a shape made with no entry is placed there.
- **Two cells at one coordinate are expressible, never written by code**: "this can be expressed in journal form but
  code should not use this case". A journal may hold such an entry, since mbse-schemas reports declared uniqueness
  rather than enforcing it; the container layout never writes one.
- **Rejection is consistent**: a transaction that violates a constraint its schemas declare "may be recorded and
  transmitted but any pair of recipients considering that transaction must consistently reject it". So only a
  constraint declared in a schema, and enforced by mbse-schemas, may reject one; the layout never rejects a mutation by
  a check of its own.

## Decided by an agent, for review

Where the user's decisions were silent, the simplest default consistent with them, each *proposed* until reviewed,
labeled with the repository and number it was decided under.

- **(mbse-diagrams 11)** **Settings outside their values are unset.** A span that is not a positive int, or an axis
  other than `"rows"` or `"columns"`, is taken as unset: the diagram's `grid_span` or `grid_grows` applies, where it
  is valid, then 3 and `"rows"`. mbse-schemas can declare neither a value domain nor an enumeration
  ([CAP-166: constraints attached where they constrain](CAP-166.md) puts them in mbse-patterns), so no recipient can
  reject such a value, and every recipient reads it the same way; the gap is reported here, per
  [PRI-032: a sibling's gap is reported, not worked around](../PRINCIPLES.md#PRI-032).
- **(mbse-diagrams 11)** **The diagram's defaults are the logical layout's**: `grid_span` and `grid_grows` are
  properties of `Logical.OfDiagram`, beside the grid settings they default.
- **(mbse-diagrams 11)** **Following a change of settings.** `Container.configured(grid)` follows a mutation that
  made a grid or changed its settings: where its span or axis changed, its cells are rearranged, in the same order,
  and its rules checked again. `Container.defaulted(diagram)` follows a change of the diagram's defaults, configuring
  each grid whose span or axis it changed. A grid records the span and axis its cells are arranged by,
  `arranged_span` and `arranged_grows`, so that the order of its cells can be read after a mutation has changed its
  settings.
- **(mbse-diagrams 11)** **The diagram's grid is written like any other**, by the mutation that first needs it, one
  that makes or moves a shape to the top level; the container layout places no top-level shape while the diagram has
  no grid, and no shape that is no diagram's member.
- **(mbse-diagrams 11)** **Rules stay owned through `Logical.Owns`** by their grid, named by its `ruled` count.
