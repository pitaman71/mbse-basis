# CAP-166: constraints attached where they constrain

*Implements* [FEA-034: analytic behavior conventions in schema](../features/FEA-034.md). Index entry: [capabilities/README.md](README.md#CAP-166). *Relates to* [CAP-025: nothing mandatory but by constraint](CAP-025.md), [PRI-021: refinement by constraint](../PRINCIPLES.md#PRI-021), [FEA-024: expressions as data](../features/FEA-024.md).

## Design

Not designed. Constraints are mbse-patterns' and mbse-expressions' ([PRI-011: the lowest repository that can own it](../PRINCIPLES.md#PRI-011)): kept beside the schemas, named predicates about a schema by its registered name, not in them, so that mbse-schemas does not depend on mbse-expressions and several sets may apply to one schema. Where nothing is mandatory but by a constraint ([CAP-025: nothing mandatory but by constraint](CAP-025.md)), the constraints attached to a model are its specification.

## Open questions

- **Where constraints attach.** A specification is constraints attached to the parts of a system they constrain, each
  held by a property named `requires` ([MBSE.md](../../MBSE.md#what-a-specification-is-made-of)); mbse-patterns'
  predicates already hold theirs so. Which scopes a constraint attaches to (a schema, a property, a relation, an
  interface, a whole specification), and how attached constraints combine into one conjunction, is not decided.
  The elements that bind parameters (see [CAP-112: parameters modeled as schema data](CAP-112.md)) are likely the same scopes.
