# CAP-267: C and C++ terms read under the ABI their holder names

*Implements* [FEA-024: expressions as data](../features/FEA-024.md). *Relates to* [CAP-229: the C expression dialect](CAP-229.md), [CAP-230: the C++ expression dialect](CAP-230.md), [CAP-097: value domains of published standards](CAP-097.md), [CAP-100: six languages' expression dialects](CAP-100.md), [PRI-042: optionality kept](../PRINCIPLES.md#PRI-042).

## As built: mbse-expressions

Built in mbse-expressions' domains as data, stage 3, group 1 (PR #30), in both languages, and released in 0.9.0; the
choices made where the decisions were silent are [the port's API, Settled in domains as data's stage 3](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-domains-as-datas-stage-3-for-the-users-review),
items 131 to 140, which hold the detail this section only bridges. Until then C's evaluation assumed one data model,
LP64, with `long double` as IEEE 754's `binary128` ([CAP-100: six languages' expression dialects](CAP-100.md)); now a
C or C++ term is read under the ABI its holder names, and each ABI is a dialect of its own.

- **The ABI dialects** (Decided, below): `Expressions.SystemV.AMD64`, x86-64's System V psABI, and
  `Expressions.Arm.AAPCS64`, AArch64's, each a family with one dialect, laid out as every dialect is (Python
  `mbse.Expressions.SystemV.AMD64`, TypeScript `@mbse/expressions/SystemV/AMD64`), a singleton of its own schema with
  no terms and no kinds of its own, serving C and C++ alike. Its `define` writes, as stored domains of ISO/IEC 11404's
  and IEEE 754's kinds ([CAP-097: value domains of published standards](CAP-097.md#value-domains)), every type the C
  and C++ standards leave to the implementation, as its ABI fixes it: `char` (signed on AMD64, unsigned on AAPCS64),
  `signed char`, `unsigned char`, `short`, `int`, `long`, `long long` and their unsigned forms, `float`, `double`,
  `long double` (x87's 80-bit extended format on AMD64, an `ieee754` domain with no `format`; `binary128` on
  AAPCS64), `wchar_t` (`int` on AMD64, `unsigned int` on AAPCS64), `char8_t`, `char16_t`, `char32_t`, `size_t`,
  `ptrdiff_t`, `intptr_t`, `uintptr_t`, `int_leastN_t` and `uint_leastN_t`, `_Float32x` and `_Float64x`, each in the
  order C's standard lists the types (API 132). An unsigned type is 11404's `modulo`, a signed one 11404's `integer`
  with `overflow` `raise` ([CAP-229: the C expression dialect](CAP-229.md)). Each ABI dialect covers its psABI document
  as an edition ([CAP-268: standards as tagged data](CAP-268.md)).
- **The holder names its ABI**: `Expressions.Framework.HasAbi(expression, abi)`, added by the framework's install,
  links an `Expressions.Framework.Expression` to a dialect, a holder naming one ABI at most (`uniques("abi")`), read
  through the expression's adjacency `abi`, which every dialect's holder inherits (API 138, 140). One store may hold
  several ABI dialects, each holder read under its own. Each ABI dialect's schema declares an anonymous adjacency to
  `HasAbi`, so that a holder naming as its ABI a dialect that is not one is refused by validation (API 132).
- **The lookup**: a C term's named type is found among C's own domains, then among those of the ABI its holder names; a
  C++ term's among C++'s, then its holder's ABI's (`C.Domains.Types`, API 133). The holder is found from the term by its
  owners (`Terms.holder_of`), a dialect's domains by name through `Framework.Domains.domains(dialect)` (API 140). The
  working value the arithmetic computes on, a `CType`, is built from a stored domain and keeps the lookup it was read
  through, so that the promotions reach the ABI's `int` (API 134). What C's evaluation, inference and validation read
  so: a literal's type and its range, a cast's target, `int` for the promotions, `size_t` for `sizeof`, `bool` for a
  comparison (API 137).
- **What is refused**, each by name: a type neither dialect defines, `'int' is not a type C or AMD64 defines`; one C's
  own dialect does not define, whose holder names no ABI, `'int' is not a type C defines, and its expression names no
  ABI`; and a lone term, by mbse-schemas' `TypeError`, "the value does not belong to a store" (API 133).
- **Every caller** installs and defines C, Cpp, AMD64 and AAPCS64 after the standard dialects, and names an ABI on its C
  and C++ holders: the suites (whose `term` helpers name AMD64 by default), the corpus (`amd64_domains`,
  `aapcs64_domains`), the tutorials' toolkit, tutorial 8 (which shows `(char)200` under both ABIs) and the skill
  (API 139). DOM-19 pins each ABI dialect's domains, a holder naming one ABI at most, the lookup and its refusals, in
  both languages.
- **Not stored**: `_Float128x`, which neither ABI provides, and is refused by name; `int_fastN_t`, `uint_fastN_t`,
  `intmax_t` and `uintmax_t`, whose widths neither the C standard nor the two psABIs fix (they are the C library's).
  ILP32 models (x32, AAPCS64's ILP32) would be dialects of their own, added when needed.
- **Found while building**: validating an ABI dialect's singleton does not reach the `HasAbi` entries that name it,
  its adjacency to `HasAbi` being anonymous; a holder's validation checks its `abi`.

## Decided

As the user decided (2026-11-10, on mbse-expressions' domains as data, stage 3's design): adopted, each the rule as
stated, quoted as given.

- **One dialect per ABI, holding only domains.** Asked whether C and C++ should have a dialect for each ABI, the user
  was shown about 12 mainstream ABIs (x86-64 System V, Microsoft x64, i386 System V and Windows, AArch64 AAPCS64, Apple
  and Windows, ARM32 AAPCS, RISC-V LP64D, PowerPC64 ELFv2, s390x, wasm32), across which what differs is the data model
  (LP64, LLP64 or ILP32), `long double`'s format, plain `char`'s signedness, `wchar_t`'s width, and the `_FloatNx`
  formats. Then this recommendation, which the user approved with "yes":
  - C and C++ stay one dialect each, holding the terms and the domains that don't depend on the ABI (`bool`, the
    `_FloatN` interchange formats, `nullptr_t`, ...).
  - Each ABI is its own small dialect holding only the ABI-dependent domains: `long`, `long double`, `char`, `wchar_t`,
    `size_t`, `_FloatNx` and the like. Each psABI is a published standard, so this follows "Adjacenct standards may be
    their own dialect" (the scope of stored domains, [CAP-097: value domains of published standards](CAP-097.md#decided)).
  - One ABI dialect serves both C and C++.
  - A store installs the ABI dialects it needs, in install order, as with the standard dialects
    ([CAP-098: dialects over one framework](CAP-098.md#decided), "No `Uses`").
  - ABIs are added as they are needed. Stage 3 builds two: x86-64 System V and AArch64 AAPCS64. These two were the
    coordinating agent's example, which the user did not contradict; recorded as such.
  - The ABI dialects are named by the namespace rule ("`Expressions.<family>.<dialect>`, a family named as its standard
    names the language"; [CAP-226: complete expression dialects](CAP-226.md#decided), "The namespace"), each spelled as
    its psABI document names itself. The names chosen are the agent's, for review (below).
  - What this replaces: the single LP64 data model C's evaluation assumed until stage 3 ("C's arithmetic types under
    LP64 ... `long double` as IEEE 754 `binary128`", [CAP-100: six languages' expression dialects](CAP-100.md), now
    corrected there), and stage 3's design's `long double` as `binary128`. Under an ABI dialect, `long double` is
    whatever that ABI says: x87's 80-bit format on x86-64 System V, `binary128` on AAPCS64. C's evaluation reads no
    data model of its own, only its holder's ABI.
- **The `_FloatNx` formats are each ABI's** (M, 2026-11-10, the design approved as a whole with "yes"): under an ABI,
  the formats of `_Float32x`, `_Float64x` and `_Float128x` are fixed by that ABI, though C23's Annex H leaves them to the
  implementation. So each ABI dialect stores them as its ABI fixes them. (M's `std::bfloat16_t` is
  [CAP-230: the C++ expression dialect](CAP-230.md#decided)'s.)
- **P. The holder names its ABI: (b)** (2026-11-10), on which ABI a C or C++ term is read under. The user's rule:
  "immediate optionality over deferred optionality over sacrificing optionality" ([PRI-042: optionality kept](../PRINCIPLES.md#PRI-042)). (a), one ABI per store,
  sacrifices optionality; (c), the caller passing the ABI, changes the API against "there is no valid programming
  context where a lone term needs a domain or schema" ([CAP-098: dialects over one framework](CAP-098.md#decided), "No
  lone terms"). So (b), as the design proposed:
  - The `Expression` holding a C or C++ term names the ABI its terms are read under, by a relation between
    `Expressions.Framework.Expression` and a dialect, unique by the expression, read through the expression's
    adjacency `abi`. Its name is the agent's, by the record's conventions.
  - One store may hold several ABI dialects, each holder read under its own.
  - A term that needs an ABI-dependent domain, whose holder names no ABI, is refused with a clear message.
  - It is not `Uses`: it records which ABI a holder's terms are read under, not a dialect's dependencies. The design
    flagged it under the standing instruction on `Uses` ([CAP-098: dialects over one framework](CAP-098.md#decided)),
    and the user settled it with this answer, so it gives no reason to reinstate `Uses`.
- **Q. Every ABI dialect defines what the implementation chooses: (b)** (2026-11-10), on which dialect defines the
  domains and schemas of `int`, `short`, `long long`, `signed char` and `unsigned char`, `float` and `double`, which the
  C standard leaves to the implementation though every listed ABI gives them alike. The user: "(b)". So:
  - Every ABI dialect defines its own domain and schema for each, with its ABI's values.
  - C's and C++'s own dialects keep only what the language standard itself fixes: `bool`, the `_FloatN` interchange
    types and the decimal types, `nullptr_t`, and C++'s `std::floatN_t` and `std::bfloat16_t`, each checked against its
    standard.
  - Everything the implementation chooses goes in each ABI dialect: the types above, `char`, `long`, `long double`,
    `wchar_t`, `size_t`, `ptrdiff_t`, `intptr_t`, `_Float32x`, `_Float64x`, and the `<stdint.h>` typedefs each ABI
    fixes, decided by what the C and C++ standards leave to the implementation.
  - This supersedes the design's recommendation (a), that what every ABI shown gives alike stays C's and C++'s.
- **The holder-to-ABI relation is kept** (2026-11-10). Told what stage 3 built that links one dialect to another, after
  saying "I am a little concerned about over-exerting ourselves to try to link between dependent dialects", the user
  answered, of `Expressions.Framework.HasAbi`: "yes, keep it". Of the lookups that read one dialect's domains from
  another's terms: "this is what I want to review" ([CAP-097: value domains of published standards](CAP-097.md#decided),
  "The links between dialects"), so they are listed below for review.

## Decided by an agent, for review

Recorded in [the port's API, Settled in domains as data's stage 3](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-domains-as-datas-stage-3-for-the-users-review),
items 131 to 140, not marked as the user's: each *proposed* until reviewed.

- **(mbse-expressions 30, domains as data, API 132)** **The ABI dialects' names**, `SystemV.AMD64` and `Arm.AAPCS64`
  (tags `amd64`, `aapcs64`): the family is the ABI as its document names it (`SystemV`, of "System V Application Binary
  Interface"; `Arm`, as Arm spells itself), the dialect the processor supplement or the standard (`AMD64`, the
  supplement's own name for x86-64; `AAPCS64`, the document's abbreviation).
- **(mbse-expressions 30, domains as data, API 140)** **`HasAbi`'s names**: named as the framework's other relations
  from a holder are, by what the first link has (`HasRoot`, `HasDomain`), its acronym spelled as the kinds' schemas
  spell theirs (`OfIeee754`); its links are the roles they play, as `Defines`' are; the framework's install adds it,
  since no dialect owns the holder. Found while building: the design's `unique [expression]` let one holder name two
  ABIs, since in mbse-schemas `unique(S)` says S is determined by the other links; it is `uniques("abi")` (API 138).
- **(mbse-expressions 30, domains as data, API 132)** **The ABI dialects declare the link**: mbse-schemas refuses a link
  filled by an object whose schema declares no adjacency to the relation, so each ABI dialect's schema declares an
  anonymous adjacency to `HasAbi` through `abi`, and a holder naming as its ABI a dialect that is not one (C's,
  Python3's) is refused by validation.
- **(mbse-expressions 30, domains as data, API 133, 134 and 140)** **The lookups between dialects**, for the user's
  review as the user asked: a C or C++ term's types are read through its holder (`Terms.holder_of`, its owners up to
  the reference object that holds the root), its own dialect's domains first, then those of the ABI the holder names,
  each dialect's domains by name through `Framework.Domains.domains(dialect)`; a working type keeps that lookup beside
  its domain, since a type of C's own (`int8_t`) cannot reach the ABI's `int` the promotions need. The refusals are
  those above, a lookup's failure a problem in validation and raised in inference and evaluation (API 137).
- **(mbse-expressions 30, domains as data, stage 3's design)** **The exact-width typedefs are C's and C++'s**, by the
  rule the user gave, what the standard fixes: `int8_t` to `int64_t` and `uint8_t` to `uint64_t` are each exactly its
  width, with no padding bits, two's complement where signed (C23, `<stdint.h>`; C++'s `<cstdint>` is C's); only whether
  one is provided, and which basic type it names, is the implementation's, as only whether `_Float16` is provided is.
  So they are not among the `<stdint.h>` typedefs an ABI fixes.
- **(mbse-expressions 30, domains as data, stage 3's design)** **What is not stored**: `_Float128x`, which neither ABI
  provides; `int_fastN_t`, `uint_fastN_t`, `intmax_t` and `uintmax_t`, which neither C nor the two psABIs fixes
  (glibc's `int_fast16_t` is 64 bits on x86-64, musl's 32).
- **(mbse-expressions 30, domains as data, API 139)** **The suites' C and C++ holders name AMD64 by default**, and
  tutorial 8 shows `(char)200` under both ABIs.
