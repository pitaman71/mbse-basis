# CAP-226: complete expression dialects

*Implements* [FEA-024: expressions as data](../features/FEA-024.md), [FEA-008: expressive program models](../features/FEA-008.md). Index entry: [capabilities/README.md](README.md#CAP-226). *Relates to* [CAP-100: six languages' expression dialects](CAP-100.md), [CAP-098: dialects over one framework](CAP-098.md).

## Design

Not built. The framework's rules for complete dialects, which each dialect's own capability applies:
[CAP-227: the Python3 expression dialect](CAP-227.md), [CAP-228: the TypeScript5 expression dialect](CAP-228.md),
[CAP-229: the C expression dialect](CAP-229.md), [CAP-230: the C++ expression dialect](CAP-230.md) and
[CAP-231: the SystemVerilog expression dialect, complete](CAP-231.md). Today's dialects, which hold the terms of
constraints, a fraction of each language's expressions, are [CAP-100: six languages' expression dialects](CAP-100.md)'s.

Proposed and decided in [mbse-expressions' proposal, complete expression dialects](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/dialects/README.md)
(branch `complete-dialects`), which is stage 1 of [mbse-programs' port](https://github.com/pitaman71/mbse-programs/blob/main/docs/proposals/port/README.md#stages-proposed-once-decided)
(branch `port-schemas`); its survey of what each dialect lacks is [the gaps, dialect by dialect](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/dialects/GAPS.md).
Its stages, each passing both gates at 100% in both languages with the corpora regenerated:

1. The decisions recorded: this capability and the five above.
2. The framework and the renames, with today's kinds: `Expressions.Framework.Term` a union of each dialect's union
   (`Expressions.<Dialect>.Expression`), the invalid-syntax kinds,
   `Python3`, `C` and `Cpp` from `Ccpp`'s kinds, `SystemVerilog`; the translators retargeted; corpus cases per dialect.
3. `Python3` complete ([CAP-227: the Python3 expression dialect](CAP-227.md)).
4. `TypeScript5`, new ([CAP-228: the TypeScript5 expression dialect](CAP-228.md)).
5. `C` and `Cpp` ([CAP-229: the C expression dialect](CAP-229.md), [CAP-230: the C++ expression dialect](CAP-230.md)).
6. `SystemVerilog` complete ([CAP-231: the SystemVerilog expression dialect, complete](CAP-231.md)).
7. Tutorials, skill, README and EQUIVALENCE; mbse-expressions 0.8.0, a breaking change. Then mbse-programs' stage 2,
   mbse-patterns and mbse-codegen-python.

## Open questions

- **A literal's spelling against its value**, to settle in stage 2 (question 2).

## Decided

As the user decided, adopted, each the rule as stated, quoted as written. On mbse-programs' port (2026-11-02,
[its Decided](https://github.com/pitaman71/mbse-programs/blob/main/docs/proposals/port/README.md#decided)), and on mbse-expressions' proposal
(2026-11-02, [its Decided](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/dialects/README.md#decided), questions 2 to 9):

- **One dialect per language and major version, covering its minor versions or standards.** "language dialects each
  of which supports a major version of a target language and all of the minor versions in it, such as Python3 or
  Typescript5. This means each language dialect must correctly handle the closure of syntaxes across minor versions
  such as 3.11 - 3.14." For C and C++, first "Maybe C11, C17, C23 Cpp17, cpp20, cpp23" (tentative; C17 adds no syntax
  over C11), then, on question 3: "it sounds like having 6 different dialects is overkill. what would you recommend?",
  and to the recommendation, "yes": two dialects, `C` and `Cpp`, each covering every standard of its language (C11 to
  C23, C++17 to C++23), each kind recording as data the standards that have it, as mbse-programs' standards do
  (`SINCE`) and as `SystemVerilog` records Verilog; separate, since C++ is not a superset of C; one union each, so that
  no union is completed by extension; whether a construct is in a standard a constraint, as validation is (below). And
  "yes keep verilog as a subset of systemverilog, presuming that is how the standards are partitioned" (it is: IEEE
  1800-2009 merged IEEE 1364). The dialects are `Python3`, `TypeScript5`, `C` (C11 to C23), `Cpp` (C++17 to C++23)
  and `SystemVerilog` (Verilog its subset).
- **Complete over the language's AST, gaps filled in mbse-expressions.** "`mbse-programs` should make use of
  `mbse-expressions.Dialects.<lang_ver>.Expression`. Yes, this means the expression dialect must completely cover the
  AST. Rather than using schema-extension, if there are any gaps in the dialect as modeled in
  `mbse-expressions.Dialects.<lang_ver>`, they should be added into `mbse-expressions`. There is no reason for an
  expression dialect to exist that is ia subset of the corresponding node of AST in the real langauge."
- **mbse-programs' kinds, names and shapes** (question 2, "yes to both"): its kinds, which follow each language's
  parser (`ast` for Python, typescript-estree for TypeScript), so that its stage 2 maps them one to one; ours that are
  narrower replaced by them (a comparison chain, `and` of n operands, comprehensions of several `for`s, calls with
  keywords, one `Subscript`), their evaluators and translators following; what has no counterpart in the grammar
  (Python's `import` and `importfrom` in an expression, `let` as `(lambda name: body)(value)`) kept, marked as an
  extension, as mbse-programs marks JSX; and concrete syntax (`Parenthesized`, a literal's spelling, adjacent strings)
  kept, so that source prints back as written.
- **`Expressions.Framework.Term` is a union of the dialects' unions; the holder is the framework's.** First, asked
  whether each dialect has its own holder, the user answered "3.", naming
  `mbse-expressions.Dialects.<lang_ver>.Expression` ("Expression terms are value objects. An instance of
  OfSchemas.Expression holds the expression root."). Then, asked about the `<dialect>_` branch prefixes ("I don't
  understand the `python_` prefix"; "I don't know that we need `Expressions.Framework.Term`"): "OK if instead we keep
  `Expressions.Framework.Term`, that can be a union of `Expressions.Dialects.<lang_ver>.Expression` which is itself a
  union." and, shown the consequences, "yes". `Expressions.Framework.Term`'s branches are the dialects (`python3`,
  `typescript5`, `c`, `cpp`, `systemverilog`, `patterns`, `matlab`, `excel`, `latex`), each branch's schema the
  dialect's union of its kinds, `Expressions.<Dialect>.Expression`, whose branches are named plainly (`binop`): no
  prefix, each name unique where it is defined. A dialect's own kinds name its union in their term slots; the
  framework's shared kinds name `Expressions.Framework.Term`, and each dialect's union lists the shared kinds it
  reuses. Where `Framework.Term` is held, a term is written with its dialect, then its kind, as a restricted `OfAny` is
  ([CAP-069: wire format shorthand (scalars)](CAP-069.md)). The holder stays `Expressions.Framework.Expression`, a
  reference object whose `root` holds a `Framework.Term`, linked by `HasRoot` as today; a dialect's
  `Expressions.<Dialect>.Expression` is its union, not a holder. A union of unions validates, builds and round-trips
  in mbse-schemas 0.26.5 as it stands.
- **The framework's kinds with term slots stay shared** (question 4): "validation will be by constraints not by
  schema". `let`, `call`, `list` and `mapping` stay shared, as decided on 2026-10-30
  ([CAP-100: six languages' expression dialects](CAP-100.md#decided), Decided), their slots any dialect's term; that a
  dialect's expression holds only its own terms is a constraint, not the schema's closure (option (ii)).
- **Bodies within expressions are not part of the term** (question 5, "(i)"): a function's, an arrow's or a lambda's
  body is not; statements are mbse-programs' owned reference objects ("Files, scopes, and statements should be owned
  reference objects"), and mbse-programs relates a body's statements to what holds the expression.
- **The sublanguages an expression holds are the dialect's** (question 5, as recommended, (a)): types, patterns, JSX,
  and SystemVerilog's sequences and properties, each a union of its own beside the dialect's terms.
- **The model and printers here, the parsers mbse-programs'** (question 6, "yes fix that phrase", (b)): mbse-programs
  reads the native parser's tree into its owned statements and the dialect's terms in one walk; completeness is checked
  here against each grammar's node list, kept as data (`ast`'s, a grammar's `node-types.json`, slang's), every node a
  kind or listed as not an expression. Python's `Text.FromText` stays until mbse-programs reads `Python3`, then moves
  there. mbse-programs' stage 1 no longer says "parsing ... complete". The native parser is mbse-programs': "`mbse-programs`
  typically uses a "native parser" or "tree walker" that conforms to and tracks evolution of publish standards. To the
  degree that the chosen "native parser" supports parsing and preserving invalid syntax, `mbse-programs` should also."
- **`error` and `missing` kinds for invalid syntax** (question 7, "agreed"): two framework kinds, every dialect's
  union holding them, modeled now and written later by parsers that keep them: `error`, what the parser skipped and the
  terms it recovered within it, and `missing`, the kind the parser expected (tree-sitter's `ERROR` and `MISSING`,
  slang's skipped and missing tokens). CPython's `ast` keeps nothing, so `Python3` read by it refuses, by position.
- **A shallow evaluator** (question 8, "agreed we can keep a shallow evalluator in mbse-expressions"): a new kind is
  validated, printed, stored and translated where a rule exists, but refused by evaluation by name ("Python3 Lambda is
  not evaluated"), each evaluator's growth a follow-up capability; what is evaluated today keeps working, the narrower
  kinds replaced keeping what they evaluate.
- **Basic is renamed Patterns, and a quantifier takes a pattern** (2026-11-02): "former `Expressions.Dialects.Basic`
  should be renamed `Expressions.Dialects.Patterns`. Any quantiier should take a Schemas.OfPattern as its sole
  argument." (First written "a Schemas.OfPredicate", which mbse-schemas no longer has; corrected by the user.) How a
  quantifier reads its pattern is proposed in [the proposal](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/dialects/README.md#decided).
- **Patterns (formerly Basic), Matlab, Excel and Latex otherwise unchanged; the translators retargeted** (question 9, "yes"): those four keep their
  kinds, changed only as the names and the holders change every dialect's install. The translators keep what they
  translate today, retargeted to the renamed dialects; a new kind has no counterpart and is refused by name. Basic and
  C, and Basic and C++, are "one rule set each over the kinds a family shares, applied to each standard" (written
  before question 3 made `C` and `Cpp` one dialect each). `TypeScript5` has no translator yet.
