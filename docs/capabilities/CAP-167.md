# CAP-167: schemas refined by other schemas

*Implements* [FEA-020: refinable models](../features/FEA-020.md). Index entry: [capabilities/README.md](README.md#CAP-167). *Relates to* [CAP-034: schemas specialized by classifier intersection and union](CAP-034.md), [VOC-003: refinement](../VOCABULARY.md#VOC-003).

## As built: mbse-schemas

Met in mbse-schemas 0.26.4, checked in the code of both languages at 0.26.4: `Schemas.Refines`, a relation of the meta-schemas, on object and container schemas (scalars refine nothing since 0.18.0). As built and decided: Decided, below.

mbse-expressions refines with it (main, unreleased until 0.8.0): `Expressions.Python3.Literal` refines the framework's
literal ([CAP-233: literals of any value](CAP-233.md#as-built-mbse-expressions)), and each dialect's holder,
`Expressions.<Dialect>.Expression`, refines `Expressions.Framework.Expression`, narrowing its `root` to the dialect's
`Term` ([CAP-226: complete expression dialects](CAP-226.md#decided)).

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(framework design)** **Narrowing to a union's branch, in either order** (2026-11-03, mbse-schemas 0.26.7), as the
  user decided: "(a)", that mbse-schemas counts a union's branch as narrowing the union, found when mbse-expressions'
  per-dialect expression holders could not narrow `root` from `Expressions.Framework.Term` to their dialect's `Term`.
  Two fixes: a refinement may narrow an inherited member's schema from a union to one of its branches' schemas (or one
  narrowing it), validation confirming it, and the refinement reads and writes that member by the schema it declares,
  never guessed ([PRI-025: never guess the schema](../PRINCIPLES.md#PRI-025)); and `.refines(...)` before or after
  `.properties(...)` or `.adjacencies(...)` gives the same schema, a redeclared member kept and checked for narrowing,
  inherited members filling in only where not redeclared (before, a member redeclared after `refines` was silently
  dropped). Tested by SCH-25 and SCH-26.
- **(framework design)** **Refinement, identities and relations** (2026-10-14), as the user decided, for mbse-expressions' framework and
  dialects as model ([PRI-018: no model needs code to read or write](../PRINCIPLES.md#PRI-018)):
  - refinement: the user is "open to adding Schemas.Refines as a relation all its own"; "Refinement across the scalar
    vs. container vs. object boundary fails validation"; an "instance of a refinement is an instance of what it
    refines"; "narrowing allowed if it can be statically confirmed by validation". A one-part intersection, which the
    user called "trivial refinement", is what `Refines` states. Built as a builder clause, `.refines(schema)`, on
    scalar, object and container schemas (SCH-24), until schemas are linked objects (phase 5) and it becomes a relation
    of its own:
    - an object refinement has the refined schema's properties and adjacencies, named and anonymous, before its own,
      and follows later changes to them; it may redeclare one narrower, a property with a type that refines the
      inherited one (or a scalar of the same token within its widths, or a container whose index and element each
      narrow), an adjacency only with the same relation and link. It is a reference object schema exactly where what
      it refines is one. Its objects fill the refined schema's links, and the refined schema's extent holds them.
    - a scalar refinement has the refined token and widths within the refined ones; a container refinement, an index
      and an element that each narrow the refined ones. (Superseded since 0.18.0 for scalars: only objects and
      containers refine; Store overhaul, Decided, 22.)
    - validation refuses a refinement of another kind, of itself, and what it cannot confirm narrows ("cannot be
      confirmed"). Modules write `refines` and a refinement's own members only.
  - identity: "change policy to allow an object's identity to be read + written by `as_identity`. Builder will
    allocate only if it's not set in the pre-existing object or by the fluent clauses". This supersedes, in part,
    "Reference identity" (below): a program may now set an identity, such as an operator's global ID
    (`Basic.Operators.Add`). Built (STO-08): a builder's `as_identity(identity)` writes it, and `as_identity()` reads
    the one written, else the source's; `create()` and `clone()` give one only where none is written, and `update()`
    renames the object. An identity no other live object of its schema has, which its naming pattern gives where it
    has one; a singleton's is its global name; data instances and value objects refuse a write. (Superseded for data
    since 0.20.0: a program writes no identity, and data has no `as_identity`; object identity 43 in [CAP-119: owned objects found by path](CAP-119.md#decided). Schema
    objects keep theirs until step 4g of the store overhaul.)
  - domains: "domains refine scalar schemas" (mbse-expressions' value domains). (Superseded: a domain is
    mbse-expressions' object, associated with a basic scalar, which has none of its own; Store overhaul, Decided, 9.)
  - relations: "mbse-schemas.Schemas.OfRelation is by default a all-directional link. Anonymous adjacencies allow for
    some adjacencies to be omitted." An entry "may be rejected if the linked object is of the wrong type. That's
    exactly why we have anonymous adjacencies at all. They still participate in type checking even though they omit
    access from the adjacent object to the relation." Built: an adjacency declared with no name
    (`r.of(Owns).me("item")`) is anonymous; the object may fill the link, and has no member and holds nothing for it.
    Validation accepts a linked object whose schema declares the link, named or anonymous (VAL-15), and modules write
    an anonymous adjacency with no name. Their absence was a bug: an object could fill a link only through a named
    adjacency, a member it may not need.

Its identity point is superseded ([CAP-118: singletons, owned and counted objects](CAP-118.md#decided)); its domains point too ([FEA-024: expressions as data](../features/FEA-024.md)); its relations point is how [CAP-155: `unique` clauses on relation schemas govern relation cardinality](CAP-155.md) is built.

## Decided by an agent, for review

Recorded in mbse-schemas' design, not marked as the user's: each *proposed* until reviewed.

- **(mbse-schemas 19)** Validating an instance of a refinement, as built in 0.26.8, applying "an instance of a
  refinement is an instance of what it refines" to validation: `Validators.Check`/`Validate(store)(schema, value)`,
  `.OfObject` and `.Reachable` accept a root whose schema is `schema` or refines it, directly or not
  (`Schemas.is_a`), and check it, and every object reachable from it, by its own schema, never by the one given, so a
  member the refinement narrows is checked as narrowed and an inherited one as inherited; a root of any other schema,
  the refined schema's own object checked against a refinement of it included, is refused as before ("the value is a
  '…', not an instance of the given schema"). Tested by SCH-25.
- **(mbse-schemas 15)** Beyond a union's branch, as built in 0.26.7: a union narrows a union whose branches, by name,
  hold its own, each narrower (a branch name the other lacks is refused); a restricted `OfAny` is narrowed only by one
  of its own schemas, an unrestricted one by a scalar or a named schema, and one `OfAny` another where each of its
  schemas would; a pair met again while checking is not confirmed, where two self-holding containers once recursed
  without end.
- proposed in building, for the user's review: refinement of unions, intersections, values of any type and
  applications is refused for now, as a refinement of another kind would be.
