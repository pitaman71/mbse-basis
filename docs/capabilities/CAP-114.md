# CAP-114: parameter bindings are substituted and checked

*Implements* [FEA-033: model parameters](../features/FEA-033.md). Index entry: [capabilities/README.md](README.md#CAP-114).

## Design

Not built, as the Parametrics proposal says:

### Not built

- **Not built**: substituting a binding (`Parameters.Apply`), checking a binding's value against its parameter's
  `ForValue` schema, and expression parameters ("TBD"). Bindings are stored, as `Parameters.Bind` would have stored
  them (Store overhaul, Decided, 12 and 28: "super lazy").

## Open questions

- **Shape constraints bound to parameters.** Extents go, and a shape is a constraint on the type of the property that
  keys a relation's entries; how a parameter (Parametrics) is bound into such a constraint, to give a tensor's shape,
  is the Parametrics work's.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(schema extension 15)** Constraining a type parameter: "We can start with level 0 but I do want to plan for level 2. But not today."
  Level 0: a generic signature (`add[T](a: T, b: T) -> T`) states its shape only, and binding a call to a registered
  intrinsic is the constraint. Level 2, planned: a parameter's optional bound, the schemas its value must refine
  (`T refines Integer`), so that inference rejects a call before binding. Relations between parameters (promotion)
  and results computed from them (SystemVerilog widths) go to intrinsics that compute the result's schema; modeling
  type-level computation is off the table.
