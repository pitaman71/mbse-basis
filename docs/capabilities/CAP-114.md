# CAP-114: parameter bindings are substituted and checked

Superseded by [CAP-313: parameter references valid where their parameters are assigned or bound](CAP-313.md): every procedure that traverses a dialect's expression
or statement tree keeps a context by its dialect's scoping rules, substituting what the context gives a parameter, and
validation checks it, as the user decided. The decisions below stand.

*Implements* [FEA-033: model parameters](../features/FEA-033.md).

## Design

Not built, as the Parametrics proposal says:

### Not built

- **Not built**: substituting a parameter assignment or a parameter binding (`Parameters.Apply`), checking a parameter
  assignment's value against its parameter's `ForValue` schema, and expression parameters ("TBD"). Parameter
  assignments and parameter bindings are stored, as `Parameters.Bind` would have stored them (Store overhaul, Decided, 12 and 28: "super lazy").

## Open questions

- **Shape constraints bound to parameters.** `OfIndexed`'s index domains go, and a shape is a constraint on the type of
  the property that keys a relation's entries; how a parameter (Parametrics) is bound into such a constraint, to give a
  tensor's shape, is the Parametrics work's.

### Expression parameters

An expression parameter is a parameter reference in an expression's term, and substituting it is the same operation as
substituting a parameter reference anywhere else ([the parametrics proposal](../../proposals/PARAMETRICS.md#substituted)).

- **Data whose shape depends on a parameter neither assigned nor bound**: what proxies accept for it (the framework design's "Parametrics, beyond the proposal"). The
  parametrics proposal answers it for validation: such data is neither valid nor invalid there.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(schema extension 15)** Constraining a type parameter: "We can start with level 0 but I do want to plan for level 2. But not today."
  Level 0: a generic signature (`add[T](a: T, b: T) -> T`) states its shape only, and binding a call to a registered
  intrinsic is the constraint. Level 2, planned: a parameter's optional bound, the schemas its value must refine
  (`T refines Integer`), so that inference rejects a call before binding. Relations between parameters (promotion)
  and results computed from them (SystemVerilog widths) go to intrinsics that compute the result's schema; modeling
  type-level computation is off the table.

## Decided by an agent, for review

Recorded in mbse-schemas' design, not marked as the user's: each *proposed* until reviewed.

### The framework design's Parametrics

From the framework design's Parametrics, Decided, where it was not marked as the user's:

- **Unknown is an outcome of validation.** Data that depends on a parameter of its schema that is neither assigned nor
  bound is neither valid nor invalid there.
