# CAP-297: simplification in every binding state

*Implements* [FEA-024: expressions as data](../features/FEA-024.md). *Applies* [PRI-046: simplification, not evaluation](../PRINCIPLES.md#PRI-046). *Relates to* [CAP-099: partial evaluation](CAP-099.md), [CAP-106: expressions evaluated three-valued](CAP-106.md).

## As built: mbse-expressions

mbse-expressions 0.11.0 holds this capability's build. The framework has one simplification procedure,
`Framework.Simplifiers`. The procedure simplifies an expression of any dialect in each of three binding states. When the
caller's scope binds every name, the procedure simplifies the expression to a literal wherever the dialect's rules can
fold the whole expression. When the scope binds some names, the procedure simplifies the expression to a residual
expression of the same dialect. When the scope binds no names, the procedure returns the expression itself, or a simpler
expression. Each dialect family's rules decide what folds ([CAP-295: simplification of single-dialect expressions with
literal leaves](CAP-295.md)).

The procedure never raises an error in a case where the language itself would not raise one. An error therefore raises
wherever the language would evaluate the subterm. Some subterms are ones that the language may never evaluate: the
branch that a conditional does not take, the right operand of a short-circuit operator, the body of a lambda, and the
operand of `sizeof`. When folding such a subterm raises an error, the subterm stays in the residual, and the error will
raise when something evaluates the residual. Each dialect declares which of its positions hold such subterms. [The
port's
API](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-simplification-for-the-users-review),
items 374 and 375, holds the detail.

## Decided by an agent, for review

- **(mbse-expressions 54, integration, API 374)** **Guarded subterms.** API item 328 says that an error "raises, as the
  expression would in its language". The coordinating session read that sentence exactly: an error raises only where
  the language would evaluate the subterm that raises it. A subterm that the language may never evaluate is called
  guarded. Two kinds of subterm are guarded. The first kind is a body in which the parent term binds names, except the
  body of a let, which the language always evaluates. The second kind is any argument that a dialect names through its
  `guarded(node, index)` function. The dialects name a conditional's branches, a short-circuit operator's right
  operand, the body of a lambda or an arrow function, the operands of `sizeof`, `alignof` and `_Generic`, the operands
  of C++'s `noexcept` and `typeid`, and the branches of Excel's `IF`. When folding a guarded subterm raises an error,
  the subterm stays in the residual, and the simplifier records no residue for it. When folding any other subterm
  raises an error, the error raises by default, as it does for `x + (1 + "a")` in Patterns. Whether such an error
  instead leaves its subterm in the residual is one of the options that
  [CAP-305: simplification's options, chosen up front](CAP-305.md) proposes. For example, `c ? 1 : null.a` stays in the
  residual when the scope does not bind `c`.
- **(mbse-expressions 54, integration, API 375)** **A known `undefined`.** TypeScript's simplifier wrote a known
  `undefined` value as `null`, because the default value of a constructor's parameter replaced the `undefined`
  argument. The parameter now has no default value, so the simplifier keeps a known `undefined` as `undefined`, as the
  Python implementation already did.
