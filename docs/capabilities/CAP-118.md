# CAP-118: singletons, owned and counted objects

*Implements* [FEA-026: deterministic object identity](../features/FEA-026.md). Index entry: [capabilities/README.md](README.md#CAP-118).

## As built: mbse-schemas

Met in mbse-schemas 0.20.0: the [store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md)'s 4c, the three modes in memory, released as 0.20.0.

### Three modes

A reference object is identified in one of three ways, which its schema's declarations select (Decided, 37):

| Mode | Declared by | Identity | Lifetime |
|---|---|---|---|
| Singleton | `.singleton(name)` | its path of no steps: its global name, the root of every path | the store's |
| Owned | an adjacency marked `owner()` | its path: the route from a singleton to it through the entries that own it | its owning entry's |
| Counted | neither | none of its own: within a document that writes it, its index in the order the document meets counted objects | the host language's: reference counted, collected once nothing holds it |

Value objects have no identity (9). Nothing is drawn at random: a path is computed from the model, a transaction's id
is given by the program (42 in [CAP-124: writes all-or-nothing in transactions](CAP-124.md#decided)), and a counted object is numbered by the document that writes it (55), so the same model
built twice, or in another language, gives the same identities and the same snapshots.

### What takes which mode

- **Singletons**, such as the root module and a directory such as `wts.Features`: by their global names, as before, each the path of no steps.
- **Owned**, through `owner()` adjacencies: named definitions of any kind (usually module scoped, owned by their module
  through `Schemas.Defines`), clauses of a definition and subclauses of a clause, and the instances of a program's
  schemas at the root level of its data model, owned by a singleton directory (37).
- **Counted**: expression terms, and most other objects (37).

There is no framework relation by which a schema owns its instances: `Schemas.HasInstance`, `OfObject.pattern` and the
generated `local-name-N` keys go (41). A schema's identity never becomes part of a path, though a schema object may be a
step in one, as any owner may (12, 30 in [CAP-123: schema objects identified by path](CAP-123.md#decided)); a schema's name is written only where an object is created, in
`Mutations.OfObject.Exists`, which must know what to build (8 in [CAP-119: owned objects found by path](CAP-119.md#decided)).

### Owned objects

`Schemas.OfAdjacency` has `owner()`. An adjacency marked `owner()` points back to the previous element of the object's
path: the object that owns it. The relation it designates has two links, the owner's and the owned's, and must

1. mark the owner link as unique, and
2. mark the owned link, along with any keys, as unique,

for example (the user's, in the builders' syntax):

```python
Directory = store.Schemas.OfObject(lambda o: o.name('Directory').ref(True).singleton('wts.Features'))
Definition = store.Schemas.OfObject(lambda o: o.name('Definition').ref(True))
Defines = store.Schemas.OfRelation(lambda r: (
    r
    .name('Defines')
    .links([
        lambda t: t.name('directory'),
        lambda t: t.name('defn'),
    ])
    .properties([lambda t: t.name('name').schema([store.Schemas.OfStr]).pattern(r'DEF-\d+\d\d')])
    .uniques([['directory', 'name'], ['defn']])  # a definition's one directory and name; they find one definition
))
store.Schemas.OfObject(Directory, lambda o: o.adjacencies([
    lambda t: t.name('dir').relation([Defines]).me('directory'),
]))
store.Schemas.OfObject(Definition, lambda o: o.adjacencies([
    lambda t: t.name('def').relation([Defines]).me('defn').owner(True),  # back to the previous path element
]))
```

A definition's path is then the singleton `wts.Features`, through `dir`, the entry named `DEF-693`, and `def` (Paths
as data). From the owner, the entry's keys select exactly one owned object, and an owned object has exactly one owner,
so a path resolves unambiguously.

Validation refuses an ownership relation of more than two links (14), and an `owner()` adjacency whose owning end a
counted schema can fill: nothing is owned by a counted object, so every path ends at a singleton (47).

`Schemas.Defines` already has this shape: it links a module to a schema with the entry's `name`, declared
`.uniques([["module", "name"], ["schema"]])`, [CAP-155: `unique` clauses on relation schemas govern relation cardinality](CAP-155.md)'s directory pattern. Modules and schemas therefore take part
like any other owned object: a schema's path runs from the root module through `Defines` entries, by name (17 in [CAP-123: schema objects identified by path](CAP-123.md#decided)). An
unnamed schema linked through a relation no key names (the container schema of `crm.Person.tags`, through
`Schemas.HasSchema`) is a subclause owned through that link, its step one with no keys (29 in [CAP-123: schema objects identified by path](CAP-123.md#decided)).

The peer shorthand's visitor is the union of an entry and the object it links: the entry's link and properties first,
then the linked object's members. An ownership entry's keys therefore hide the linked object's properties of the same
name, and `t.name(...)` writes the path where the relation declares `name` and the object where it does not. The
explicit form says which: `d.dir(lambda a: a.insert(lambda e: e.name('DEF-693').defn(spec)))`, where `e` is the entry.

### Ownership chains, settled

No chain to an object with a directory entry is needed for an owned object to be well-formed: settled by object identity 37 (Decided, below). An owned object is placed by its owning entry, and its path runs from a singleton through its ownership entries.

### Counted objects

A counted object has no identity outside the document that writes it (55). Nothing finds it except by visiting what
links it (40), and a later transaction reaches it the same way, through a symbol whose locator starts at an owned object
or a singleton and follows links, so no later transaction refers to it by a name. Within one document, a snapshot or a
Reachable transaction, it is numbered in the order the document meets counted objects, so that two links to it stay
one object and cycles close: a reference is `{"$ref": {"n": <index>}}`, beside `{"$ref": <path>}`, by which an owned
object and a singleton alike are referred to (a singleton's path has no steps). Reading the document gives each its own
new object; the numbers mean nothing after.

A counted object is created by a transaction, by a verb or through a symbol (a `Mutations.OfUpsert` of a putative
object in a mutation expression, [FEA-027: mutations as queries](../features/FEA-027.md)); a clone is a creation in the transaction
that clones (46 in [CAP-124: writes all-or-nothing in transactions](CAP-124.md#decided), 54 in [CAP-139: upserts find before they create](CAP-139.md#decided)). It lives while anything holds it, an object that links it or the program, as the host language
decides; the store does not keep it alive.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(object identity 9)** As the user decided later (2026-10-16), "I finally get what you are trying to communicate about UUIDs breaking some assumptions about reentrancy": "value objects still do not need an identity".
- **(object identity 10)** "all reference objects may need a computed name".
- **(object identity 11)** "singletons, such as the root module, will form the root of all paths to any non-singleton reference object".
- **(object identity 14)** "Schemas.OfAdjacency gains 'owner()' which if marked means the adjacency points back to the previous identity path
  element. The designated relation must (a) mark the owner link as unique and (b) mark the owned link along with any
  keys as unique. This should make path resolution unambiguous.", with `Defines` as Ownership gives it:
  `.unique('directory', 'name').unique('defn')`, [CAP-155: `unique` clauses on relation schemas govern relation cardinality](CAP-155.md)'s directory pattern.
- **(object identity 20)** A "non-singleton reference object whose schema has no owner() adjacency: validation rejects the new reference
  object schema not having an ownership path". (Superseded by 37: such an object is counted.)
- **(object identity 21)** "Every reference object must participate in this process via an ownership adjacency: named definitions of any
  kind (usually module scoped), clauses of a definition, subclauses of a definition clause". (Narrowed by 37: most
  other objects, expression terms among them, are counted.)
- **(object identity 31)** A reference object whose schema declares no `owner()` adjacency is owned by its schema, through a framework
  relation shaped as `Schemas.Defines` is, `Schemas.HasInstance`, linking a schema to its objects with the entry's
  `name`, generated where none is given ("yes to HasInstance"). A contact's path is then the root module, `crm`,
  `Contact` (through `Defines`) and the entry named `contact-6` (through `HasInstance`), on the wire:

  ```json
  {"singleton": ".", "next": {"entry": {"i": "schemas", "o": "", "properties": {"name": "crm"}, "next": {"entry": {
    "i": "schemas", "o": "", "properties": {"name": "Contact"}, "next": {"entry": {
      "i": "instances", "o": "", "properties": {"name": "contact-6"}, "next": {"target": {}}}}}}}}}
  ```

  So 20 applies where a schema has neither an `owner()` adjacency nor a schema to be owned by: none, as built.
  (Superseded by 37: such an object is counted; `HasInstance` goes.)
- **(object identity 37)** As the user decided (2026-10-18), on the overhaul so far: "The overhaul we did on object identity was mostly a good idea. And I get that there are problems with repeatability with UUIDs. However, I think the idea of eliminating the entire use case of reference-counted objects is a mistake." "We need options, and I am skeptical of the HasInstance relation": Identity by kind of object:
  - "schema singletons : same as before, explicit object identity";
  - "schema definitions : yes, via the new `owner` adjacencies";
  - "schema definition clauses and sub-clauses : yes, via the new `owner` adjacencies";
  - "expression terms : should be reference counted";
  - "instances program-defined schemas at the root level of their data model : yes, via the new `owner` adjacencies";
  - "most other objects : reference counted".

  This supersedes 19 in [CAP-124: writes all-or-nothing in transactions](CAP-124.md#decided) (a UUID per transaction returns), 20 and 21 (a reference object without an ownership path is
  counted, not refused), and 31, 33 in [CAP-120: owned objects named and placed when built](CAP-120.md#decided) and 34 as far as they concern `Schemas.HasInstance`, which goes (see Open
  questions, 1).
- **(object identity 39)** A counted object's name within its transaction is its "creation order index within the transaction". (Superseded by 55.)
- **(object identity 40)** "counted objects cannot be directly found programmatically only via visitor".
- **(object identity 41)** As the user decided (2026-10-18), on the questions 37 to 40 left: `Schemas.HasInstance`, `OfObject.pattern` and the `local-name-N` keys: "yes, they all go" (superseding 31, 33 in [CAP-120: owned objects named and placed when built](CAP-120.md#decided)'s
  `HasInstance` case, and 34 in [CAP-120: owned objects named and placed when built](CAP-120.md#decided)). A key is generated only by an ownership relation's key property's pattern (13 in [CAP-120: owned objects named and placed when built](CAP-120.md#decided)).
- **(object identity 47)** "correct, nothing can be owned by a counted object nor can an ownership path proceed through any relation with more
  than two links": validation refuses an `owner()` adjacency whose owning end a counted schema can fill, as 14 already
  refuses an ownership relation of more than two links.
- **(object identity 55)** As the user decided (2026-10-19), asked "Do we really need to record the outcome of sharding?", on the answer that nothing beyond one document needs a counted object's identity ("yes, please"): A counted object has no identity beyond the document that writes it: within a snapshot or a Reachable transaction it
  is numbered in the order the document meets counted objects, a reference `{"$ref": {"n": <index>}}`, and reading
  gives each a new object. No later transaction names one; it reaches it through what links it (40). This supersedes
  39 and 49 in [CAP-128: graphs sent as one-transaction documents](CAP-128.md#decided), and 54 in [CAP-139: upserts find before they create](CAP-139.md#decided)'s naming by symbol, which is a mutation expression's, not an identity.
- **(object identity 79)** As the user decided (2026-10-20), on expression terms and schema paths: Recursive expression terms ("yes"): a term is a counted reference object, linked to the terms it holds through
  relations, so that recursion goes through links, which 72 allows; mbse-expressions adapts in 4h. (Amended by 82: a
  term tree may be a recursive value.)

- **(framework design)** **Reference identity** ([Visitor pattern](CAP-107.md), "Reference Identity", as the user wrote it), refining
  The visitor pattern's "global name, otherwise a UUID" (superseded since 0.20.0 by [Object identity](../features/FEA-026.md),
  Decided, 1 to 36: an identity is the object's path, read off its ownership; there are no UUIDs, an object its schema
  owns being keyed by its local name and a number where it has no naming pattern; `by_identity` gives way to lookup by
  keys; a snapshot lists each object with its path and its schema's name, and a reference is its path alone; and in
  turn since 0.20.0 by its Decided, 37 to 55: an object is a singleton, owned, or counted, a counted object having no
  identity beyond the document that numbers it; `Schemas.HasInstance`, naming patterns on object schemas, the
  local-name-and-number keys, `as_identity` and `Stores.Store.restore` are gone):
  - a reference object with a global name (`.singleton("foo")`) uses it on the wire; a reference object schema may
    instead give a naming pattern to `.ref()` (`.ref(r'FEA-(\d+\d\d)')`, the number "extend[ing] on the left"); one
    declared with `.ref()` alone has a UUID given by `.create()` or `.clone()`; on the wire every identity is
    "qualified with the schema's registered name and module name", a qualification "only appropriate for over the
    wire"; `validate()` refuses a schema with both a global name and a naming pattern;
  - "The choice of formatted name and registration with the implied directory must happen automatically anytime a
    named reference object is created or copied" ("No user serviceable parts inside"): "there is one directory store
    per schema", "one directory per schema within each store"; "allocated IDs are strictly increasing (even in the
    presence of yet to be designed deletions)", so loading a snapshot advances a schema's counter past every ID it
    reads ("yes");
  - programs read an identity through `Visitors.OfObject.as_identity` and find an object by `Stores.by_identity`
    (its arguments below); they "cannot set or modify their identity", so decoding is the one writer of a loaded
    object's identity, and "on snapshot load, repeated appearance of the same ID is interpreted as update";
  - the qualified form is the schema's registered name, `/`, then the name (`"crm.Feature/FEA-001"`), a global name
    written alone, being unique in a store ("that is fine"); `by_identity` finds every live object of the store, through a
    weak directory, not only its data ("yes, every live object");
  - `as_identity()` and `by_identity` both take the unqualified name, "at the cost of prepending a schema parameter to
    by_identity": `store.by_identity("crm.Feature", "[FEA-001: schema-driven UI](../features/FEA-001.md)")`;
  - in snapshots, identities replace the symbols, as the objects' keys and in `$ref`, and references keep `$schema` ("okay
    to keep $schema for now");
  - a UUID is random, so where output must be reproducible (the conformance corpus, tests of exact text, the tutorials'
    outputs) schemas take naming patterns, whose counters are deterministic, and UUIDs are tested by their shape and
    round trips ("a"), rather than stores drawing UUIDs from a seeded source, which "a random source is given to
    whatever draws from it, not held by a store" rules out;
  - on update, "merging should naturally fall out of the builder pattern. property access should notice that the
    pre-existing object already has that property and return a builder on that property, etc.": decoding writes into
    a live object through its builder, editing a property's value object in place, and what the snapshot omits is
    kept, not cleared. Reloading must not add entries ("reloading them adds entries is not desirable"), and entries
    without a key are matched by "overwriting what is present in the order being co-visited". Until relations were
    split from containers (Containers, above; one-link relations are gone, and a container is rewritten element by
    element), that held for one-link relations, whose entries are their owner's alone and whose order a snapshot
    carries: the i-th row overwrites the i-th entry held, in the order a snapshot writes
    them, and rows past those are added. A relation of two links or more has no order to co-visit, an entry sitting
    in a list at each end, so a row is the entry held that agrees with its links and properties, the k-th equal row
    the k-th such entry, and is added where none agrees ("finish V4 that way"). Builders keep every object's entries
    in their order through an update, so that positions hold;
  - "for value objects as_identity should return None", and so does any visitor without an identity (an empty one, a
    builder of an object not yet created): "it feels like None/null is a better representative of no identity, but I
    don't have a strong opinion", so it was taken.
  The choices the agent made in building it (naming patterns, `Stores.Store.restore`) went with it, superseded.
- **(framework design)** Identity, from "Refinement, identities and relations" ([CAP-167: schemas refined by other schemas](CAP-167.md#decided)): a program could set an identity through `as_identity`.
