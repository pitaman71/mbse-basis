# CAP-240: conflicting layout rules ignored and requeued

*Implements* [FEA-056: fungible diagramming keeps agents and humans in the loop](../features/FEA-056.md).

Of two trivially incompatible rules, the later is ignored and queued, and a mutation that lifts the conflict reapplies
the queued rules in order: in Python and TypeScript for container layout, in TypeScript for physical layout.

## Design

As [the diagrams proposal](../../proposals/DIAGRAMS.md) states it. For container layout, mbse-diagrams'
[pull request 4](https://github.com/pitaman71/mbse-diagrams/pull/4) builds it, `Framework.Container`'s rules and their
settling, in both languages, with suite CNF. For physical layout, it waits for physical layout itself,
[CAP-242: incremental physical placement](README.md#CAP-242): until then, this capability is not met.

## Decided

The user's decisions (2026-11-05), in review of mbse-diagrams#4:

- **The container layout processes mutations, never the model.** On `layout` placing the children and specs a
  container already had: "It feels like layout already violates the no-snapshots rule." A container is given its grid
  before its children, which reach it afterwards, each as a mutation, and settling starts from what a mutation
  touched, not from every rule.
- **Tests are mutation sequences, each mutation a transaction expression**: "1 and 2 yes", to tests whose steps are
  each a mutation of the data model, as a transaction expression, the declarative, journalled form, followed by the
  container model's adjustments to it, "where |adjustments| >= |steps|".
- **A page to step through them, in three columns**, the data model, the container model and the container layout,
  each "reserve the bottom 25% to show the current mutation and use the top 75% to show the state of the model with
  the mutation's changes highlighted"; "the third column shows the resulting container layout". It is mbse-diagrams'
  `python3/tools/container_trace.py`, Python only: "Equivalence across languages is not strictly necessary."

## Decided by an agent, for review

Where this capability and the proposal were silent, the simplest default consistent with them, with
[CAP-238: container schemas and grid insertion](CAP-238.md) and [CAP-239: grid adjacency](CAP-239.md)'s decisions and with mbse-schemas, each *proposed* until reviewed, labeled with
the repository and number it was decided under.

- **(mbse-diagrams 4, mbse-diagrams 6)** **A container layout's rules** are reference objects, `Container.OfRule`, as
  the user's "relations are not reference objects" asks of what has state of its own: each owned by its grid, in the
  order it reached the grid (`Container.Rules`), enforcing one adjacency spec (`Container.Enforces`), and `ignored`
  where the grid cannot meet it. The queue is the ignored rules, in that order.
- **(mbse-diagrams 4)** **"Later"** is later in that order, which is the order of the mutation sequence that added the
  specs.
- **(mbse-diagrams 4)** **Settling, by induction.** The grid held every rule but the ignored before a mutation, so
  after it only the rules it touched, a new one and the ignored are checked, in the order they reached the grid: each
  kept where it holds; where it does not, met by one change of the sequence, CAP-239's, that breaks none of the kept
  rules that change disturbs; where none can, ignored. The shapes a change moves are touched in turn, for the rules
  after it. An ignored rule is tried again, in its turn, after every mutation.
- **(mbse-diagrams 4)** **Adjustments are data.** Each function returns its adjustments, in order: a grid made, a shape
  placed, moved or leaving its cell, a rule held, met, ignored or dropped, the extents changed, the cells turned. A
  mutation makes one at least. Replayed in a fresh store, a mutation sequence makes the same adjustments.
- **(mbse-diagrams 4, mbse-diagrams 6)** **A removal is anticipated.** A child's removal deletes it and its rules,
  and a spec's removal its rule, so the container layout adjusts before the mutation, with `removing(child)` and
  `unjoining(spec)`, while they still exist, as the proposal's "anticipate the effect those mutations have on the
  previous layout state".
- **(mbse-diagrams 4)** **"Trivial" incompatibility** is what one such change cannot resolve: a rule whose one change
  would break an earlier rule that holds, or that the grid's extents leave no room for. Incompatibilities that only
  several changes together could resolve are not sought.
- **(mbse-diagrams 4)** **Reverting** a child once a spec to it is removed happens only where that spec's rule held, and
  placed it; an ignored rule's removal moves nothing.
