# CAP-183: modeling system interactions as modules, interfaces, ports, implementations, instances and channels

*Implements* [FEA-009: layered interaction models](../features/FEA-009.md). *Relates to* [CAP-028: layered interaction models](README.md#CAP-028), [CAP-041: every kind of participant](README.md#CAP-041), [CAP-182: modeling system structure as containers, axes and containment](CAP-182.md).

## As built: mbse-sysarch

Met in mbse-sysarch 0.1.0, Python only, on mbse-schemas 0.22.0: checked in the code at 0.1.0
(`mbse.Architecture.Systems.Framework.Interactions`; the INT, CHK and SER suites). `Interactions.define(store)` builds
the package in the caller's store, after Structure's, as
[the design's Interactions table](https://github.com/pitaman71/mbse-sysarch/blob/main/docs/SYSARCH.md#interactions)
gives it: a library that owns its modules by name, a module its interfaces and an interface its ports, so that each
has a path from the library; implementations of a module, whose named instances of other modules cooperate over named
channels, each carrying messages of one value schema from its sources to its destinations. `Interactions.Check()(root)`
lists what no `unique` clause expresses. The schema `Interactions.HasSchema` is not mbse-schemas' meta relation
`Schemas.HasSchema`; the two are always written qualified.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **The plan, as the user wrote it**, under "System Architecture + Interaction Models":

  > Repo: `mbse-sysarch`
  >
  > Files:
  > - `mbse-sysarch/python3/mbse/Architecture/Systems/Framework/Interactions`
  >
  > OBJECT denotes mbse-schemas.Schemas.OfObject (ref)
  > RELATION denotes mbse-schemas.Schemas.OfRelation (ref)

  Its composition, a channel's distribution across several destinations configurable and BROADCAST by default:

  > - OBJECT Interactions.Module # nameable, instantiatable, addressible component
  > - OBJECT Interactions.Interface # place where messages exist relative to a containing Module
  > - RELATION Interactions.HasInterface(module,name,intf)
  > - OBJECT Interactions.Port # optional designation of the sides/senses of an interface
  > - RELATION Interactions.HasPort(module,name,intf)
  >
  > - OBJECT Interactions.Implementation
  > - RELATION Interactions.Implements(impl, module)
  >
  > - OBJECT Interactions.Instance # structural instance
  > - RELATION Interactions.HasInstance(impl, name, instance)
  > - OBJECT Interactions.Channel # directional carrier of messages between source and destination interface(s) whoses messages' type is provided as a schema. Distribution semantics across multiple destinations are configiurable and default to BROADCAST. 
  > - RELATION Interactions.HasChannel(impl, name, channel)
  > - RELATION Interactions.HasSchema(channel, schema)
  > - RELATION Interactions.Connects(channel, intf, port)
  >
  > - Interactions.Implementation # a realization of a module using asynchronously cooperating submodules

- **While building it**, recorded in [mbse-sysarch's design, Resolved](https://github.com/pitaman71/mbse-sysarch/blob/main/docs/SYSARCH.md#resolved):
  the repository and its scope, Python only for now (item 1); implementations and instances are containers (item 4);
  `HasPort(intf, name, port)`, an interface owning its named ports (item 6); a channel attached to a port, which
  carries the direction, through `Connects(channel, instance, intf, port)` (item 7); a channel's message schema a
  relation to the schema object (item 8); and a library that owns the modules (item 9).

## Decided by an agent, for review

Recorded in [mbse-sysarch's design, Resolved](https://github.com/pitaman71/mbse-sysarch/blob/main/docs/SYSARCH.md#resolved),
items 10 to 16, not marked as the user's: each *proposed* until reviewed. Those most worth reviewing:
`Interactions.Instantiates(instance, module)`, which the plan does not list (item 10); the implementation filling
`Connects`' `instance` at its module's boundary (item 11); the distributions `"BROADCAST"`, `"ANYCAST"` and
`"ROUND_ROBIN"` (item 12); and a module named only by its library entry (item 14).

## Open questions

Paths below the module, an interface without ports, an instance's two names, directions beyond in and out, which
distributions are wanted, choosing an implementation for an instance, TypeScript, and a port to mbse-diagrams for
rendering: [mbse-sysarch's design, Open questions](https://github.com/pitaman71/mbse-sysarch/blob/main/docs/SYSARCH.md#open-questions).
