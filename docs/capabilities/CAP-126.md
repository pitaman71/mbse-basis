# CAP-126: schema objects read through the store protocol

*Implements* [FEA-037: the framework built on its own protocols](../features/FEA-037.md). Index entry: [capabilities/README.md](README.md#CAP-126). *Relates to* [FEA-028: one API surface for all data access](../features/FEA-028.md), [CAP-136: one finisher for every build](CAP-136.md).

## Design

Not built: mbse-schemas reads schema objects outside the protocol, field by field, in about 300 field reads in each
language (`Proxies`, `Plain`, `Transactions`, `Builders`, `Validators`, `Comparison`, `Paths`, `Adapters`). It was the
[store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md)'s 4k, taken out of its step 4 as tech
debt, with the commit-time rule kept (Decided, below). Their updates within a transaction are a `Proposals`' still
(96 in [CAP-124: writes all-or-nothing in transactions](CAP-124.md#decided)).

### The commit-time rule

Whatever is built keeps the rule: a change to a schema object that existed before a transaction is seen only once
that transaction commits (Object identity, Decided, 96 in [CAP-124: writes all-or-nothing in transactions](CAP-124.md#decided)), and data that uses the change is
written in a transaction after it.

### Options

The survey of 4k (2026-10-23) found three. None short of retiring the dataclasses changes the public read API
(`as_schema()`, `store.registered(...)` and field reads).

- **Schema state through `Visitors.OfStore`**, copied on write as `values` and `entries` are, replacing the
  deferred-builder mechanism (`_defers`, `_pending`, `Proposals.deferred`): moderate, about one to one and a half
  weeks, with a low performance risk and no change of API. It simplifies the code the single finisher replaces, so it
  is coordinated with [CAP-136: one finisher for every build](CAP-136.md), so that schema building is not rewritten twice.
- **Through read-only builders**: large, with a high performance risk, since a builder copies its object's fields.
- **Schema objects as store data (proxies)**, the dataclasses retired: very large; it breaks every public read and
  contradicts the meta-schemas' design ("The data are not proxies", [CAP-109: schemas as linked objects in modules](CAP-109.md)); only together
  with the single finisher and such a redesign.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(object identity 100, its tech-debt clause)** Schema objects are read outside the protocol, field by
  field, for the time being: "that is acceptable for the time being. Retain as tech debt".
- **(store overhaul 32)** As the user decided (2026-10-26), after the survey: "yes keep the commit-time rule and log 4k
  as tech debt". The commit-time rule is the lasting rule, not a limitation awaiting 4k; reading schema objects
  through the store is internal tech debt, done without changing it.
