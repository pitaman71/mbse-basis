# CAP-254: an install's uid changed with its content

*Implements* [FEA-032: schema loading and wire alignment](../features/FEA-032.md). *Relates to* [CAP-115: schemas defined by idempotent installs](CAP-115.md).

## Design

Not built. Each install runs under a fixed transaction uid, such as mbse-expressions'
`mbse.Expressions.C.Expressions/1`, and each `define` under its own (`mbse.Expressions.IEEE754.Expressions.define/1`).
When an install's content changes, its uid stays `/1`: mbse-expressions' domains as data, stage 1, changed what
Patterns' and Python3's installs write without changing their uids. A store that ran an install's earlier content,
or a journal that recorded it, is not shown to apply the new content correctly: whether it is applied, skipped as
already run, or conflicts is not established, and no rule says when a uid changes. This capability is that tech debt:
an install's uid, or whatever identifies what it writes, changes with its content, so that a store holding an
earlier install is brought to the new one, or refused, never silently left behind.

## Open questions

- What identifies an install's content: a version in its uid (`/2`), a digest of its schemas, or the package's
  version.
- What a store holding an earlier install does: upgrade in place, refuse, or report.

## Decided

- **Logged as tech debt** (2026-11-09): raised by the review of mbse-expressions#27 (its question 6: "The install uids
  stay `/1` although Patterns' and Python3's install content changed. Does anything rely on that?"); the user: "this
  is an important question, but not priority. find a place to store it as tech debt".
