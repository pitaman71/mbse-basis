# CAP-313: parameter references valid where their parameters are assigned or bound

*Implements* [FEA-033: model parameters](../features/FEA-033.md). *Supersedes* [CAP-181: parameters wherever literals may appear](CAP-181.md) and
[CAP-314: parameters assigned or bound by the data objects their schema governs](CAP-314.md). *Relates to* [CAP-312: a parameter reference in place of anything with a schema](CAP-312.md),
[CAP-114: parameter bindings are substituted and checked](CAP-114.md), [the parametrics proposal](../../proposals/PARAMETRICS.md#validated).

Validation takes a parameter context, and reports one of three results for the parameter references in what it
validates: invalid, partial and valid, or bound and valid. A dialect defines its own statements that assign or bind
parameters, and its procedures interpret them.

## Decided

As the user decided, besides the decisions the parametrics proposal records:

- **Validation takes a parameter context**: "The validation routine needs to take a parameter context, which I think we
  elsewhere defined as a map from parameter names to the object or symbol to which it is bound. As validation proceeds
  recursively if it encounters a binding statement it can create a sub-context. It's pretty standard." The parameter
  context is an argument of the validation procedure, and nothing more: "parameter context is an argument to the
  validation procedure and that is that".
- **Three results, and no option**: "invalid, partial (and valid), bound (and valid)", and "if you provide those three
  result codes the option is unnecessary". Validation reports what it finds, and its caller decides what to accept.
- **Dialects define what assigns or binds a parameter**: "I don't know that we need a generic
  `Parametrics.AssignsValue` and `Parametrics.BindsObject` separate from a term object. Rather perhaps this is a schema
  pattern that dialects should define and which procedures (validation, simplification, comparison, etc.) should
  interpret." Asked whether this was the direction meant: "yes this is the direction I mean".

## Design

- **The parameter context.** A parameter context maps each parameter's name to the value assigned to it, or to the
  object or symbol bound to it. Validation takes it as an argument, and a caller that gives none gives an empty one.
- **What assigns or binds a parameter.** A dialect defines its own statements that assign a parameter a value or bind it
  to an object, as it defines its other terms. mbse-schemas defines none. The dialect's procedures interpret them:
  where one of them meets such a statement, it makes a sub-context, in which the statement's parameters map anew and
  hide the same names outside, and passes the sub-context down.
- **The three results.** A parameter reference at a place that expects schema S is:
  - **invalid** where the context maps its parameter to something of the wrong kind, a value where the place expects an
    object or an object where it expects a value, or to something of another schema than S;
  - **partial**, and valid, where the context does not map its parameter;
  - **bound**, and valid, where the context maps its parameter to a value or an object of S.

  What validation validates is invalid where any parameter reference in it is invalid, partial where none is invalid
  and one is partial, and bound where every parameter reference in it is bound.
