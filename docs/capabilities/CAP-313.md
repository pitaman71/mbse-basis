# CAP-313: parameter references valid where their parameters are assigned or bound

*Implements* [FEA-033: model parameters](../features/FEA-033.md). *Supersedes* [CAP-181: parameters wherever literals may appear](CAP-181.md). *Relates to*
[CAP-312: a parameter reference in place of anything with a schema](CAP-312.md), [CAP-314: parameters assigned or bound by the data objects their schema governs](CAP-314.md),
[CAP-114: parameter bindings are substituted and checked](CAP-114.md), [the parametrics proposal](../../proposals/PARAMETRICS.md#validated).

A parameter reference is valid where its parameter context assigns its parameter a value, or binds it to an object, of
the schema that the place holding the reference expects. Validation reports it as invalid where the context neither
assigns nor binds its parameter, and where the context assigns or binds it to something of another schema.

## Decided

As the user decided, besides the decisions the parametrics proposal records:

- **Validation takes a parameter context**: "The validation routine needs to take a parameter context, which I think we
  elsewhere defined as a map from parameter names to the object or symbol to which it is bound. As validation proceeds
  recursively if it encounters a binding statement it can create a sub-context. It's pretty standard." A parameter
  context maps each parameter's name to the value assigned to it or the object or symbol bound to it.

## Design

- **The context a caller gives.** Validation takes a parameter context, empty unless the caller gives one, so that
  validating one object can resolve the parameters that its owners, or an application, assign or bind.
- **Sub-contexts.** Where validation, descending through the data, meets a data object that holds parameter
  assignments or parameter bindings, through `Parametrics.AssignsValue` or `BindsObject`, it validates what that object
  holds in a sub-context. In the sub-context, those parameters' names map to the object's values and objects, and they
  hide the same names in the context around it. What encloses a parameter reference is therefore whatever validation
  passed through to reach it.
- **Checking a reference.** A parameter reference at a place that expects schema S is valid where the context maps its
  parameter's name to a value or object of S, and invalid where the context maps it to something else, or does not map
  it. A parameter assignment's value is checked against its parameter's `ForValue` schema, and a parameter binding's
  object against its parameter's `ForObject` schema.
- **Unknown.** Data whose schema depends on a parameter that its context leaves unassigned and unbound is neither valid
  nor invalid there: validation reports it as unknown.
- **In mbse-expressions.** Its simplifier's scope (`Symbolics.Scope`, whose `bind` gives a sub-scope) is a context of the
  same kind. mbse-schemas holds its own parameter context, because mbse-expressions depends on mbse-schemas and not the
  reverse.
