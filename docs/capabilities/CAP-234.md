# CAP-234: an object no entry owns deleted

*Implements* [FEA-026: deterministic object identity](../features/FEA-026.md). *Relates to* [CAP-121: owned objects deleted in cascade](CAP-121.md).

## Design

Not built, and not yet in priority scope (the user, 2026-11-03). Removing an owned object's owning entry deletes it
([CAP-121: owned objects deleted in cascade](CAP-121.md)); an object that no entry owns has no entry to remove, so
deleting it needs a way of its own. mbse-schemas' tutorial 9 shows the gap. As the user put it, it is "a
straightforward reference counting problem over relation entry links": what decides is how many relation entries
link the object.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **Deferred past step 4 of the store overhaul** (2026-10-22): "4j : implement removing entries, but defer deleting
  objects to a later phase".
- **Needed, later** (2026-11-03), settling the store overhaul's open question of whether it is needed at all (its
  Decided, 27): "I think CAP-234 is needed, just not now. Also, it's a straightforward reference counting problem over
  relation entry links".
- **A tech debt of mbse-expressions linked here** (2026-11-10), as the user approved ("yes"), that a debt an existing
  capability already covers is linked to it rather than made a capability of its own: its test stores accumulate
  counted `Expressions.Framework.Expression` objects, reference objects no entry owns, which nothing deletes (checked
  in its main at 3711f8a).
