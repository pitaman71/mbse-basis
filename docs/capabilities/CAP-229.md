# CAP-229: the C expression dialect

*Implements* [FEA-024: expressions as data](../features/FEA-024.md), [FEA-008: expressive program models](../features/FEA-008.md). *Relates to* [CAP-226: complete expression dialects](CAP-226.md), [CAP-230: the C++ expression dialect](CAP-230.md), [CAP-100: six languages' expression dialects](CAP-100.md), [CAP-036: complete kinds for Python, TypeScript and C and C++](CAP-036.md), [CAP-093: every construct of C's and C++'s standards](CAP-093.md), [CAP-091: Ccpp expressions bridged to C and C++ source](CAP-091.md).

## As built: mbse-expressions

Built in mbse-expressions' stage 5 of [the complete dialects](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/dialects/README.md#stages)
(PR #19 and its follow-up, PR #23) and released in 0.8.0 (v0.8.0, at ff7c762), in both languages; every choice made
where the decisions were silent is in [the port's API, Settled in stage 5 (C and Cpp)](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-stage-5-c-and-cpp-for-the-users-review),
items 87 to 107, which hold the detail this section only bridges. `C`, `Expressions.C.Expressions` since the namespace
rename ([CAP-226: complete expression dialects](CAP-226.md#decided), Decided), is a complete dialect by
[CAP-226: complete expression dialects](CAP-226.md)'s rules: every expression of C11, C17 and C23 (ISO/IEC 9899,
6.5), in mbse-programs' Ccpp names and shapes, separate from [CAP-230: the C++ expression dialect](CAP-230.md); with
it, it replaces the Ccpp dialect ([CAP-100: six languages' expression dialects](CAP-100.md)). Reading C's every
construct is [CAP-093: every construct of C's and C++'s standards](CAP-093.md)'s, and a bridge to C source
[CAP-091: Ccpp expressions bridged to C and C++ source](CAP-091.md)'s.

- **The kinds**: `Expressions.C.Expressions.Term` has 25 branches, each a value object
  `Expressions.C.Expressions.<Name>` with mbse-programs' properties in source order, tagged by its name lowercased
  (`binaryexpression`, `castexpression`): among them `genericselection`, `compoundliteralexpression`,
  `initializerlist` and `designatedinitializer`, GNU's `statementexpression` and `extensionexpression`, `typeid`, and
  the framework's `error` and `missing`. They replace the nine kinds C held before (item 87). C defines its own copy of
  each kind it shares with C++, holding its own terms (item 89). Each kind records as data the standards that have it,
  C11, C17 and C23 (`constant` C23's alone, GNU's extensions none) (item 95): since 0.9.0, as the editions C's `define`
  covers, ISO/IEC 9899:2011, 2018 and 2024 ([CAP-268: standards as tagged data](CAP-268.md)).
- **Names**: an identifier used as an expression is the framework's `variable`, as C's grammar has a plain identifier
  expression (Decided, below); every other name is an `identifier` node, `Expressions.C.Expressions.Identifier`, the
  one branch of C's `Name` union, wherever mbse-programs has a name node (item 88).
- **The sublanguages and helpers**: `Type`, a type name (`typeid`) or invalid syntax, which `Term` lists too for the
  positions that hold an expression or a type alike (`sizeof(int)`, `_Generic`'s controlling operand); `Pattern`,
  invalid syntax alone, held by nothing (Decided, below); the helpers' unions named after mbse-programs' categories
  (`Name`, `Specifier`, `Declarator`, `Parameter`, `AttributeSpecifier`, `Designator`, `Initializer`), read by the
  framework as `Terms.Part`s (item 89).
- **Constants**: `Expressions.C.Expressions.Literal` refines the framework's
  ([CAP-167: schemas refined by other schemas](CAP-167.md)) and adds what its text encodes, `prefix`, `quote`, `base`,
  `separators` and `suffix` ([CAP-233: literals of any value](CAP-233.md)); a prefix or a suffix C does not write, and
  an integer no type its suffix and base allow can hold, is a problem. C's `constant` holds C23's `nullptr` (item 90).
- **Bodies**: a statement expression's is not held, and is printed `{}`; a struct's, a union's or an enum's is said by
  `body`, a bool (item 93).
- **Writers**: `literal`, `identifier`, `unary`, `binary`, `conditional`, `cast`, `member`, `subscript` and `call`
  are kept, writing the complete kinds, for code generation (Decided, below; item 94).
- **Printing**: `Text.ToText` ports mbse-programs' printer, byte-identical in both languages, by C's precedence
  (item 97); `FromText` is mbse-programs' ([CAP-226: complete expression dialects](CAP-226.md#decided), Decided).
- **Completeness as data**: `grammars/c-tree-sitter.json` maps each of tree-sitter-c 0.23.6's 125 named node types to
  a kind, a branch of `Type` or a helper, or lists it as not an expression with its reason. DIA-26 checks it in both
  languages, DIA-24 the kinds, DIA-25 printing, and DIA-11 and DIA-12 C's kinds and evaluation; the corpus's `c` case
  holds every kind (items 100 and 103).
- **Domains as data** (0.9.0): C's `define` writes the types C's standard fixes, `bool`, `int8_t` to `int64_t`,
  `uint8_t` to `uint64_t`, `_Float16` to `_Float128`, `_Decimal32` to `_Decimal128` and `nullptr_t`, as stored domains
  ([CAP-097: value domains of published standards](CAP-097.md#value-domains)); every other type a C term reads is the
  ABI's its holder names, and C's evaluation, inference and validation read each named type from the stored domains
  through the holder, its code type tables gone
  ([CAP-267: C and C++ terms read under the ABI their holder names](CAP-267.md)).
- **Evaluation stays shallow**, as decided ([CAP-226: complete expression dialects](CAP-226.md#decided), Decided):
  what C evaluated keeps evaluating in its complete shape, a literal typed by its suffix and base (since 0.9.0, a
  lookup of the stored domain, Decided, below), and every other kind is refused by name (item 96). Patterns <-> C keeps what it translated, one rule set with Patterns <-> Cpp (item 98).

## Decided

As the user decided (2026-11-04, following up stage 5,
[the proposal's Decided](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/dialects/README.md)):
adopted, each the rule as stated, quoted where the wording matters.

- **C keeps the framework's `variable`.** Shown "C++ uses only `idexpression`, mbse-programs' one kind, so `variable`
  isn't listed in C++'s union... C keeps `variable`, since C's grammar has a plain identifier expression", the user:
  "1, 2: confirmed". A C++ term in C is refused.
- **Nothing holds C's `Pattern`.** Shown "C's `Pattern` exists but nothing holds it, and the record says why: C
  expressions bind no names", the user: "3 = (a) is fine". `Expressions.C.Expressions.Pattern` is invalid syntax alone.
- **C's writers stay, for code generation**: "4. for codegen, we keep the writers separately because they emit code
  not just wire format for the model". They are kept beside the builders through which every other term is written
  ([PRI-019: fluent builder syntax](../PRINCIPLES.md#PRI-019)).
- **Typing C literals by suffix, before domain inference** (2026-11-04, on mbse-expressions' domains as data, its
  question 5, an open question from #19's review): "1,5. yes before per your recommendation": kept, as a lookup of the
  stored domain by the literal's suffix and base, the tables of which names a suffix allows staying the rule, as C's
  standard gives it: it is what the old typed constant did, and it is a lookup, not inference
  ([CAP-232: domains inferred for terms](CAP-232.md)). Which ABI the types are read under is
  [CAP-267: C and C++ terms read under the ABI their holder names](CAP-267.md#decided)'s.

## Decided by an agent, for review

Recorded in [the port's API, Settled in stage 5 (C and Cpp)](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-stage-5-c-and-cpp-for-the-users-review),
items 87 to 107, not marked as the user's: each *proposed* until reviewed. Those most worth reviewing:

- **(mbse-expressions port, API 90)** **A character's quote is C's spelling**: `'a'` is an `int` in C, as `97` is, so
  its quote is spelling there, and not in C++, where `'a'` is a `char`. A prefix and a suffix are what a literal is,
  not its spelling: two literals of one value and different suffixes are different terms.
- **(mbse-expressions port, API 94)** **A cast's type is written through the builders**, a spec of the dialect's
  `Type`: the writer does not read a type name from a string, which would guess whether each word is a keyword or a
  type's name ([PRI-025: never guess the schema](../PRINCIPLES.md#PRI-025)).
- **(mbse-expressions port, API 95)** **A feature within a kind is not recorded** (C23's `typeof`, `alignof` beside
  `_Alignof`): whether a term is in a standard is a constraint, to come.
- **(mbse-expressions port, API 101)** **Invalid syntax in every sublanguage**: every dialect's `Type` and `Pattern`
  list `error` and `missing`, superseding API 71
  ([CAP-228: the TypeScript5 expression dialect](CAP-228.md#decided-by-an-agent-for-review)).

Recorded in [the port's API, Settled in domains as data's stage 3](https://github.com/pitaman71/mbse-expressions/blob/main/docs/proposals/port/API.md#settled-in-domains-as-datas-stage-3-for-the-users-review), items 131 to 139, not marked as the user's:
each *proposed* until reviewed, C++'s alike ([CAP-230: the C++ expression dialect](CAP-230.md)); those of the ABI
lookup are [CAP-267: C and C++ terms read under the ABI their holder names](CAP-267.md#decided-by-an-agent-for-review)'s.
Those most worth reviewing:

- **(mbse-expressions 30, domains as data, API 137)** **A type lookup's failure is a problem in validation**, and raised in
  inference and evaluation.
- **(mbse-expressions 30, domains as data, API 137)** **A cast to a single identifier neither dialect defines is a
  program's own type**, not arithmetic, once the holder names an ABI; a name C's keywords spell must be defined.
- **(mbse-expressions 30, domains as data, API 137)** **The stored floating and character types evaluate**: `_FloatN`,
  the decimal types and `L'a'` in their formats, a decimal with a binary operand refused; a decimal literal's value is
  the binary64 float it holds (`0.1df` is `0.1000000`); a floating suffix the language does not write gives an unknown
  type, and `_Float128x`, which neither ABI provides, is refused by name.
- **(mbse-expressions 30, domains as data, API 135)** **`NULLPTR` stays a code token**: nothing reads `nullptr_t`
  arithmetically.
- **(mbse-expressions 30, domains as data, API 135)** **A result's type is named by the first of C's names in the order
  its standard lists them** (`int` before `int32_t`, `long` before `int64_t`), where its type equals several stored
  domains: `NAMES`, a list of names, not of types.
- **(mbse-expressions 30, domains as data, API 136)** **A constant's type by its value** (`of`: `int`, `long` or
  `unsigned long`, `double`, `bool`) is a lookup by name; inference types a constant through its kind's `typed`, whose
  record reaches the store, since `domain_of` takes a value alone.
