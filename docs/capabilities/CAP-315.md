# CAP-315: every read within a transaction

*Implements* [FEA-030: clean mutation-based transactional API](../features/FEA-030.md).

Every read of a store happens within a transaction open on that store, as every write does
([CAP-124: writes all-or-nothing in transactions](CAP-124.md)). A read with no transaction open on the store is refused. The rule
covers reading a data object's property values and its entries, and resolving a reference (`References.resolve`,
`References.present` and `References.implied`).

## Decided

As the user decided, when asked what allowed a read outside a transaction, which no decision had allowed or refused:
"Every read happens within a transaction" (the first of the options offered). `References.resolve`,
`References.present` and a proxy's `.get()` are each refused outside a transaction, as a write is. Every caller that
reads outside a transaction is migrated.

## Design

- **What a read sees.** Within a transaction, a read goes through the transaction's overlay, so that it sees what the
  transaction has written (89 in [CAP-124: writes all-or-nothing in transactions](CAP-124.md#decided)). This rule changes nothing about that.
- **What a read-only transaction costs.** A transaction that only reads commits nothing. It writes nothing through to
  a store below, and the store tells no follower of it. mbse-schemas 0.26.27 already behaves so.
- **Loading.** A store with a store below loads an object that it does not hold when a read within a transaction
  reaches the object. The load applies the object's document as the store's committed data. Loading is still no
  transaction of the store's ((mbse-schemas 30) in [the stacked stores proposal](../../proposals/STACKED-STORES.md#decided)), and it
  happens only within the reader's transaction.
- **Objects held across transactions.** A proxy obtained in one transaction may be kept after that transaction ends.
  A read through the proxy is refused unless a transaction is open on its store at the moment of the read. A frame that
  `store.transaction(...)` gives back is read so too.
- **Stages.** The rule is built in two stages, as CAP-124's writes were (88 in [CAP-124: writes all-or-nothing in transactions](CAP-124.md#decided)):
  1. `References.resolve`, `References.present` and `References.implied` refuse a call with no transaction open on the
     store. This stage lands with [CAP-311: references stabilized](README.md#CAP-311).
  2. Every read of a data object refuses a read with no transaction open on its store. Every caller in mbse-schemas,
     and in the repositories that depend on it, is migrated.

## Open questions

- **Schema objects.** Does the rule cover reading a schema object, as validators, code generators, simplifiers and the
  builders read one? mbse-schemas reads a schema object outside the store's protocol, field by field, as tech debt
  that [CAP-126: schema objects read through the store protocol](CAP-126.md#decided) records.
