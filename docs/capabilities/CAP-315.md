# CAP-315: every read within a transaction or through a follow

*Implements* [FEA-030: clean mutation-based transactional API](../features/FEA-030.md).

Every read of a store's data happens in one of two ways. A transaction that the store's layer interprets reads it,
as every write does ([CAP-124: writes all-or-nothing in transactions](CAP-124.md)). Otherwise a follow delivers what a transaction committed, and
the follower reads what the follow delivers. Nothing reads a layer's data from outside both, and a read with no
transaction open on the store is refused. A visitor, which reads a store's data, lives only within the transaction
that made it; the store, a path and a value object outlive it. A schema object is not data in this sense: the rule
does not cover it.

## Decided

As the user decided:

- **Every read happens within a transaction** (the first of the options offered, when asked what allowed a read
  outside a transaction, which no decision had allowed or refused). A proxy's `.get()` and the resolution of a
  reference are each refused outside a transaction, as a write is. Every caller that reads outside a transaction is
  migrated.
- **A follow is the one alternative**: "Follows is the one legitimate alternative to transactions for read-only
  access."
- **A follower reads what the follow delivers**: "A follower reads what the follow delivers, and Follower
  subscriptions are layer-coupled as well."
- **Schema objects are not covered**: "CAP-315 does not cover schema objects." Validators, code generators,
  simplifiers and the builders read a schema object with no transaction open, as they do now.
- **An entry's reference is matched, not bound** (agreed to the recommendation offered). No pattern binds a relation
  entry by its reference. An entry has no identity beyond its relation, its links and its properties, so that a
  pattern whose symbols are given the references of the objects it links, and whose spec gives the entry with those
  properties, gives a frame exactly where the entry holds. A client checks an entry's reference, as a frame's witness
  carries one, by such a pattern.
- **A visitor lives within a transaction**: "any class that implements Visitor must be have a lifetime that is
  lexically scoped (such as `with store.transaction()`). Paths on the other hand are durable."
- **The store is not scoped**: "the store survives indefinitely."
- **A value object is not its visitor**: "a value object and a visitor of that value object are not necessarily the
  same thing." A value object, such as a reference, is data, and outlives the transaction. The visitor that reads it
  does not.
- **Frames hold bindings and assignments**: "Frames hold symbol bindings and property assignments, not proxies."
- **Data harvested is stale**: "Programs are permitted to harvest data by reading visitor inside of a transaction, but
  any data held is basically stale on contact."

Each layer of a stack has its own transaction interpreter, coupled with the layer, as the user decided in
[the stacked stores proposal](../../proposals/STACKED-STORES.md#decided). A transaction's reads are therefore the work
of that interpreter.

## Design

- **What a read sees.** Within a transaction, a read goes through the transaction's overlay, so that it sees what the
  transaction has written (89 in [CAP-124: writes all-or-nothing in transactions](CAP-124.md#decided)). This rule changes nothing about that.
- **What a read-only transaction costs.** A transaction that only reads commits nothing. It writes nothing through to
  a store below, and the store tells no follower of it. mbse-schemas 0.26.27 already behaves so.
- **Resolving a reference.** A symbol given a reference binds what the reference designates (references 8 in
  [CAP-141: queries start from a referenced object](CAP-141.md#decided)). The layer's interpreter finds it through hooks that the layer provides: the
  object at a path among what the layer holds, the entries of a relation that link an object, and the schema that a
  path implies through the layer's schemas. What happens when the layer does not hold the object is the layer's own
  policy, which its hook carries. A store in memory gives none. A cache layer passes the transaction down the stack
  whole ([CAP-308: stacking by mutation transactions, in one round trip](README.md#CAP-308)). A client resolves a reference by a transaction whose symbol is
  given the reference, not by a function over the Store interface, so that `References.resolve` is withdrawn.
- **A follow.** A follower reads what the follow delivers: each committed transaction's effect, which designates
  objects by their references. It reads nothing else of the layer. A subscription is coupled with its layer, as the
  layer's interpreter is.
- **A visitor's lifetime.** A visitor is anything that implements one of the visitor protocols over a store's data: a
  data object's proxy, and the visitors of its properties, its adjacencies, its entries, its containers and its
  values. It exists only within the transaction that made it, and any use of it after that transaction ends is
  refused. `store.singleton(...)` gives a visitor, so that it is called within a transaction. The store itself
  implements `Visitors.OfStore` and lives on.
- **What outlives a transaction.** A path, a value object such as a reference, and every value a program copies out of
  a visitor outlive the transaction. A program may harvest data so, within a transaction, but what it holds afterwards
  is stale from the moment the transaction ends. To read the store again, it opens another transaction and gives a
  symbol the reference it kept.
- **Frames.** A frame that `store.transaction(...)` gives back holds its symbols' bindings, each object by its
  reference, and the property values it assigns, not visitors.
- **A value object apart from its visitor.** In mbse-schemas today, one proxy is both a value object and its visitor:
  `store.References.OfObject(...)` gives a proxy that holds the value. Stage 2 separates them, so that the value
  outlives the transaction and the proxy does not.
- **Stages.** The rule is built in two stages, as CAP-124's writes were (88 in [CAP-124: writes all-or-nothing in transactions](CAP-124.md#decided)):
  1. `References.resolve` is withdrawn. Each of its callers, in mbse-schemas' tests and tutorials, resolves a reference
     by a transaction whose symbol is given it instead. [CAP-130: references to objects, entries and frames](CAP-130.md)'s note of what was built changes with
     it.
  2. A visitor's lifetime is the transaction that made it: a visitor used after it ends is refused, and
     `store.singleton(...)` refuses a call with no transaction open. A frame given back holds references and values,
     and a value object is held apart from its visitor. Every caller in mbse-schemas, and in the repositories that
     depend on it, is migrated.
