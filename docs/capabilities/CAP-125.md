# CAP-125: imperative transaction scope

*Implements* [FEA-030: transactions](../features/FEA-030.md). Index entry: [capabilities/README.md](README.md#CAP-125).

## As built: mbse-schemas

Met in mbse-schemas 0.22.0: a transaction's imperative scope, built in the [store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md)'s 4e-2 (`with store.transaction():` in Python, `store.transaction(() => ...)` in TypeScript), released as 0.22.0.

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(object identity 98)** As the user decided (2026-10-21), asked how code that calls builders and proxies directly gets inside a transaction once writes outside one are refused (44 in [CAP-124: writes all-or-nothing in transactions](CAP-124.md#decided)), choosing "Imperative scope too (Recommended)": A transaction has an imperative scope beside its expression: "Add a public scope beside the declarative form: Python
  `with store.transaction():`, TypeScript `store.transaction(() => { ... })` given a no-argument function. Builder
  calls work inside it as today, in the overlay. Fixtures and tutorials move to declarative upserts with mappings (92)
  where that reads naturally; builder tests keep testing builders inside the scope." Offered against declarative
  transactions only, every builder test rewritten as a transaction or moved to builders outside any store, and
  against a private scope for tests alone.
- **(object identity 103)** Imperative-scope transactions (98) are "Not on the wire": only a transaction's expression is journaled; what an
  imperative scope writes reaches the wire through a later snapshot. (Offered against a transaction derived from
  its writes at commit.)
