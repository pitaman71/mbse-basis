# CAP-171: parameters attached to every schema kind by extension

*Implements* [FEA-031: schemas as extensible data](../features/FEA-031.md). Index entry: [capabilities/README.md](README.md#CAP-171). *Relates to* [FEA-033: model parameters](../features/FEA-033.md). What a parameter is, and its model, is [CAP-112: parameters modeled as schema data](CAP-112.md).

## As built: mbse-schemas

Met in mbse-schemas 0.24.0, as [CAP-112: parameters modeled as schema data](CAP-112.md) is: the [store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md)'s 4m, built in two stages and released as 0.24.0 (Stages, as built, below).

### The extension

`mbse-schemas/Parametrics.install` extends `Schemas.OfX` with three adjacencies each:
- `Schemas.OfX.parameters` to `Parametrics.HasParameters`

- `Parametrics.install` extends each `Schemas.OfX` (every kind of schema) with one adjacency, `parameters` to
  `HasParameters` (first drafted with `values` to `BindsValue` and `objects` to `BindsObject` besides, since dropped).

### What changes

- **The core loses parameters.** `Schemas.HasParameter` goes, and so does each kind's built-in `parameters` adjacency
  and its `parameters` member in the data classes and builders; `Schemas.OfParameter` stays in `Schemas`, a name and a
  description. Parameters are declared only where `Parametrics` is installed.
- **Snapshots** write a definition's parameters as the extension's entries ([CAP-116: framework schemas extended, checked](CAP-116.md): an extension's
  relation written once); a store without `Parametrics` reads them as a snapshot made with extensions it lacks
  (Store overhaul, Decided, 19).
- **Moved to it** ("yes move the corpus to the updated Parametrics framework"): the corpus's `Grid`, `Tricky` and
  `Lives` (its `era`), so the corpora change in both languages together; PAR rewritten; SCH, BLD, SNP, PAT and INS
  where they declare parameters; the skill (python.md, typescript.md, modeling.md); the framework design's Parametrics (now here and in [CAP-113: parameters bound at their definitions](CAP-113.md), [CAP-114: parameter bindings are substituted and checked](CAP-114.md), [CAP-163: parameters bound, applied and generated beyond mbse-schemas](CAP-163.md)).

### Stages, as built

- **4m-1, `Parametrics` beside today's parameters.** `Framework/Parametrics.py` and `Framework/Parametrics.ts`, exported
  as `Framework.Parametrics` beside the other modules: `install(txn)`, the draft above, defining
  `Parametrics.OfParameters`, `Defines`, `ForValue`, `ForObject`, `HasParameters`, `BindsValue` and `BindsObject`, and
  extending `Schemas.OfParameter` and every kind; and `validate(store, defn)`. Installed before use, never by the
  bootstrap; installed again, it writes nothing. Declared in an install, a set is defined where its definition links
  it, as the draft writes it, `txn.Parametrics.OfParameters(lambda ps: ps.parameters({...}))`; imperatively, the same
  through `store.Parametrics.OfParameters`. PAR-03 to PAR-06 cover it, in both languages.

### What building it found

*What building it found the framework lacked, built in both languages:*

- Within a spec, `txn.X.Y(cb)` for a reference object schema of data records a definition where it is linked, as
  `txn.Schemas.OfX(cb)` does for a schema object; the executor makes it where it writes the link, and finds an equal
  one held (before, it created the object at once, outside the transaction's spec).
- An extension's adjacency read on a schema object no store holds yet, one being built, holds nothing (it raised).
- A schema object that existed before a transaction is updated at its commit (Object identity, Decided, 96 in [CAP-124: writes all-or-nothing in transactions](CAP-124.md#decided)); its
  entries in an extension's relations are now written at once, in the transaction's proposals, as data's are. Written
  at commit, they went into the store, and were then overwritten by the proposals' entry tables of the objects they
  link, wherever the transaction had written other entries of those objects: reading a snapshot, a definition lost
  its set where one of its parameters was for an object of the definition itself. EXT-05 asserts the entry within
  the transaction.
- Python: matching a spec's entry against an entry held that links data took the link's target for a builder.

*Snapshots*: a set is data, written with the store's data as a counted object; the definition's entry in
`HasParameters` is written once, from the definition, in the data's transaction, as an extension's relation's entries
are (EXT-05). A set's entries are data's keyed entries, written sorted by their names ([CAP-155: `unique` clauses on relation schemas govern relation cardinality](CAP-155.md), [CAP-128: graphs sent as one-transaction documents](CAP-128.md)), so a set
read back holds its parameters in that order, not as declared.

### 4m-2, every use moved, the core's parameters removed

- **4m-2, every use moved, the core's parameters removed.** `Schemas.HasParameter`, every kind's built-in `parameters`
  adjacency, the data classes' `parameters` (a scalar's equality no longer compares them), `_parameter_problems`
  (`parameterProblems`, `sameParameters`), the builders' `parameters` member and the module data's go, in both
  languages, from `Schemas.install` too, which the bootstrap reads: the store's own schemas are those less
  `Schemas.HasParameter`. `Schemas.OfParameter` stays, a `description` (its data's `name` field kept, set by nothing
  now, as the user decided: "do not remove it"). The extension's adjacency on every kind is named `parameters`, as drafted. A pattern's `validate()` keeps its
  symbol-and-variable clash; the clashes with parameters are `Parametrics.validate`'s.

  Moved to `Parametrics`:
  - the conformance corpus: `module` installs `Parametrics.install` first, and declares `Grid`'s and `Tricky`'s sets
    and `Lives`' (`era`) in place. *The bindings chosen, for the user's review:* `Grid`'s `n` ("Its side") and `x`, each
    for a value of `Schemas.OfInt`; `Tricky`'s `a` for a value of `Schemas.OfInt`, `b` of `Schemas.OfStr`, `c` for an
    object of `Grid` and `d` of `Tricky` itself, so that the corpus holds both ends and a parameter for an object of its
    own definition; `Lives`' `era` for a value of `Schemas.OfStr`. Both corpora regenerated, byte-identical; CONF-04
    reads `module` into a store that installed `Parametrics` first.
  - the suites: PAR rewritten (PAR-01 to PAR-04, 4m-1's PAR-03 to PAR-06; the core's two cases gone); SCH, BLD, SNP and
    PAT lose the core's parameters (SNP's two members shown alike through other adjacencies are a symbol and a variable;
    PAT's and SCH's clashes are a symbol's and a variable's); INS's install given nothing defines a property
    (`crm.Note`'s `text`) in place of a parameter. EXT, which declared none, is unchanged. CONF-04 and the portability
    smoke test read `module` into a store that installed `Parametrics`.
  - tutorial 1's outputs (a scalar's data printed without `parameters`), re-executed in both languages; the skill
    (`python.md`, `typescript.md`, `modeling.md`); the framework design's Parametrics (Built, Moved out, an open question),
    META_SCHEMAS.md, SCHEMA_EXTENSION.md and VISITOR_PATTERN.md where they describe parameters. the serialization design and the
    READMEs did not mention them.

  *Snapshots*: a definition's parameters are the extension's entries, its set written with the data (PAR-04); a
  snapshot round-trips into a store with `Parametrics` installed, written again the same; a store without it reads it
  as Store overhaul, Decided, 19 says, ignoring `Schemas.OfParameter`'s `for_value` and `for_object` and the kinds'
  `parameters`, and keeping the rest (the sets, now unlinked, and `Parametrics`' own schemas, which a snapshot writes as
  any store's own).

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(parametrics 4)** **First of what remains of step 4**: "4m should go before 4k or any other 4*". In two stages: **4m-1**,
  `Parametrics` and its validation, beside today's parameters (both gates at 100%); **4m-2**, every use moved, the
  core's parameters removed, the corpora regenerated.

The other Parametrics decisions, about the model, are [CAP-112: parameters modeled as schema data](CAP-112.md)'s.

## Decided by an agent, for review

Recorded in mbse-schemas' design, not marked as the user's: each *proposed* until reviewed.

### Parametrics 4m-1, fixed by the agent

*Fixed by the agent, for the user's review* (2 to 5, the model's, are [CAP-112: parameters modeled as schema data](CAP-112.md)'s):

- (1) **The name clash.** Every kind has the core's `parameters` until 4m-2, and the extension check refuses a name a
  schema has, so in 4m-1 the extension names each kind's adjacency to `HasParameters` `parameter_set`; 4m-2 renames
  it `parameters` when the core's goes. PAR-01 and PAR-02 keep testing the core's until then.
- (6) **The install's uid is `mbse.Schemas.Parametrics/1`**, as the framework's own installs are named
  (`mbse.Schemas.Paths/1`), not the draft's `mbse-schemas.Parametrics/1`.
