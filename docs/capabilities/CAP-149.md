# CAP-149: data accessed through the store protocol

*Implements* [FEA-028: one API surface for all data access](../features/FEA-028.md). Index entry: [capabilities/README.md](README.md#CAP-149).

## As built: mbse-schemas

Met in mbse-schemas 0.22.0: the [store overhaul](../../../mbse-schemas/docs/proposals/store-overhaul/README.md)'s 4e-3, which renamed `Stores.Store` `Visitors.OfStore`, routed every access to data through it, and refactored the overlay into `Proposals`, which implements it over a store or over other proposals (a savepoint); released as 0.22.0. Schema objects are still read outside it: [CAP-126: schema objects read through the store protocol](CAP-126.md).

## Decided

As the user decided: adopted, each the rule as stated, quoted where the wording matters.

- **(object identity 100)** As the user decided (2026-10-21), asking for "Visitors.OfStore — a clean API surface through which all data accesses must go", the overlay refactored "into a new Proposals.py/ts component. Proposals.py/ts implements Visitors.OfStore", and answering the three questions put: `Visitors.OfStore` is the store's protocol, and every access to data goes through it: an object's property values,
  a value object's, and the entries that link an object; `Stores.Store` is renamed `Visitors.OfStore`, and the
  proxies' store, `Proxies.OfStore`. A transaction's writes are a `Proposals`, which implements `Visitors.OfStore`
  over the store it proposes changes to, reading through to it what it does not hold; committed, it writes into it,
  and aborted, it is dropped. A `Proposals` may be made over another ("3. yes"): a savepoint, so that a decoder
  within a transaction writes all or nothing within it.
